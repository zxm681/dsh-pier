## 一、入口与解析

- `[源码]` 服务用 `node:net.createServer`，默认仅绑定 `127.0.0.1`，只允许 `127.0.0.1`、`localhost`、`::1` 作为 host；端口默认 7410–7419。这是 TCP 字节流而非 HTTP/WS 服务器；绑定 loopback 阻止直接从局域网连入，却不隔绝本机进程或浏览器发往 loopback 的请求。证据：`packages/dsh-vscode-kit/src/server.js:13-16,29-30,62-78,100-117,186-199`。
- `[源码]` TCP `data` 进入换行分帧，再逐行 `JSON.parse`；有效入站请求/通知须有字符串 `method`，经 `authorize` 后才交 `onRequest`；超 8 MiB 无换行缓冲触发错误和连接销毁。**解析层不识别 HTTP 方法、Host/Origin 头或 WebSocket upgrade**。证据：`packages/dsh-vscode-kit/src/server.js:143-167`；`packages/dsh-vscode-kit/src/protocol.js:233-319,339-367`。
- `[源码]` 每条带 `method` 的入站消息要求顶层 token 匹配实例随机 32 字节 token；连接初始 `authorized=false`，只有正确 token 消息才标为已准入，DSH 主动请求只挑已准入 link。`links` 集合仍包含未准入 socket，连接存在不能当授权。证据：`packages/dsh-vscode-kit/src/server.js:122-124,131-161,171-183`；`packages/dsh-vscode-kit/src/protocol.js:263-276`；`packages/dsh-vscode-kit/src/index.js:63-74`。

## 二、浏览器路径及既有实验证据边界

- **WebSocket：**浏览器 API 首先发送 HTTP Upgrade 握手，裸 TCP 的首行不是合法 JSON-RPC `method` 行，服务端也没有 HTTP 101 Upgrade 回应代码；正常浏览器 WebSocket API 不能把此 socket 当成成功的 WebSocket 通道。`[源码]` `server.js:13,163-167`、`protocol.js:308-319`；`[既有抽样]` T3 第一、二检查点记载 GET/WS `dispatched=0`。这不证明所有浏览器/代理变体都不可投递字节。
- **fetch/form 等 HTTP：不能宣称完全不可达。** HTTP 请求行/头不符合逐行 JSON 对象，通常报解析错误；但发送 POST 时**正文可以是一行合法 JSON 加换行**。裸 TCP 分帧不追踪 HTTP Content-Length 或头/体边界，遇到正文里的合法 JSON 行会继续解析。如果其中含正确测试 token 与 `method`，既有隔离抽样观察到 `HTTP POST dispatched=1`。`[源码]` `server.js:163-166`、`protocol.js:308-319,348-367,263-285`；`[既有抽样]` `D:/code-workspace/.expert-taskboards/dsh-pier.json` 的 T3 两条检查点（2026-10-21 22:50:28、23:27:52）。**该抽样是构造 HTTP POST 的分派观察，不是恶意网页端到端可利用性证明**：浏览器的 forbidden headers、CORS/PNA、mixed-content、端口禁用表、浏览器版本及预检等条件未在网页环境逐一测试；跨源响应能否读与请求能否发也不同。请求体可控性 ≠ 知道 token。
- **WebRTC：**标准网页 WebRTC API 不向任意指定 `127.0.0.1:7410–7419` 暴露可直接写入 ndjson 的裸 TCP socket；这是 API/传输能力判断，不是本轮浏览器实测。`[源码]` 本端只有 `node:net` TCP 入口（`server.js:13,62-78`）；`[未验证]` 不对浏览器扩展、Native Messaging、代理/本地 helper 或未来 API 作全称排除。它们若获本机网络/文件权限，须按本机客户端另行建模。
- `[既有抽样]` 错误测试 token 后 `connected=true`，同一连接后续正确 token 消息仍可分派；`[源码]` `authorize` 拒绝返回错误/丢弃通知而不销毁 socket，下一条会重新校验（`protocol.js:265-276`、`server.js:149-167`）。这是**拒绝当前命令但保留连接**，不是错误 token 的越权分派；连接存活、命令可分派、持有正确 token 是三个独立事实。

## 三、DNS rebinding 与 Node inspector 对比

- `[推断，附条件]` DNS rebinding 可把攻击者控制的主机名解析到 loopback，尝试让网页以同源/可发请求的形式触达本机端口；只有受害浏览器允许该路径、请求字节包含可解析 ndjson、并且攻击者知道有效 token 时，才能沿本实现的受保护 `method` 分派。**Host/Origin 不是此裸 TCP 服务的协议字段**；现有解析器既不验证也不理解它们。故不能说 DNS rebinding 在网络可达层面绝对不成立，也不能把“可连接”直接升级为“有权执行命令”。证据：`server.js:115-117,143-167`、`protocol.js:263-276,308-319`；POST 有条件分派的证据见第二节既有抽样；网页 DNS rebinding 端到端未验证。
- `[先例]` 既有源码调研 `docs/先例调研-鉴权放在哪一层.md:152-175` 引述 Node inspector `src/inspector_socket.cc` 的 IP-literal Host 限制，防止基于 HTTP/WS 入口的 DNS rebinding；T3 第一检查点记录 Node v24.20.0 隔离观察 `inspector HTTP 200 / Host 400 / WS 101`。Inspector 要解析 HTTP Host/WS 握手，且该先例描述无 token 鉴权；此桥是裸 TCP ndjson、入站逐消息 token 校验，两者的**入口与防线不同**。不能把 inspector 的 Host 校验直接当作本桥已具备/必须照抄的控制，也不能仅因 token 存在就忽略 HTTP POST 字节注入面。
- `[未验证]` 上述 inspector 三项数值只来自旧检查点而非本次实验；具体 Node 版本、DNS 重绑定链、浏览器 origin/CORS/PNA 策略，以及 `localhost`/`::1` 绑定行为的跨平台差异没有本轮新证据。若未来改用 HTTP/WS 或去掉 token，必须重新设计 Host/Origin、防 rebinding 和预检策略，不得沿用本报告“无 HTTP 解析”的判断。

## 四、鉴权、凭据风险与严重度（高→中→低）

| 风险 / 利用条件 | 等级与证据强度 | 处置优先级 |
|---|---|---|
| **同用户恶意进程/可读发现文件的代码取得 token**：发现 JSON 明文含 `port,token,pid`；读到且能连 loopback 即可发合法 `method`。`server.js:122,190-199`、`discovery.js:44-57,115-131`。当前 token 是桥的能力凭据，不是独立用户授权；当前扩展只列四项能力，含读取选区/诊断与打开文件（`capabilities.js:16-22,84-132`）。 | **高（以同用户进程或发现文件读取为前提，源码证据；未做恶意进程端到端利用测试）**；若攻击者本来可任意执行同用户代码，其权限可能已经很强，等级是本桥被借用时的数据/操作面，不声称新的 OS 提权。 | 1：将本地同用户读权限视为实质信任边界限制；敏感数据不经该通道广播；未来写能力必须另加人可见会话授权。 |
| **Windows 发现文件权限不能据 `chmod 0600` 承诺强 ACL**：目录 mode `0700`、文件 mode `0600`，但 Windows 显式 chmod 失败被忽略；没有源码证据证明 DACL 隔离同用户进程。`discovery.js:38-55`。 | **中（Windows 条件风险，源码证据；未读取实际文件 ACL，也未读取真实 token）**。 | 2：在独立夹具验证 DACL/权限继承并记录可读主体；避免把 mode 文档表述成 Windows 强隔离保证。 |
| **HTTP 正文可触及 ndjson 分派 + DNS rebinding 条件链**：POST 带正确测试 token 曾分派；没有 token 的恶意网页是否能取得凭据未证，不能写成已证浏览器任意命令执行。`protocol.js:263-285,308-319`；T3 既有抽样。 | **中（字节注入/已知 token 场景已有抽样；网页可利用链未验证）**。无 token 的单独跨源网页风险需保持条件化，不作高危已利用断言。 | 2：守住逐消息 token；未来如添加 HTTP/WS 入口，另设 Host/Origin/CSRF/PNA 威胁模型和浏览器真测。 |
| **未准入连接资源与出站广播口**：错误 token 不断连；`broadcast()` 向 `links` 中所有连接通知，若上层将敏感内容作为通知广播，未准入 socket 也可能接收；当前包内未找到生产 `broadcast()` 调用，**不声称实际敏感内容已泄漏**。`server.js:139-141,163-171,234-250`；唯一现有调用为 `packages/dsh-vscode-kit/test/server.test.js:189`。 | **中（条件性设计风险，源码可达路径；实际敏感 payload 未证）**。裸连滥用连接/解析资源也须以实际负载证明，不把可能性写为 DoS 既成事实。 | 2：敏感通知仅发送给已准入 link；限制连接数、认证时限及消息频率需另立变更/负例。 |
| **错误 token 后同连接可继续尝试**：错误消息得 -32001/通知丢弃，后续正确 token 可准入；64 字符 hex 字符串来自 32 随机字节，不靠断连作为保护。`server.js:122,149-161`、`protocol.js:265-276`；T3 既有抽样。 | **低（行为已观察；不能据此推导暴力枚举现实可行或认证绕过）**。 | 3：监测异常频率、后续加认证失败限制；不能把“断连”当替代鉴权。 |

当前 `request()` 发送时可自动附 token，而 `notify()/respond()` 默认不带、`respondError()` 恒不带；响应先按 `id`/无 `method` 分流，不执行同一路入站请求鉴权（`protocol.js:146-180,183-230,240-253`）。`docs/先例调研-鉴权放在哪一层.md:209-225` 的“建连后验一次、不在每条消息里带”的概括与**当前 `server.js:149-159`、`protocol.js:265-276` 逐条验证请求/通知**不一致；此处以当前源码为准，旧调研作为先例而非现状证明。不得给未认证者的 -32001 响应附送 token。

## 五、建议、未验证项与解锁条件

1. **先保全既有防线**：保留 loopback bind、实例随机 token、每条入站请求/通知校验与已准入 link 过滤；测试要分别断言“TCP 建立”“分派”“凭据来源”，并做负例/变异检验。更改响应/通知凭据行为须先审计泄露面（`server.js:115-159`、`protocol.js:146-276`、`index.js:63-74`）。
2. **最低修复建议而非本任务实施**：广播按授权过滤或明确禁止敏感 payload；为连接/分帧/失败速率设边界；对 Windows ACL 做独立权限夹具验证；任何新 HTTP/WS 入口独立作 Host/Origin 及 DNS rebinding 评审。此处没有变更产品代码；当前结构不能宣称这些措施已完成（`server.js:163-171,234-237`、`discovery.js:45-55`）。
3. **未测清单**：浏览器真实 fetch 简单/非简单请求与各版本 PNA/CORS/端口策略、DNS rebinding 端到端、WebRTC/浏览器扩展或本地代理转发、Windows DACL 与同用户隔离、任意敏感 payload 的生产广播、资源耗尽阈值、TLS/跨主机迁移；本轮仅复用旧三次抽样，不补实验。`work/PM-恢复检查点.md:8,29-32` 明确其证据边界。
4. **准确解锁**：T3 报告完成只解除“缺少威胁面报告”的依赖，不代表代码加固、网页攻击排除或自动编辑安全验收。现有扩展能力仅四项（`capabilities.js:16-22`）；`work/协作编辑-技术门槛.md:5-9,30-46` 的编辑、会话授权、撤销、路径/缓冲区 CAS 与隔离要求仍为 **NO-GO**。后续必须走明确的人类裁决、隔离夹具、独立评审及真宿主负例；不得以本 T3 的 done 自动打开编辑功能。
