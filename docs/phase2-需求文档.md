# 阶段 2 需求文档：VSCode ↔ DSH 桥接协议库（打样范围）

> 状态：完成（访谈 2 轮 6 问，全部有明确答案）。进入阶段 3 可行性分析。
> 日期：2026-10-21。访谈对象：用户（主人）+ 我（大肥鱼）。

---

## 一、目标（一句话）

做一个 **DSH 侧桥接协议库**（npm 包），让任意 DSH 插件能通过一条标准化、可复用、低耦合的通道调用 VSCode 能力；打样首个能力为 **openFile + 读编辑器选区**。

## 二、访谈结果（6 问全录）

| # | 问题 | 答案 | 理由/影响 |
|---|---|---|---|
| 1 | 通信通道 | **loopback TCP + 发现文件** | 能驱动已开着的 DSH GUI；四段式链路完整；DSH 侧纯 cordis 插件开 TCP，扩展侧零依赖 |
| 2 | 首能力 | **openFile + 读编辑器选区** | 最小闭环横穿全链路；只读不注入，避开踩坑 9（静默注入红线）；验证完即有实际用途 |
| 3 | 消费者定位 | **先自用，接口预留多插件** | 消息带 namespace、能力带前缀等解耦机制从一开始就做对，升级不返工 |
| 4 | VSCode 侧形态 | **自研薄扩展**（独立 id） | 四段式完整可练手；不被他人的版本绑定；验证协议库独立性 |
| 5 | 信任模型 | **token 鉴权 + 首次握手确认** | 握手时桥上报身份，VSCode 侧首次弹窗确认一次并记住；敏感能力将来再加逐能力确认 |
| 6 | 交付形态 | **本地包 + vsix 手动装** | 迭代快；日后想发布随时能发 |

## 三、硬约束（来自 m00159 主人原始设想 + 本会话补充）

1. **简洁为先**：模板打样优先套用已验证方案（dsh-vscode-bridge / dsh-acp-door 的协议模式）。
2. **低耦合**：新功能尽量不与原设计耦合；从零设计则模块间不耦合。→ 协议库与具体插件解耦、与 DSH 版本解耦（握手报 dshVersion + capabilities）。
3. **沟通节奏**：设计期间多与主人交流，不一次思考几十分钟；每阶段结束紧凑汇报 + 最多一问。
4. **验证优先**：模板完成后先最小测试，验证通过再做总结；失败要报失败。
5. **落文件**：每阶段结论落盘（本项目 docs/ 目录）。
6. **许可证**：只参考 MIT/BSD/Apache 方案；不碰 GPL/AGPL。
7. **钉版**：理解过的第三方源码 commit 要记录版本号，上游更新后理解不过期。
8. **安全红线**：注入内容必须让用户选择/编辑，不能静默发消息（踩坑 9）。

## 四、范围（打样模板的范围，防止蔓延）

### 4.1 打样要做（in scope）

- **DSH 侧 npm 包**（名字候选：dsh-vscode-kit / dsh-vscode-protocol，待查重后定）：
  - cordis 插件：启动 loopback TCP 服务（端口区间扫描 + 发现文件 0600 原子写）
  - 协议：ndjson JSON-RPC 2.0 + token 鉴权 + 能力上报（capabilities）
  - 核心库：请求-响应配对、超时、错误传播、多消费者 namespace 隔离
  - 首个方法族：`vscode.*` —— `vscode.openFile({path, line?, column?})` + `vscode.getSelection()`
- **VSCode 侧薄扩展**（独立 id）：
  - 连接发现文件中的 TCP 端口，token 校验
  - 首次握手弹窗确认（记住授权）
  - 转发 `openFile`（用官方 `vscode.window.showTextDocument` + `--goto` 语义）与 `getSelection`（`vscode.window.activeTextEditor`）
  - 未信任工作区（Workspace Trust）不启动后端
- **示例消费者**：一个 DSH 插件（demo），证明「第三方插件零耦合接入协议库」。
- **最小测试**：协议层单测 + 一次真机端到端（真 DSH 插件 → TCP → 扩展 → VSCode 打开文件/读回选区）。

### 4.2 打样不做（out of scope，防蔓延）

- ❌ 注入/编辑类能力（踩坑 9 红线，等交互设计单独做）
- ❌ 逐能力白名单/授权面（首版只做「首次握手确认」这一个确认面）
- ❌ 多扩展/多 VSCode 实例仲裁（发现文件已支持多 DSH 实例；反向多 VSCode 不做）
- ❌ Remote-SSH/WSL 反向连通（只做本机 loopback；WSL 正向用 localhostForwarding 白捡）
- ❌ npm 公开发布 / Marketplace 上架（本地 link + vsix 手动装）
- ❌ 面板/UI/嵌 webview（那是 Fengze233 的路线，不是本库）

## 五、非功能需求（打样也要守住的底）

- **零/低依赖**：DSH 侧优先零依赖（记取 bridge 的 `ERR_MODULE_NOT_FOUND` 教训）；扩展侧只用 VS Code API + node 内置。
- **版本走廊**：DSH 0.2.1-rc.2 起步，握手报 `dshVersion` + `capabilities`，方法族缺失降级不整体崩。
- **安全**：token 每实例随机、发现文件 0600、原子写、退出回收、死 pid 残留清扫；loopback 仅 127.0.0.1。
- **可观测**：连接/握手/拒绝/超时都要有日志与诊断码（学 openFile 的 `missReason` 模式）。

## 六、验收标准（最小测试怎么算通过）

1. DSH 插件调用 `vscode.openFile({path})` → 本机 VSCode 打开对应文件（可带 line:column）。
2. DSH 插件调用 `vscode.getSelection()` → 拿到当前编辑器选中文本（无选区返回空 + 明确状态）。
3. 未授权（token 错 / 未确认）→ 返回结构化错误码，不静默挂起。
4. 两个 DSH 实例并存 → 各自发现文件、互不干扰。
5. 协议库单测全绿（请求-响应配对、超时、并发、错误传播）。
6. 示例消费者插件与协议库之间只有公开 API 接触点（低耦合可验证）。
