## 1. 目标与非目标

**一句话（只对「消费已发布能力」成立）**：把「第三方 DSH 插件使用**编辑器已发布的能力**」压缩成**一个服务名 + 一个入口对象**，让对方只写一行 `inject` 加一次取服务就能调用，且永远不需要知道端口、发现文件、token 的存在。

**这句话不能外推到「第三方新增能力」**（评审 R1）：`inject` / `ctx.get` 只解决**依赖获取**，它不会在 VS Code 侧长出一个 handler。桥端能力清单是源码里的固定数组 `[码] capabilities.js:17-22`，分派表是固定对象、未登记的方法一律 `-32005` `[码] capabilities.js:217-234`；新增能力仍必须走 `AGENTS.md` 的「加新能力的三步」`[档] AGENTS.md:68-74`。两种接入成本见 §2.1 / §2.2。

现状已经是这个形状：`ctx.provide('dshVscodeKit', facade)` `[码] index.js:300`，消费者 `export const inject = ['dshVscodeKit']` + `ctx.get('dshVscodeKit')` `[码] demo:18、demo:26`。**本文的产出不是新机制，而是把已有 facade 冻结成契约**，并写清它现在没做到的部分。

**不做**：

| 不做 | 理由 / 证据 |
|---|---|
| 不暴露传输细节（port / token / 发现文件 / link / connSeq） | 铁律 8 的分层已把它们留在 server 内部 `[码] server.js:124-137`；snapshot 里虽能看到 port/discoveryPath，但源码自己标注「不属于稳定 API」`[码] index.js:171` |
| 不新增第二个接入点（不再加服务名、不加注册表） | 用户要「最好只留一个钩子」；多一个入口就多一套版本与权限要维护。**注意**：一个入口只减少「入口数量」，不减少「桥端维护」——见 §2.2 |
| 不承诺跨大版本的二进制/语义兼容 | 见第 4 节；协议只有单整数版本号 `[码] protocol.js:46` |
| 不代理任意 VSCode 命令 | 能力表是白名单四条目 `[码] capabilities.js:17-22`，未实现方法统一 -32005 `[码] capabilities.js:229-234` |
| 不代第三方注册入站能力 | 入站只认 `bridge.ping`/`bridge.hello`，其余 -32601 `[码] index.js:370-390`。这是**今天的硬边界**，要放开属第 7 节待决 |
| 不承担编辑授权语义 | 编辑 grant **授给谁、授权含义**属协作编辑自身设计 `[档] work/协作编辑-M0复核与保守裁决.md:16-19`，钩子只管「能不能把请求送到编辑器」。**精确边界**（第 3 轮返工补）：本契约**不定义**「谁有资格授权」，但**规定**「没有有效绑定时不许执行」以及判定的位置与形态（§6.1 / §6.1.1）——授权语义归协作编辑，绑定门的执行归本钩子 |
| 不保证静默重试成功 | 异步动作必须走请求（第 5 节），通知没有失败回执 |

## 2. 钩子的形状

**唯一接入点** = 服务名 `dshVscodeKit`，入口对象 = `apply()` 里 `ctx.provide` 的那个 facade。

| 要素 | 取值 | 证据 |
|---|---|---|
| inject 服务名 | `'dshVscodeKit'`（大小写敏感） | `[码] index.js:300`、`[码] demo:18` |
| 入口对象 | facade（普通对象，非 Service 子类） | `[码] index.js:260-289` |
| 最少必需字段 | 只有两个：`waitReady(ms)` 与 `request(method, params, opts)`；糖衣 `vscode.*` 是可选便利 | `[码] index.js:263、277` |
| 就绪语义 | 服务**无条件** provide，监听未起时方法仍在、调用返回 `-32007`（`reason:'server-not-ready'`） | `[码] index.js:242-243、291-300`；铁律 1 明确禁止传 check 谓词 `[档] AGENTS.md:7-8` |
| 消费者不知道的东西 | 端口、token、发现文件路径、link、connSeq、TCP 全都不在入口对象上 | `[码] index.js:40-61` |

### 2.1 消费已发布能力：真·最小接入（1 行依赖 + 1 次 get）

`inject` 是纯字符串数组声明、不需要 import cordis `[档] docs/phase5-打样日志.md §1.1`；`ctx.get` 拿到的 facade 在监听未就绪时也**不是 null**，避免「拿到 `{}` 再裸 TypeError」`[码] index.js:236-243`。

第三方消费示例（服务名、参数名与源码一致；**必须 `await` 且 `catch`**，理由见 §5.1「成功外形的错误结果」）：

```js
export const name = 'my-plugin'
export const inject = ['dshVscodeKit']            // 唯一需要加的一行

export function apply(ctx) {
  const kit = ctx.get('dshVscodeKit')             // 唯一 entry 点
  ctx.effect(() => {                              // 长任务自己管生命周期
    ;(async () => {
      try {
        const r = await kit.vscode.openFile({ path: 'C:/w/a.md', line: 3 })
        if (r?.opened !== true) throw new Error('bridge returned an unexpected shape')
        // 到这里才算「确认业务成功」，不是「没报错就算成功」
      } catch (err) {
        // 失败必须落地成可见结果：err.code 是稳定错误码，err.data 是诊断
        console.error('[my-plugin] openFile failed', err?.code, err?.message)
      }
    })()
  })
}
```

真实消费者就是这个形状：`readSelection()` / `openFile()` 都 `await` 并把失败转成 `{ok:false, code, message}` `[码] demo:36-56`。**契约要求**：本文与后续所有示例都要与真实消费者同形——禁止出现「调用不 await、`catch` 里空转、把返回值当成功」的写法。

### 2.2 第三方新增能力：不是 1 行，是三步（绕不过）

| 步骤 | 必须做什么 | 为什么绕不过 |
|---|---|---|
| ① 桥端登记 | `CAPABILITIES` 数组加条目 + `handlers` 表加实现 | 清单是源码固定数组 `[码] capabilities.js:17-22`；`dispatch` 只认 `handlers[method]`，未登记即 `-32005` `[码] capabilities.js:229-234`。这里**没有**任何第三方注册函数 |
| ② DSH 侧糖衣（**可选**） | 在 `kit.vscode` 加一行转发 | 通用 `request('vscode.xxx', …)` 已能直发任意方法名 `[码] index.js:263、129-162`，糖衣不是硬需求；若加，`VscodeKit.vscode` 与 facade 的 `vscode` **两处都要加** `[码] index.js:55-60、245-258` |
| ③ 双端测试 + E2E + 真机 | 两侧单测、`scripts/e2e.mjs`、真 VS Code 验一次 | `[档] AGENTS.md:68-74`；单测与 E2E 都用假宿主，证明不了编辑器那半边 `[档] AGENTS.md:60-62` |

**结论（也是本篇最容易被误读的一句）**：「一个服务名」省掉的是**第三个入口**，不是桥端实现。任何声称「第三方不改桥包就能新增 VS Code 能力」的设计，都必须另外提出扩展机制与部署/权限边界；**在当前源码下这个能力不存在**，本文不承诺它。

### 5.1 「成功外形的错误结果」（`[规定]`，评审 R4）

**问题不是「会不会失败」，而是「失败了却长得像成功」。** 代码事实：响应识别只看「有 `id`、无 `method`」`[码] protocol.js:240`，命中 pending 后——**有 `error` 就 reject，否则一律 `entry.resolve(msg.result)`** `[码] protocol.js:242-251`。因此对端只要回一条合法 JSON-RPC 空响应 `{"jsonrpc":"2.0","id":<pending>}`，调用方就拿到 `resolve(undefined)`：不抛错、不超时、不带任何诊断。

**这不只是理论**：协议层只在「我方作为被调方」时把 `undefined` 归一成 `null` `[码] protocol.js:293-303`——那是**对自己的约束**；对端返回什么，协议层不做形状校验（`handleMessage` 命中即 resolve）。

**契约要求（facade 边界必须校验，不可下推给消费者）**：

1. 每个走 facade 的调用返回后，**在返回给调用方之前**按该能力的返回契约校验形状；不合格即抛 `-32009 invalid-response`，`data = { method, got, expected }`（`got` 用 `typeof`/键名摘要，不倾泻整个响应体）。

## 6. 安全边界

**谁能调**：任何在 DSH 进程内、声明了 `inject: ['dshVscodeKit']` 的插件。**当前没有 per-plugin 授权**——拿到服务就能调任何 `vscode.*` `[码] index.js:55-60、245-258`，`method` 前缀不做调用者校验 `[推导]`。威胁模型里「同用户进程可读发现文件拿 token」这一条同样适用于任何已加载的插件 `[档] docs/威胁模型-通道可达面.md:32`。

### 6.1 会话/窗口绑定：写入类能力的前置硬门（`[规定]`，不再是「可暂缓选项」）

**定位变更（评审 R3）**：旧稿把「目标窗口/会话」列为第 7 节待决 #1，读起来像「可以先不做」。**这不成立**——它是**写入类能力的前置硬门**：没有绑定就不放行写。读操作（当前四项只读能力 `[码] capabilities.js:17-22`）不改宿主状态，可以维持「单活跃编辑器」；**任何写入类**（未来的写文件、`applyEdit`、保存、改选区、暂存/提交）在绑定成立之前**一律拒绝**。

**绑定的三条要求**（`[档] work/协作编辑-M0复核与保守裁决.md:16-19`，逐字对齐）：编辑 grant 必须绑定「DSH 会话 + 指定 VS Code 窗口」，断线/重连即撤销；token 只是连接准入，**不等于**编辑授权；缓冲区变化来源不明时只冻结该文件。

### 6.1.1 执行端闭环：代际绑定 + 逐操作复核 + 失败闭合（`[规定]`；第 3 轮返工，**① 与新增 ①-b/①-c/①-d 为第 4 轮重写，修 new-2 跨域计数**）

**T52 多窗口落地补充（不改 grant 的安全判据）**：写路径带 `target` 一律 `-32014 target-not-routable`（`undefined` / `null` 按未给处理），判定在 `_bindWriteTarget` **之前**，不会借 target 改写授权目标；写目标永远由 grant 记录的 **link 对象引用**决定。依据：[index.js:1663–1678](<../packages/dsh-vscode-kit/src/index.js#L1663-L1678>)。绑定读（`sessionId` + `SESSION_BOUND_READS`）若同时给 target，先解析、再取 grant 记录；无有效记录仍报 `-32010`，两条有效 link 不同则 `-32014 target-unauthorized`，**不回退 `_activeLink()`**，也不静默忽略 target。依据：[index.js:1679–1708](<../packages/dsh-vscode-kit/src/index.js#L1679-L1708>)。窗口号仅用于发现/读路由，不替代 grant、epoch 或对象身份；`windowId` 与 `connSeq` 禁止互相比（字段表见 §3.1）。

**为什么「发包前拒」不够（评审 R3 的核心）**：发送前的门只能证明**那一刻**绑定有效，证明不了发包之后、执行之前的状态：

- 请求在途时连接断了或换了新连接 → 旧 grant 该失效，但请求已经在网线上；
- 同一连接上后续又授权了**另一个窗口**，而这条在途请求属于旧窗口；
- 通用 `request('vscode.xxx', …)` 与糖衣走**同一条链路** `[码] index.js:263、156`，协议上看不出哪条是写；靠方法名白名单拦不住未来的写方法。

所以闭环必须落在**执行端**，且必须**逐操作**判，不能只判一次。

**① grant 关联 `session + window + authorization epoch`**

> **第 4 轮返工（回应评审 new-2，blocker）：代际值的计数域写错了，本节重写。**
>
> 上一稿把**宿主进程级**的 `connSeq`（`[码] server.js:137` 把它定义在整个服务实例上、`:178` 每条新连接 `link.connSeq = ++connSeq`）与**扩展侧每个窗口各自独立**的本地连接计数，当成同一个 `connectionGeneration`，还要求两端「逐字相等」。这是**两个不同的计数域**：DSH 先接窗口 A 再接窗口 B 时，宿主侧是 1 与 2；而 A、B 是两个独立的扩展 host 进程，各自都是本进程第一次 `attach`（`[码] connector.js:132-172`，那里**连代际字段都没有**），本地纪元都自然可以是 1 —— 于是**没有任何异常的正常场景**下就是 `2 ≠ 1`，有效 grant 被判成过期。
>
> **结论：这不是实现的错，是契约把两个域写成了一个域。** 本节改为「**单一生成方 + 线上值**」，并删掉「两端各自计数」这个前提。

| 字段 | 含义 | 取值来源 |
|---|---|---|
| `sessionId` | DSH 侧发起协作编辑的会话 | `[规定]` 宿主侧会话标识（**当前不存在**，需新增） |
| `windowId` | 指定的那一个 VS Code 窗口 | `[规定]` 窗口身份（**当前不存在**；`connSeq` 冒充不了，见上表）。**本轮不要求它参与代际判定**，理由见 ①-b 的「窗口绑定怎么成立」 |
| `grantEpoch` | **授权快照的身份值**（取代上一稿的 `connectionGeneration`，字段语义收窄、更名以免与「连接序号」混淆） | `[规定]` **唯一生成方 = DSH，生成时机 = 授权那一刻**，与 `grant.id` 同批产生。取值 `[实现]`：opaque 不可猜测值（如 128-bit 随机 hex），**每次授权一个新值**、跨窗口唯一、**不可排序、不可由对端推断**。它是**线上值**：DSH 随 grant 报文下发 → 扩展保存 → 写请求原样回带。**两端都不许自己重算，也不许由 `connSeq` 换算** |
| `boundConnSeq` | `[规定]` **纯诊断的惰性字段**：DSH 记下授权时承载连接的 `link.connSeq` | 只进日志与错误 `data` 的人读信息。**不得**参与等值/排序判定，**不得**下发给扩展当判据 |

> **`[2026-10-22 落地]`** 前两行里「**当前不存在**」已过期，字段本身进了实现：`sessionId` / `windowId` 都在 `GrantStore.issue()` 时写进 grant 记录（`[码] packages/dsh-vscode-kit/src/grant.js`），墓碑里也保留（直到被 `GRANT_TOMBSTONE_LIMIT` 挤掉）。分工与本节定性一致——`sessionId` **参与一致性校验**（`judgeSession()`：身份只从两处取，扩展侧是承载连接上由 `bridge.hello` 登记的会话、DSH 侧是显式传入的调用方上下文；业务 `params.sessionId` 一律拒，否则等于自证），`windowId` 仍**只作人读标签、许可为 `null`**，不参与代际判定。`grantEpoch` / `boundConnSeq` 两行的规定原样落进代码，一字未改。

`grantEpoch` **是等值判据，不是排序判据**：比较的两端是「grant 报文里的值」与「请求回带的那个值」——**同一个由 DSH 生成、经线上传输的值**；**不是**「宿主计数器 vs 扩展本地计数器」。三条一起禁止，一条都不许放宽：

- **禁止**把 `connSeq` 当身份：它的口径是**建连先后**（`[码] server.js:127-137、178`），与「授权给了谁」无关；
- **禁止**「取当前最大序号」或「哪条活着用哪条」来挑写目标：那正是 `connSeq` 被误用的根源——**拿排序当身份**；
- **禁止**要求两端**各自计算**一个代际值再比是否相等：上一稿的错，任何一侧换了计数起点就误判（本轮唯一的 blocker 就是这个）。

**①-b 代际值怎么产生、怎么传、怎么存、怎么失效（`[规定]`，本轮写死，不留猜测）**

**（1）传输位置——判据只出现一次，两端用的是同一份**：

| 环节 | 报文 / 字段 | 方向 | 谁生成 | 谁判定 |
|---|---|---|---|---|
| 建立 grant | `bridge.grant` 能力请求，`params.grant = { id, epoch, sessionId, windowId? }`（方法名 `[实现]` 可定，**字段名与语义本轮写死**） | DSH → 扩展 | DSH | 扩展做结构校验后存档 |
| 写请求 | 现有 `link.request` 的 `params.grant = { id, epoch }`（**顶层字段**；糖衣与 `request('vscode.xxx')` 同形，不因入口不同而异） | DSH → 扩展 | DSH 从自己存的那份**原样复制**，不重算 | 扩展逐操作比对 |

- **不新开通道、不新开入口**：grant 报文与写请求都走**同一条已准入连接**、同一个 `bridge.*` 命名空间（`[码] index.js:156、263`）；扩展侧仍只有唯一漏斗 `handleInbound` → `dispatch`（`[码] connector.js:85-99`）。§7 #2 的 (a) 不变：第三方看不到 `grant` / `epoch` 这些字段。
- **DSH 侧「存的那份」**：`grants[sessionId] = { id, epoch, link, windowId?, boundConnSeq }`，其中 `link` 是**对象引用**，不是序号。发写请求时，目标是 `grants[sessionId].link`（**按身份**），**不是** `_activeLink()` 的 argmax 结果——`_activeLink()` 只服务读路径的「单活跃编辑器」（`[码] index.js:78-93`，口径见 `[档] AGENTS.md:16`）。

**（2）执行端保存与失效时机**：

| 事件 | 动作 |
|---|---|
| 收到 `bridge.grant` 且结构校验通过 | 以 `grant.id` 为键存入**进程内**表：`{ id, epoch, link, cause: null }`；`link` = **收到这条报文的那条连接实例**（对象引用，不取序号）。**每窗口同时最多 1 个有效 grant**：新 grant 到达即覆盖，旧 grant 置 `cause:'superseded'` |
| 承载连接 `close`（断线 / 重连 / 进程退出） | 该连接投递过的所有 grant 立刻置 `cause:'disconnected'`。**这一步必须在执行端本地完成**：撤销的正确性不依赖 DSH 事后补发撤销报文（跨进程通知可能根本发不到，那就成了「靠运气闭合」） |
| 会话侧主动撤销 | 收到撤销报文（`bridge.revoke`，`[实现]` 可选）→ `cause:'revoked'`。**没有这条报文也不影响正确性**：关连接即撤 |
| 扩展 host 重启 | 全部 grant 消失，等价于「从未授权」。grant **不落盘**（落盘等于把一次授权复制到别的进程和别的时段） |
| 墓碑 | 失效的 grant 不立刻丢，保留 `{ id, epoch, cause }` 供诊断，按最近 N 条（`[实现]` 建议 32）淘汰。墓碑**不参与放行判定**，只决定 `data.reason` |

**（3）窗口绑定怎么成立（不依赖任何数值身份）**：grant 是**投递即绑定**——它只被发到选定的那条连接，只存在**那一个窗口的扩展进程内存**里。别的窗口的扩展进程**从来没有**这条 grant，所以「改投另一个窗口」必然落到 `no-grant`，不需要先知道 `windowId` 是多少。`windowId` 是人读标签与会话侧一致性提示，**不是安全判据**。这样本轮不必先把 §7 #1 的窗口身份来源做完，代际判定也不会被它拖成依赖。

**①-c `-32010` 的五个 `reason` 怎么分（`[规定]`，与既有码表逐条对齐）**

执行端判定的**唯一顺序**，先命中先返回，**不做多因合并**：

| 序 | 条件 | 码 + `reason` | 备注 |
|---|---|---|---|
| 1 | 写入类请求未带 `params.grant` | `-32010` `no-grant` | 「从未申请绑定」，与 §6.1 表首行同义 |
| 2 | `params.grant.id` 在本地表**查不到**（含墓碑已淘汰、host 重启后） | `-32010` `no-grant` | 保守归「没有可用绑定」，处置相同 |
| 3 | 命中墓碑且 `cause = 'disconnected'`（**承载连接已换/已断**） | `-32010` `grant-generation-stale` | 典型场景：重连后旧请求晚到 |
| 4 | 命中墓碑且 `cause ∈ {'superseded','revoked'}` | `-32010` `grant-revoked` | 「已有新授权覆盖」或「人撤销了」，与 §6.1 表第四行同一个语义 |
| 5 | 命中有效 grant，但 `params.grant.epoch !== stored.epoch` | `-32010` `grant-generation-stale` | 冗余校验（`id` 已唯一）；fail-closed 成本近零，留着挡「看错/拼错/伪造同 id」 |
| 6 | 命中有效 grant，但 `stored.link !== 当前持有该请求的连接实例` | `-32010` `grant-generation-stale` | **进程内对象身份比较，不比对任何数字**——这一条取代上一稿的跨域等值 |
| 7 | 以上全部相等 | 放行，继续进 handler 直到线性化点 | `sessionId` 的一致性由 **DSH 发送前**判；扩展侧没有第二份会话概念，不重复判（避免两处口径漂移） |

**为什么 `id`、`epoch`、连接身份三个都要**：`id` 回答「这是哪一次授权」，连接身份回答「同一个窗口里，请求是不是走在那条被授权的连接上」，`epoch` 回答「授权快照没被替换、没被看错」。三者正交，各自独立 fail-closed，任一条缺失都不会被别的条补上。

**② 执行端在写入线性化点之前逐操作复核，`generic request` 不得免检**

- **写入线性化点（`[规定]` 定义）**：该能力 handler 里**第一次改动宿主状态**的那次调用（例：`host.openTextDocument` `[码] capabilities.js:109`；未来的写文件 / `applyEdit` / `save` 各自在自己的登记项里写明）。线性化点**之前**拒绝 = 零副作用；**之后**拒绝 = 已落点，见 ④。
- **复核位置**：执行端唯一漏斗 `handleInbound` 交给 `dispatch` **之前** `[码] connector.js:85-99`，以及 `capabilities.dispatch` 分派进 handler **之前** `[码] capabilities.js:229-235`。两处同在一个进程内，调用方绕不过去。
- **复核内容**（逐操作、不看缓存）：按 ①-c 的七行顺序判——请求携带的 `params.grant.id` 与 `params.grant.epoch` 必须与执行端**当前**持有的那份 grant 相等，且**当前持有该请求的连接实例就是 grant 的承载连接**（对象身份比较）。任一不等即拒。**不存在「扩展侧自己算一个当前连接纪元再比」这一步**——那是上一稿的跨域比较，已撤销；扩展侧从头到尾没有自己的代际计数器。
- **`generic request` 不得免检**：不按「是不是糖衣」决定要不要查，而按「该能力是否登记为写入类」决定（清单来自 §2.2 第①步的登记项）。糖衣与 `request('vscode.xxx')` 在协议上不可区分 `[码] index.js:156、263`，所以「只查糖衣」等于不查。
- **今天不会以「漏检」形态出现**：写入类能力在接口层还不存在（本节末段），所以这条约束目前无执行对象，但它必须先写死，否则写能力一落地就是无门状态。

> **`[2026-10-22 落地]`** 「目前无执行对象」已过期：写入类清单现在非空（`[码] packages/dsh-vscode-kit/src/grant.js` 的 `WRITE_METHODS = ['vscode.applyEdit']`），这条约束对每一个登记项都真的在跑；扩展侧的两处漏斗（能力层 `capabilities.js` 与连接层 `connector.js` 的 `dispatch` 之前）用的是**同一个函数** `extensionWriteGate()`，不存在第二份判定。

**③ 失效即失败闭合，禁止改投活跃编辑器**

§6.1 那张表覆盖**发送前**的三种；下表补**在途**与**执行端**两种，两者共用同一个码，区别只在 `data.reason`：

| 触发 | 判定层 | 码 + `reason` | 处置 |
|---|---|---|---|
| **发包后目标连接消失 / 已换成别的连接** | DSH 侧在途 | `-32010` `target-gone` | **不得重发到另一条连接**；直接失败闭合，让调用方重新申请 grant |
| **执行端发现请求与 grant 不同源**（承载连接已换、grant 已被覆盖或撤销、`epoch` 不符） | 扩展侧 | `-32010` `grant-generation-stale`（连接已换）／`grant-revoked`（被覆盖或主动撤销），分派见 ①-c | 拒绝执行并回错；**不得**退回到「当前活跃编辑器」执行 |

**为什么五种情形都归 `-32010`、不新增码（评审要求说明区别）**：`no-grant` / `grant-mismatch` / `grant-revoked` / `target-gone` / `grant-generation-stale` 这五种对调用方的**处置完全一样**——停下、去目标窗口重新申请 grant、不得重试原调用。再加一个码只会把同一条处置路径劈成两条，却不增加任何可执行信息。区别由 `data.reason` 承担（诊断字段，不是判定依据），码本身只表达「没有可用的写绑定」。**若将来出现处置确实不同的情形**（例如需要人重新确认 vs 可以自动重试），那才值得独立码——今天没有这种情形，所以不预留空码，避免又一个「定义了但零处抛出」的码（对照 `-32002` 的现状 `[码] protocol.js:21、37`）。

**④ 越过不可取消写点的操作：报真实结果，不承诺撤销**

- 请求一旦越过写入线性化点，**撤销 grant 不会让落点消失**。契约**禁止**把「撤销后零落点」当承诺（与 §5 表末行同义）。
- 正确表述：这类操作按既有裁决报告**真实结果**——成功即「已落点」；超时 / 断线即「**结果未知**」，必须按「可能已落点」处理并让人核对；`-32002 declined` 才是「人拒绝且未落点」。
- `[规定]`：将来每个写入类能力都必须在 §2.2 第①步的登记项里写明**它的线性化点在哪**、以及**越过之后失败如何报告**。没写这两项的写入类能力不得进 `CAPABILITIES`。

**落地前的外部行为（`[规定]`，原 §6.1 末段，保留不变）**：写入类能力整个视为「未支持」——不是「可能成功」，而是**在接口层就不存在**（当前 `CAPABILITIES` 只有四项只读 `[码] capabilities.js:17-22`）。不允许出现「写入方法已登记但绑定门未做」的中间态：那等于把未授权写入放给所有已加载插件（§6 开头「没有 per-plugin 授权」）。本节的 ①②③④ 是**写能力落地的前提条件**，不是并行项。

#### 6.2.2 问一：保存要不要先确认缓冲区仍干净？

**先摆清楚 `isDirty` 到底说了什么。** `isDirty` 是宿主给的**一个布尔汇总** `[码] capabilities.js:708-796`，
语义是「缓冲区与编辑器最后一次从磁盘读入/写出的内容不同」。它**不能**区分两件完全不同的事：

- 缓冲区是 **DSH 自己刚 `applyEdit` 写进去的**（正当：我改的，我请你存）；
- 缓冲区是 **人在我改完之后敲的**（不正当：§6 硬约束第 4 条「缓冲区变化来源不明时只冻结该文件，
  不覆盖、**不自动保存**」）。

| 选项 | 代价 |
|---|---|
| **(a) `isDirty === false` 才允许保存** | 自相矛盾：此时缓冲区与磁盘一致，保存是 no-op，这个能力**等于什么都没做**。更糟的是，这个门唯一能放行的场景恰好是**危险的**——缓冲区干净但磁盘被外部改过时，"保存"会把外部改动**打回去**。 |
| **(b) 无条件允许 + `allowDirty: true` 显式覆盖** | 粒度太粗：`isDirty:true` 的两种来源无法区分，`allowDirty:true` 一次授权就把「我改的」和「人改的」一起放过去了。等于把 §6 硬约束第 4 条降级成一句注释。 |
| **(c) 复用双锚点做「自我锚定」+ 显式意图**（倾向） | 多一次 `getDocumentState` 往返拿锚点；**且它只覆盖编辑器知道的改动**，不覆盖磁盘（磁盘那一半交给 §6.2.3）。 |

**倾向 (c)**，理由是一条链：

1. **`applyEdit` 的写是经版本 CAS 的**（`[码] edit-transaction.js`：版本比对在 `TextEditor.edit` 的**同步 callback** 里，
   这是唯一真挡住 B1 的那道），所以只要 `expectedVersion` 相等，就能证明「从 DSH 上次锚定到现在，
   **没有人**动过缓冲区」。
2. 因此 Tier 3 的正确前置不是「缓冲区干净」，而是「**缓冲区等于 DSH 知道的那一份**」——
   这正是 `expectedVersion` + `expectedIncarnation` 的语义，**`-32012` 可以原样复用，不新增机制**
   （`[码] capabilities.js:286-300`、`:320-358`、`:369-376`）。
3. `isDirty` **不参与服务端判定**，理由与 §6.1.1 ②「逐操作复核、不看缓存」同源：它是缓存性汇总，
   不是逐操作事实。它仍留在 `getDocumentState` 的返回里供调用方**自己**决定要不要请求。

`[规定]` 三条：

- **`vscode.save` 必须带 `expectedVersion` + `expectedIncarnation`**（与 `applyEdit` 同两个字段、同 `-32012`）。
  理由：没有化身身份证明不了"是同一个文档实例的同一个版本"，与 T35 撤销"不带化身的写"的裁决一致。
- **必须带显式意图**：`params.mode: 'save' | 'save-and-discard-buffer'`（档位/命名见 §6.2.8 `[待决]` 1）。
  缺省 `'save'`：仅当 `version` 一致才落盘；`'save-and-discard-buffer'` 是**唯一**允许在 `version` 不一致时落盘的形态，
  语义是"我明确要求把缓冲区**现在的内容**落盘，即使它含有人类刚敲的字"。**这个模式必须由 grant 显式授权**，
  不许调用方自己决定——否则它就是 `allowDirty:true` 换了个名字。
- **`saved` 谓词反转**：`applyEdit` 返回 `saved:false`；`vscode.save` 成功后返回 `saved:true`，
  且**只有 `doc.save()` 解析为 `true` 时才允许**（`[码] vscode.d.ts:160` `save(): Thenable<boolean>`）。
  解析为 `false` 一律按失败报（`-32603` + `reason:'host-save-failed'`），**禁止**返回 `{saved:true}`——这是 §5.1「成功外形的错误结果」的同一条禁令。

#### 6.2.3 问二：磁盘被外部改过怎么办？

**这里必须先承认一个硬约束，它决定了整问的上限：`TextDocument.save()` 没有 CAS 参数。**

`[码] vscode-host.js:187-218` 的注释已经把结论写死了——`version` 不能用年月日、内容哈希或 `mtime` 代替。
反过来也成立：**`version` 相等不蕴含磁盘没变**。而 Tier 2 之所以能做到"写前必有锚"，
是因为 `TextEditor.edit` 的同步 callback 里能读 `document.version`（`[码] edit-transaction.js`）；
**`save()` 没有任何等价入口**（`[先例] #16`：`vscode.d.ts:160` 的签名是 `save(): Thenable<boolean>`，零参数）。
所以：

> `[规定]` **Tier 3 的原子性上限是「尽力早失败」，不是 Tier 2 那个 `-32012`。**
> 契约禁止把 Tier 3 的保证写成与 Tier 2 等价；任何"保存是原子的"表述都是过度承诺。

在这个上限下，锚点只有三种可选项：

| 选项 | 代价 |
|---|---|
| **(a) 不判，直接 `save()`** | 静默覆盖外部改动（`git checkout`、另一个工具、外部进程）。丢掉的改动**不可从 git 恢复**（它从未提交），与我们"禁止清理他人改动"的红线正面冲突。否决。 |
| **(b) 保存前 `workspace.fs.stat` 比对 `{mtime, size}`**（倾向默认） | 一次额外往返，O(1)；`mtime` 是毫秒（`[码] vscode.d.ts:9456-9488` `FileStat.mtime`），FAT/网络盘分辨率更粗；**同尺寸内容改写看不出来**（改一个字符）。 |
| **(c) (b) + 全量 `sha256`** | O(n) 读整份；受既有的 `MAX_TEXT_BYTES = 8 MiB` 约束（`[码] capabilities.js:46`），超限的文件本来就不读内容，**给不出哈希** → 只能拒或降级；**而且仍不能消除"读完到 `save()` 之间"的窗口**。 |

**倾向：(b) 做默认门，(c) 做成可选严格档（默认关）。** 论证是一条原则，不是省钱：

> `[规定]` **Tier 3 的磁盘锚点是「善意防护」，不是「恶意防护」。**
> 善意防护（人切了分支、另一个工具改了文件）几乎必然改 `mtime`——(b) 足够。
> 恶意防护（同毫秒、同尺寸的刻意构造）**在 `save()` 无 CAS 的前提下根本做不到**，
> 加 `sha256` 只是把窗口缩小一点却给出"已经安全"的错觉。**把做不到的事写进"不保证"里，
> 比假装做到更安全。**

`[规定]` 落地形状：宿主新增 `readDiskStat(abs) → {mtime, size} | null`（**今天宿主返回面 14 项里没有 stat**
`[码] vscode-host.js:336-351`，这是新增面，须走 §2.2 三步）；`vscode.save` 调用方必填
`params.expectedDisk = {mtime, size}`；不符即 `-32013 DISK_STATE_CONFLICT`（见 §6.2.7）。

`[待决]` 见 §6.2.8 第 2 条：是否把 `sha256` 提为默认。

#### 6.2.4 问三：删除走回收站还是硬删？

**这一节的结论（`[2026-10-23]` T44 裁决起）：`vscode.deleteFile` 不做销毁。**

它把目标 **`rename`** 进 `<工作区根>/.dsh-quarantine/<UTC 时间戳>-<原名>`：**不 `unlink`、不进回收站、一个字节都不销毁**
（语义裁决 `[码] capabilities.js:1714-1728`；宿主原语 `[码] vscode-host.js:608`；`packages/dsh-kit-bridge/test/t40-host-surface.test.js`
有一条静态守门：「宿主面**没有**删除方法、`src/` 里也没有任何删除调用」）。名字、档位、grant、人工确认、整份备份**全部保留**
——变的是**动作**，不是门槛。

**为什么放弃销毁**（三条实证，写在这里防止以后有人把 `unlink` 加回来）：

1. **open-writer 窗口**：隔离前对原件 `openSync(f, 'r+')` 拿到的写句柄**不因 `rename` 失效**。验完字节、动手删之前用那个
   fd 写入同长度的新字节，被销毁的就是没人见过的那一份，而旧快照会冒充「删掉的就是它」。
2. **provider 消费窗口**：`workspace.fs.delete(uri)` 消费 URI 的那一刻，可以「先 `rename` 走隔离体、在同一隔离名上写新字节、
   再删」——随机名挡不住「名字还在、内容已换」。
3. **跨卷部署**（T46）：VS Code 文件服务的 `rename` 在跨卷时会落进 `pfs.Promises.rename` 的 EXDEV 分支**先 copy 再 rimraf 源**，
   且不把 EXDEV 交回来——「零删除」恰好会在最该成立的部署上不成立（证据 `[档] work/t45-probes/provider-evidence.md`，
   reviewer 实测 copy=1 / delete=1）。现在改走 `fsp.rename`（`MoveFileExW` / `rename(2)`）：同卷原子改名只动目录项，
   跨卷**抛 EXDEV 原样上抛**，不复制不删除 `[码] vscode-host.js:608-660`。

结论：**校验对象与销毁对象之间隔着时间，而 `hash` 只描述名称下的字节。不销毁才是结构性的解法。**

**现在的判序**（逐字对源码 `[码] capabilities.js:1738-1741`）：路径与形态 → 双锚点 → 脏缓冲区意图门 → 磁盘锚点 → 绑定门 →
**整份备份（交不出就拒）** → **人工确认（独立长超时）** → 动手前重验（路径/磁盘/字节）→ 取对象身份 → **`rename` 进隔离区
（唯一动作，也是线性化点）** → 归档后认对象、在新位置重测字节 → 返回。

**回执长什么样**（`[码] capabilities.js:1751-1760、1986-2022`）：

| 字段 | 谁测的、什么时候测 |
|---|---|
| `quarantined: true`、`from`、`to` | 移动成功：`from` 是原名，`to` 是隔离体路径。**没有 `deleted` / `trashed`**——「没有删除」要在返回体里就是字面事实，不是注释里的承诺 |
| `confirmedSha256` / `confirmedByteLength` | 人看着点确认的**那一刻**、与 `snapshot` 同源的那一份 |
| `quarantinedSha256` / `quarantinedByteLength` | **移动完成之后**在隔离体新位置上实测，**绝不复用** `confirmed*` |
| `bytesChanged: boolean`（+ `bytesChangedNote?`） | 上面两者不同 ⇔ 归档后隔离体被就地改写过（第 1、2 条窗口）。**如实标注、两份都不丢**：确认时那份在 `snapshot`，现在这份在 `to` |
| `snapshot` / `backup` | 整份可恢复字节（`utf8-text` 或 `base64`）+ 长度 + `sha256`；`backup.delivered: true` 是「交出去了」的谓词 |
| `quarantine {path, original, retained, restored}`、`nameCollision` | 隔离区实际路径、原名、是否仍保留（`retained: true`）；同名冲突是否用过随机后缀 |

**剩下的唯一判据：被移走的是不是人批准的那个对象。** 归档前取 `(dev, ino)`（`[码] capabilities.js:1883`），
归档后在隔离体上再取一次（`:1941`）：相同 ⇒ 同一个 inode ⇒ 完成，随后**重新测量**（与确认时不同就 `bytesChanged:true`，
两份都不丢）；不同 ⇒ 有人「挪走原件 + 同字节顶名」⇒ **归还隔离体**并报 `-32013`
`reason:'target-replaced-before-quarantine'`，**两份文件都在** `[码] capabilities.js:1955-1974`。
判据是身份不是字节：字节完全相同也必须拒——人批准的是那个 inode。

逐条回答本问的四个子问题：

**① 回收站还是硬删？** `[规定]` **两个都不做**（`[2026-10-23 改判]`）。原来的判定是「强制 `useTrash: true`、且不声称可恢复
（`trashed` 的唯一诚实取值是 `'unknown'`）」；现在动作连「删」都不是：目标被搬进 `.dsh-quarantine/`，
**再没有「进没进回收站」这个不确定性，也没有「重命名后按名字删」那个窗口**（见上面三条实证）。

代价写清楚，不许被文案优化掉：**工作区里会多一个只会长大、不会自己变小的目录**——清理是人的事；本能力**没有 `restore` 入口**
（`vscode-host.js` 的返回面里没有任何删除/搬回来的方法），要拿回文件请人去 `.dsh-quarantine/` 把它挪回原位。
`[待决]`（§6.2.8 第 4 条改写）：要不要提供「列隔离区 / 恢复」两个入口——**倾向下期单独一轮**，本期不加，
因为它会把「谁有权搬回来」变成一个新的授权问题（搬回来也是一次写盘）。

**② 要不要人工确认？** `[规定]` **要，且默认开**（`[码] capabilities.js:2042`）。依据：VS Code 自己 `explorer.confirmDelete`
默认 `true`（`[先例] #14`）——**DSH 替人搬文件而不问，比宿主更激进**。确认框展示**内容预览**，所以整份备份必须排在确认**之前**
（`[码] capabilities.js:1839-1847` 的注释写明这个顺序是对的：没有快照就没有预览）。两条失败态都用既有码，不新增：

- 人没点「删除」→ `-32002 declined`，`data.choice` 原样回报 `[码] capabilities.js:2083-2090`；
- 确认框超时（默认 `DEFAULT_DELETE_CONFIRM_TIMEOUT_MS = 120_000` `[码] capabilities.js:109`）→ `-32004` `reason:'confirm-timeout'`，
  **超时即作废这次许可，迟到的「同意」不生效** `[码] capabilities.js:2066-2078`。

本端线路超时**必须比对端确认超时宽**：`DELETE_REQUEST_TIMEOUT_MS = 180_000` `[码] index.js:274`，留 60s 余量，
好让对端那个更具体的 `reason:'confirm-timeout'` 先到（两个值要一起调：若 `deleteConfirmTimeoutMs ≥ 180s`，本端会先超时，
`reason` 就看不见了）。

**③ 删目录怎么办？** `[规定]` **不支持**。递归删除会被直接拒（`-32602` + `reason:'recursive-delete-unsupported'`）。
`[待决]`（§6.2.8 第 5 条）：要不要将来开"空目录删除"这一极小档。

**④ 多根工作区 / 符号链接怎么办？** 全部**拒**，而且这两条**不需要新机制**：
路径守卫的规则 0 已经「工作区根不是恰好一个 → 拒绝写入」（`[码] workspace-paths.js:105-176`），
规则 2 已经「整条链逐段 `lstat`，任何一段 symlink/junction → `-32602`」（`:121 firstLinkInChain`）。
删除**恰好是这两条规则最没有争议的用法**：它只作用于**已存在的真实文件**，
完全避开了「新建文件时父目录还不存在」那半个证明缺口（`[码] workspace-paths.js` 规则 5）。
`[待决]`（§6.2.8 第 6 条）："删符号链接本身（而非其目标）"是不是一个应当支持的独立语义——**倾向不支持**，
与 §6 硬约束第 3 条「禁 symlink/junction/reparse point」一致，模糊的语义不值得单开一档。

**删除的线性化点**（§6.1.1 ④ 要求每个写入类能力必须写明）：**`host.quarantineRename()` 这一调用**
（`[码] capabilities.js:1917` → `[码] vscode-host.js:608`；`[2026-10-23 改判]`，原判是 `workspace.fs.delete()`）。
越过之后一律按「**已经挪走了**」报告——但**仍然没有任何字节被销毁**，所以「报真实结果」比原来更容易：
真值就是 `quarantine` / `bytesChanged` 那几个字段。失败闭包写在这里：`rename` 抛错 ⇒ 一律 `-32603`
`reason:'quarantine-failed'` + `hostCode`（`crossVolume: true` 当 `hostCode:'EXDEV'`），消息里明说
**nothing was deleted and nothing was moved**，并**拒绝**用 copy+delete 伪装跨卷 `[码] capabilities.js:1918-1937`；
隔离目录建不出来 ⇒ `reason:'quarantine-dir-failed'`（`:1896-1911`）；归档后读不到隔离体 ⇒ `reason:'quarantine-not-observed'`
（`:1941-1954`，`mayHaveApplied:false`）。`applyEdit` 的对应物是 `host.applyEditText`（`[码] capabilities.js:798-1000`），两者形态一致。

**这条能力明确挡不住什么**（与本文其余部分同一条诚实口径，别读成「以后补」）：

- **搬完之后隔离体的字节仍可能被改写**：那个 `open-writer` 的 fd 指向 **inode 而不是路径**，`rename` 之后它对同一个 inode
  仍然有效。所以回执用 `bytesChanged` **如实标注**「现在这份 ≠ 人确认的那份」，但**两份都不丢**（`snapshot` + `to`）。
  这是移动语义的固有性质，不是遗漏；想彻底消除只能不提供这个能力。
- **「工作区里少了一个名字」不等于「少了一份内容」**：内容还在，只是换了名字和目录。任何把它描述成「删除」的文案都是错的。
- **不做 CAS**：`(dev, ino)` 只证明「移走的是同一个对象」，不证明「人看到的内容就是磁盘上的内容」——后者由确认前的字节重验
  （`-32013` `reason:'bytes-changed'`）尽力挡，覆盖的是「确认框开着的那段时间」。

#### 6.2.5 问四：§7 #4 的 per-plugin 白名单必须在写盘前先做吗？

**先诚实给出一条既有违约**：§7 #4 的倾向写的是「(b) **在写能力落地前必须做**」，
而 **Tier 2（`vscode.applyEdit`）已经在 `026733c` 落地，且没有白名单**（§6 开头：
「当前没有 per-plugin 授权」`[码] index.js:55-60、245-258`）。也就是说**这条倾向已被实现事实违反**。
本节不能假装没发生，只能给判断并把债记清楚。

**判断：分档，且不是"要不要"而是"哪一档开始必须"。**

| 档 | 白名单 | 判断依据 |
|---|---|---|
| Tier 1 / Tier 1+ | **可以不做** | 只读四能力的损失面是"读走选区/诊断"；§7 #4 已认定「只读四能力风险可接受」，本节维持该结论，不扩大改动面。 |
| Tier 2 缓冲区编辑 | **本来是"必须"，但已经漏了** | 真实风险是"插件 bug/幻觉把缓冲区改坏"，**可撤销**（宿主撤销栈 + `-32012` 双锚点 + `saved:false`），人一按 Ctrl+Z 就回来。所以这是**可补救的债**，不是不可接受的默认值——但它必须留在债清单上，在白名单落地时一起收口。**不许把它当作"Tier 3 也可以先不做"的先例。** |
| Tier 3 落盘 | **必须** | ① 落盘产生 **git 可见的改动**，一旦被 `git add`/提交就变成"他人的改动"，与项目红线冲突；② 落盘**消灭 `saved:false` 这个谓词**，把"缓冲区可能被改"升级成"磁盘被改"，可撤销性从 Ctrl+Z 降到 `git restore`——**而 `git restore` 在本项目里被明令禁止**；③ 归因错误：看起来是**用户**保存的。 |
| Tier 4 删除 | **必须，且必须先于或同时于 Tier 3** | 爆炸半径是**整个工作区**，且不可逆（§6.2.4）。让删除比保存更容易获得授权，是档位轴上的倒挂。 |

**不做白名单的威胁模型**（这是本问的核心，必须写死）：

- **T-A 插件误调 / 模型幻觉**：一次错误路径拼装 → 删 `src/**`。损失 = 全部未提交工作；
  恢复路径 = git（若已提交）/ 回收站（**若真的进了，而我们无法证明**）/ 无。
- **T-B 提示注入（真正的新增面）**：编辑器里的文本（被读进来的代码、README、被 `getSelection` 取走的选区、
  `readDocumentState` 的 `text`）进入模型上下文；攻击者只需**把"删除 ../../xxx"写进一个文件**，
  就可能驱动 `vscode.deleteFile`。**路径守卫挡得住"出工作区"，挡不住"工作区内一个完全正确的路径"。**
  这是本项目**第一个"只靠写文件内容就能触发不可逆操作"的通道**。
- **T-C 归因**：删除由扩展发起，宿主看到的是"用户/扩展删了文件"；人无法区分这是自己删的还是 DSH 删的。

`[规定]` 由此得出：**白名单是必要条件，不是充分条件**——它挡不住 T-B（注入走的是合法路径）。
所以 Tier 4 必须**同时**有：白名单（减少能触发不可逆操作的调用方数量）+ 人工确认（把 T-B 变成"人看见了"）+
内容快照（把不可逆变成"材料还在"）。三者缺一，T-B 就是可成功利用的。
`[待决]`（§6.2.8 第 3 条）：白名单的**粒度**——按插件名、按档位、还是「插件 × 最高档位」。
倾向**插件 × 最高档位**，依据是 Codex 的 `GranularApprovalConfig` 按**动作类别**分层而不是给总分
（`[先例] #10`）："能读"和"能删"不是同一根轴上的刻度。

#### 6.2.6 落盘之后，既有的三道门够不够？

这是任务点名要回答的问题，逐门给结论：

| 既有门 | Tier 2（缓冲区） | Tier 3（落盘） | Tier 4（删除） | 结论 |
|---|---|---|---|---|
| **`-32010` 绑定门** | 够 | **够，且零改动** | **够，且零改动** | `[码] grant.js:96-101` 的 JSDoc 已经写明「保存/新建/删除/改名（T4、T5）往 `WRITE_METHODS` 追加，门就是自动生效的——判据是一张表，不是一个开关」。**这是本项目里少见的"设计时就留好了口子"的地方**，不要在这上面重复设计。 |
| **`-32012` 双锚点** | 够（`expectedVersion` + `expectedIncarnation` + `expectedRangeText` 三道叠加） | **只够一半**：挡住"缓冲区被谁改过"，**完全挡不住"磁盘被谁改过"** | 同 Tier 3 | Tier 3/4 必须**外挂** §6.2.3 的磁盘锚点。`save()` 无 CAS（`:160`）是硬上限，**不能靠改锚点绕过去**。 |
| **路径守卫** | 够 | 够 | **恰好最够** | Tier 4 只作用于已存在的真实文件，绕开了"新建时父目录还不存在"那半个缺口（`[码] workspace-paths.js` 规则 5）。规则 0（单根即拒）/ 规则 2（任何 reparse point 即拒）对删除是纯收益。 |

**不够的那一条，性质上不是"门不够"，而是"门管不了"**：Tier 3/4 的残余风险是**不可逆**与**归因**，
两者都不是判定能解决的，只能靠 §6.2.4 的三条（返回值诚实 + 缩面 + 交材料）与 §6.2.5 的三条（白名单 + 确认 + 快照）。
**别指望再补一道门。**

#### 6.2.7 新码提议

`[规定]` 沿用既有编号空间 `[码] protocol.js:15-58`，**只新增一个码**：

**`-32011` 明确保持空号**：§8.6 第 3 条已写明它留给「收窄档位」的设想（未实现、未占码位）。
本节新增的档位轴**不占用它**——档位是 grant 上的一个字段，不是一个新的错误类别。
