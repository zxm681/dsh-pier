## 1. 目标与非目标

**一句话（只对「消费已发布能力」成立）**：把「第三方 DSH 插件使用**编辑器已发布的能力**」压缩成**一个服务名 + 一个入口对象**，让对方只写一行 `inject` 加一次取服务就能调用，且永远不需要知道端口、发现文件、token 的存在。

**这句话不能外推到「第三方新增能力」**（评审 R1）：`inject` / `ctx.get` 只解决**依赖获取**，它不会在 VS Code 侧长出一个 handler。桥端能力清单是源码里的固定数组 `[码] capabilities.js:17-22`，分派表是固定对象、未登记的方法一律 `-32005` `[码] capabilities.js:217-234`；新增能力仍必须走 `AGENTS.md` 的「加新能力的三步」`[档] AGENTS.md:68-74`。两种接入成本见 §2.1 / §2.2。

现状已经是这个形状：`ctx.provide('dshVscodeKit', facade)` `[码] index.js:300`，消费者 `export const inject = ['dshVscodeKit']` + `ctx.get('dshVscodeKit')` `[码] demo:18、demo:26`。**本文的产出不是新机制，而是把已有 facade 冻结成契约**，并写清它现在没做到的部分。

**不做**：

| 不做 | 理由 / 证据 |
|---|---|
| 不暴露传输细节（port / token / 发现文件 / link / connSeq） | 铁律 8 的分层已把它们留在 server 内部 `[码] server.js:124-137`；snapshot 里虽能看到 port/discoveryPath，但源码自己标注「不属于稳定 API」`[码] index.js:171` |
| 不新增第二个接入点（不再加服务名、不加注册表） | 用户要「最好只留一个钩子」；多一个入口就多一套版本与权限要维护。**注意**：一个入口只减少「入口数量」，不减少「桥端维护」——见 §2.2 |
| 不承诺跨大版本的二进制/语义兼容 | 见第 4 节；协议只有单整数版本号 `[码] protocol.js:46` |
| 不代理任意 VSCode 命令 | 能力表是白名单四条目 `[码] capabilities.js:17-22`，未实现方法统一 -32005 `[码] capabilities.js:229-234` |
| 不代第三方注册入站能力 | 入站只认 `bridge.ping`/`bridge.hello`，其余 -32601 `[码] index.js:370-390`。这是**今天的硬边界**，要放开属第 7 节待决 |
| 不承担编辑授权语义 | 编辑 grant **授给谁、授权含义**属协作编辑自身设计 `[档] work/协作编辑-M0复核与保守裁决.md:16-19`，钩子只管「能不能把请求送到编辑器」。**精确边界**（第 3 轮返工补）：本契约**不定义**「谁有资格授权」，但**规定**「没有有效绑定时不许执行」以及判定的位置与形态（§6.1 / §6.1.1）——授权语义归协作编辑，绑定门的执行归本钩子 |
| 不保证静默重试成功 | 异步动作必须走请求（第 5 节），通知没有失败回执 |

|---|---|---|

| 入口对象 | facade（普通对象，非 Service 子类） | `[码] index.js:260-289` |

| 消费者不知道的东西 | 端口、token、发现文件路径、link、connSeq、TCP 全都不在入口对象上 | `[码] index.js:40-61` |

### 2.1 消费已发布能力：真·最小接入（1 行依赖 + 1 次 get）

`inject` 是纯字符串数组声明、不需要 import cordis `[档] docs/phase5-打样日志.md §1.1`；`ctx.get` 拿到的 facade 在监听未就绪时也**不是 null**，避免「拿到 `{}` 再裸 TypeError」`[码] index.js:236-243`。

第三方消费示例（服务名、参数名与源码一致；**必须 `await` 且 `catch`**，理由见 §5.1「成功外形的错误结果」）：

```js
export const name = 'my-plugin'
export const inject = ['dshVscodeKit']            // 唯一需要加的一行

export function apply(ctx) {
  const kit = ctx.get('dshVscodeKit')             // 唯一 entry 点
  ctx.effect(() => {                              // 长任务自己管生命周期
    ;(async () => {
      try {
        const r = await kit.vscode.openFile({ path: 'C:/w/a.md', line: 3 })
        if (r?.opened !== true) throw new Error('bridge returned an unexpected shape')
        // 到这里才算「确认业务成功」，不是「没报错就算成功」
      } catch (err) {
        // 失败必须落地成可见结果：err.code 是稳定错误码，err.data 是诊断
        console.error('[my-plugin] openFile failed', err?.code, err?.message)
      }
    })()
  })
}
```

真实消费者就是这个形状：`readSelection()` / `openFile()` 都 `await` 并把失败转成 `{ok:false, code, message}` `[码] demo:36-56`。**契约要求**：本文与后续所有示例都要与真实消费者同形——禁止出现「调用不 await、`catch` 里空转、把返回值当成功」的写法。

### 2.2 第三方新增能力：不是 1 行，是三步（绕不过）

| 步骤 | 必须做什么 | 为什么绕不过 |
|---|---|---|
| ① 桥端登记 | `CAPABILITIES` 数组加条目 + `handlers` 表加实现 | 清单是源码固定数组 `[码] capabilities.js:17-22`；`dispatch` 只认 `handlers[method]`，未登记即 `-32005` `[码] capabilities.js:229-234`。这里**没有**任何第三方注册函数 |
| ② DSH 侧糖衣（**可选**） | 在 `kit.vscode` 加一行转发 | 通用 `request('vscode.xxx', …)` 已能直发任意方法名 `[码] index.js:263、129-162`，糖衣不是硬需求；若加，`VscodeKit.vscode` 与 facade 的 `vscode` **两处都要加** `[码] index.js:55-60、245-258` |
| ③ 双端测试 + E2E + 真机 | 两侧单测、`scripts/e2e.mjs`、真 VS Code 验一次 | `[档] AGENTS.md:68-74`；单测与 E2E 都用假宿主，证明不了编辑器那半边 `[档] AGENTS.md:60-62` |

**结论（也是本篇最容易被误读的一句）**：「一个服务名」省掉的是**第三个入口**，不是桥端实现。任何声称「第三方不改桥包就能新增 VS Code 能力」的设计，都必须另外提出扩展机制与部署/权限边界；**在当前源码下这个能力不存在**，本文不承诺它。

### 5.1 「成功外形的错误结果」（`[规定]`，评审 R4）

**问题不是「会不会失败」，而是「失败了却长得像成功」。** 代码事实：响应识别只看「有 `id`、无 `method`」`[码] protocol.js:240`，命中 pending 后——**有 `error` 就 reject，否则一律 `entry.resolve(msg.result)`** `[码] protocol.js:242-251`。因此对端只要回一条合法 JSON-RPC 空响应 `{"jsonrpc":"2.0","id":<pending>}`，调用方就拿到 `resolve(undefined)`：不抛错、不超时、不带任何诊断。

**这不只是理论**：协议层只在「我方作为被调方」时把 `undefined` 归一成 `null` `[码] protocol.js:293-303`——那是**对自己的约束**；对端返回什么，协议层不做形状校验（`handleMessage` 命中即 resolve）。

**契约要求（facade 边界必须校验，不可下推给消费者）**：

1. 每个走 facade 的调用返回后，**在返回给调用方之前**按该能力的返回契约校验形状；不合格即抛 `-32009 invalid-response`，`data = { method, got, expected }`（`got` 用 `typeof`/键名摘要，不倾泻整个响应体）。
2. **最低限度校验**（对所有能力，含未来新增）：拒绝 `undefined` / `null` / 非对象。**没有例外**——四条已发布能力返回的全是**对象外壳**（`[码] capabilities.js:106、111、126、193、214`），数组只出现在对象的**字段里**（`editors`、`files`），从不出现在顶层。旧稿「`listOpenEditors` 这类除外：必须是 `Array`」**已撤销**（第 3 轮返工，评审 new-1）：照它实现会把每一次正常响应都判成 `-32009`。
3. 已发布四能力的最小必填，**逐字对齐 handler 实际返回**，不得凭签名印象推测（`[码] capabilities.js:84-215`）：

## 6. 安全边界

**谁能调**：任何在 DSH 进程内、声明了 `inject: ['dshVscodeKit']` 的插件。**当前没有 per-plugin 授权**——拿到服务就能调任何 `vscode.*` `[码] index.js:55-60、245-258`，`method` 前缀不做调用者校验 `[推导]`。威胁模型里「同用户进程可读发现文件拿 token」这一条同样适用于任何已加载的插件 `[档] docs/威胁模型-通道可达面.md:32`。

**能做什么**：四项只读/准只读能力（打开文件、读选区、读诊断、列编辑器）`[码] capabilities.js:17-22`，且被编辑器侧工作区信任门再拦一道 `[码] capabilities.js:72-77`。

**不能做什么**：写/改/删/保存（未实现，第 3 节）；绕过工作区信任；从 `links` 里挑对端；让未准入连接收到通知；把 token 塞进出站消息除非显式要求。

### 6.1 会话/窗口绑定：写入类能力的前置硬门（`[规定]`，不再是「可暂缓选项」）

**定位变更（评审 R3）**：旧稿把「目标窗口/会话」列为第 7 节待决 #1，读起来像「可以先不做」。**这不成立**——它是**写入类能力的前置硬门**：没有绑定就不放行写。读操作（当前四项只读能力 `[码] capabilities.js:17-22`）不改宿主状态，可以维持「单活跃编辑器」；**任何写入类**（未来的写文件、`applyEdit`、保存、改选区、暂存/提交）在绑定成立之前**一律拒绝**。

**绑定的三条要求**（`[档] work/协作编辑-M0复核与保守裁决.md:16-19`，逐字对齐）：编辑 grant 必须绑定「DSH 会话 + 指定 VS Code 窗口」，断线/重连即撤销；token 只是连接准入，**不等于**编辑授权；缓冲区变化来源不明时只冻结该文件。

| 缺口 | 证据 |

| 钩子只有「当前活跃编辑器」一个概念，没有窗口/会话身份 | `[码] index.js:78-93` 只从 `server.trusted` 里挑 `connSeq` 最大的活连接 |
| 断线**不撤销任何东西**（因为还没有 grant 可撤销） | `[码] server.js:172-173` socket close 只做 `trusted.delete` / `links.delete` |
| `connSeq` 不能当窗口身份 | 它的口径是**建连先后**，不是「最后准入」；逆序握手时两者会选出不同窗口 `[码] server.js:127-137、178`、`[档] AGENTS.md:16` |
| `link.authorized` 不承担安全边界 | 仅留作诊断/兼容 `[档] AGENTS.md:16` |

**判定顺序（`[规定]`，三层不可跳 + 两个时点不可省）**：① 版本门（§4.1，能否通话）→ ② **绑定门（本节，本会话对该窗口有没有写 grant）** → ③ 能力执行。①② 任一不过，业务能力**一次都不执行**，且必须在发送前拒（不能靠编辑器回错）。

**两个时点（第 3 轮返工补，评审 R3）**：上面的 ①② 只覆盖**发送前**。只做发送前检查，不足以覆盖「发包之后、执行之前 grant 被撤销」或「连接代际已变」——那两种情况请求已经在路上或已到对端。所以绑定必须在**两个时点各判一次**：**发送前**（DSH 侧，能否把请求发出去）与**执行前**（扩展侧，逐操作复核，能否真的执行），详见 §6.1.1。只写发送前 = 半个门。

### 6.1.1 执行端闭环：代际绑定 + 逐操作复核 + 失败闭合（`[规定]`；第 3 轮返工，**① 与新增 ①-b/①-c/①-d 为第 4 轮重写，修 new-2 跨域计数**）

**为什么「发包前拒」不够（评审 R3 的核心）**：发送前的门只能证明**那一刻**绑定有效，证明不了发包之后、执行之前的状态：

- 请求在途时连接断了或换了新连接 → 旧 grant 该失效，但请求已经在网线上；
- 同一连接上后续又授权了**另一个窗口**，而这条在途请求属于旧窗口；
- 通用 `request('vscode.xxx', …)` 与糖衣走**同一条链路** `[码] index.js:263、156`，协议上看不出哪条是写；靠方法名白名单拦不住未来的写方法。

所以闭环必须落在**执行端**，且必须**逐操作**判，不能只判一次。

**① grant 关联 `session + window + authorization epoch`**

> **第 4 轮返工（回应评审 new-2，blocker）：代际值的计数域写错了，本节重写。**
>
> 上一稿把**宿主进程级**的 `connSeq`（`[码] server.js:137` 把它定义在整个服务实例上、`:178` 每条新连接 `link.connSeq = ++connSeq`）与**扩展侧每个窗口各自独立**的本地连接计数，当成同一个 `connectionGeneration`，还要求两端「逐字相等」。这是**两个不同的计数域**：DSH 先接窗口 A 再接窗口 B 时，宿主侧是 1 与 2；而 A、B 是两个独立的扩展 host 进程，各自都是本进程第一次 `attach`（`[码] connector.js:132-172`，那里**连代际字段都没有**），本地纪元都自然可以是 1 —— 于是**没有任何异常的正常场景**下就是 `2 ≠ 1`，有效 grant 被判成过期。
>
> **结论：这不是实现的错，是契约把两个域写成了一个域。** 本节改为「**单一生成方 + 线上值**」，并删掉「两端各自计数」这个前提。

| 字段 | 含义 | 取值来源 |
|---|---|---|
| `sessionId` | DSH 侧发起协作编辑的会话 | `[规定]` 宿主侧会话标识（**当前不存在**，需新增） |
| `windowId` | 指定的那一个 VS Code 窗口 | `[规定]` 窗口身份（**当前不存在**；`connSeq` 冒充不了，见上表）。**本轮不要求它参与代际判定**，理由见 ①-b 的「窗口绑定怎么成立」 |
| `grantEpoch` | **授权快照的身份值**（取代上一稿的 `connectionGeneration`，字段语义收窄、更名以免与「连接序号」混淆） | `[规定]` **唯一生成方 = DSH，生成时机 = 授权那一刻**，与 `grant.id` 同批产生。取值 `[实现]`：opaque 不可猜测值（如 128-bit 随机 hex），**每次授权一个新值**、跨窗口唯一、**不可排序、不可由对端推断**。它是**线上值**：DSH 随 grant 报文下发 → 扩展保存 → 写请求原样回带。**两端都不许自己重算，也不许由 `connSeq` 换算** |
| `boundConnSeq` | `[规定]` **纯诊断的惰性字段**：DSH 记下授权时承载连接的 `link.connSeq` | 只进日志与错误 `data` 的人读信息。**不得**参与等值/排序判定，**不得**下发给扩展当判据 |

> **`[2026-10-22 落地]`** 前两行里「**当前不存在**」已过期，字段本身进了实现：`sessionId` / `windowId` 都在 `GrantStore.issue()` 时写进 grant 记录（`[码] packages/dsh-vscode-kit/src/grant.js`），墓碑里也保留（直到被 `GRANT_TOMBSTONE_LIMIT` 挤掉）。分工与本节定性一致——`sessionId` **参与一致性校验**（`judgeSession()`：身份只从两处取，扩展侧是承载连接上由 `bridge.hello` 登记的会话、DSH 侧是显式传入的调用方上下文；业务 `params.sessionId` 一律拒，否则等于自证），`windowId` 仍**只作人读标签、许可为 `null`**，不参与代际判定。`grantEpoch` / `boundConnSeq` 两行的规定原样落进代码，一字未改。

`grantEpoch` **是等值判据，不是排序判据**：比较的两端是「grant 报文里的值」与「请求回带的那个值」——**同一个由 DSH 生成、经线上传输的值**；**不是**「宿主计数器 vs 扩展本地计数器」。三条一起禁止，一条都不许放宽：

- **禁止**把 `connSeq` 当身份：它的口径是**建连先后**（`[码] server.js:127-137、178`），与「授权给了谁」无关；
- **禁止**「取当前最大序号」或「哪条活着用哪条」来挑写目标：那正是 `connSeq` 被误用的根源——**拿排序当身份**；
- **禁止**要求两端**各自计算**一个代际值再比是否相等：上一稿的错，任何一侧换了计数起点就误判（本轮唯一的 blocker 就是这个）。

**①-b 代际值怎么产生、怎么传、怎么存、怎么失效（`[规定]`，本轮写死，不留猜测）**

**（1）传输位置——判据只出现一次，两端用的是同一份**：

| 环节 | 报文 / 字段 | 方向 | 谁生成 | 谁判定 |
|---|---|---|---|---|
| 建立 grant | `bridge.grant` 能力请求，`params.grant = { id, epoch, sessionId, windowId? }`（方法名 `[实现]` 可定，**字段名与语义本轮写死**） | DSH → 扩展 | DSH | 扩展做结构校验后存档 |
| 写请求 | 现有 `link.request` 的 `params.grant = { id, epoch }`（**顶层字段**；糖衣与 `request('vscode.xxx')` 同形，不因入口不同而异） | DSH → 扩展 | DSH 从自己存的那份**原样复制**，不重算 | 扩展逐操作比对 |

- **不新开通道、不新开入口**：grant 报文与写请求都走**同一条已准入连接**、同一个 `bridge.*` 命名空间（`[码] index.js:156、263`）；扩展侧仍只有唯一漏斗 `handleInbound` → `dispatch`（`[码] connector.js:85-99`）。§7 #2 的 (a) 不变：第三方看不到 `grant` / `epoch` 这些字段。
- **DSH 侧「存的那份」**：`grants[sessionId] = { id, epoch, link, windowId?, boundConnSeq }`，其中 `link` 是**对象引用**，不是序号。发写请求时，目标是 `grants[sessionId].link`（**按身份**），**不是** `_activeLink()` 的 argmax 结果——`_activeLink()` 只服务读路径的「单活跃编辑器」（`[码] index.js:78-93`，口径见 `[档] AGENTS.md:16`）。

**（2）执行端保存与失效时机**：

| 事件 | 动作 |
|---|---|
| 收到 `bridge.grant` 且结构校验通过 | 以 `grant.id` 为键存入**进程内**表：`{ id, epoch, link, cause: null }`；`link` = **收到这条报文的那条连接实例**（对象引用，不取序号）。**每窗口同时最多 1 个有效 grant**：新 grant 到达即覆盖，旧 grant 置 `cause:'superseded'` |
| 承载连接 `close`（断线 / 重连 / 进程退出） | 该连接投递过的所有 grant 立刻置 `cause:'disconnected'`。**这一步必须在执行端本地完成**：撤销的正确性不依赖 DSH 事后补发撤销报文（跨进程通知可能根本发不到，那就成了「靠运气闭合」） |
| 会话侧主动撤销 | 收到撤销报文（`bridge.revoke`，`[实现]` 可选）→ `cause:'revoked'`。**没有这条报文也不影响正确性**：关连接即撤 |
| 扩展 host 重启 | 全部 grant 消失，等价于「从未授权」。grant **不落盘**（落盘等于把一次授权复制到别的进程和别的时段） |
| 墓碑 | 失效的 grant 不立刻丢，保留 `{ id, epoch, cause }` 供诊断，按最近 N 条（`[实现]` 建议 32）淘汰。墓碑**不参与放行判定**，只决定 `data.reason` |

**（3）窗口绑定怎么成立（不依赖任何数值身份）**：grant 是**投递即绑定**——它只被发到选定的那条连接，只存在**那一个窗口的扩展进程内存**里。别的窗口的扩展进程**从来没有**这条 grant，所以「改投另一个窗口」必然落到 `no-grant`，不需要先知道 `windowId` 是多少。`windowId` 是人读标签与会话侧一致性提示，**不是安全判据**。这样本轮不必先把 §7 #1 的窗口身份来源做完，代际判定也不会被它拖成依赖。

**①-c `-32010` 的五个 `reason` 怎么分（`[规定]`，与既有码表逐条对齐）**

执行端判定的**唯一顺序**，先命中先返回，**不做多因合并**：

| 序 | 条件 | 码 + `reason` | 备注 |
|---|---|---|---|
| 1 | 写入类请求未带 `params.grant` | `-32010` `no-grant` | 「从未申请绑定」，与 §6.1 表首行同义 |
| 2 | `params.grant.id` 在本地表**查不到**（含墓碑已淘汰、host 重启后） | `-32010` `no-grant` | 保守归「没有可用绑定」，处置相同 |
| 3 | 命中墓碑且 `cause = 'disconnected'`（**承载连接已换/已断**） | `-32010` `grant-generation-stale` | 典型场景：重连后旧请求晚到 |
| 4 | 命中墓碑且 `cause ∈ {'superseded','revoked'}` | `-32010` `grant-revoked` | 「已有新授权覆盖」或「人撤销了」，与 §6.1 表第四行同一个语义 |
| 5 | 命中有效 grant，但 `params.grant.epoch !== stored.epoch` | `-32010` `grant-generation-stale` | 冗余校验（`id` 已唯一）；fail-closed 成本近零，留着挡「看错/拼错/伪造同 id」 |
| 6 | 命中有效 grant，但 `stored.link !== 当前持有该请求的连接实例` | `-32010` `grant-generation-stale` | **进程内对象身份比较，不比对任何数字**——这一条取代上一稿的跨域等值 |
| 7 | 以上全部相等 | 放行，继续进 handler 直到线性化点 | `sessionId` 的一致性由 **DSH 发送前**判；扩展侧没有第二份会话概念，不重复判（避免两处口径漂移） |

**为什么 `id`、`epoch`、连接身份三个都要**：`id` 回答「这是哪一次授权」，连接身份回答「同一个窗口里，请求是不是走在那条被授权的连接上」，`epoch` 回答「授权快照没被替换、没被看错」。三者正交，各自独立 fail-closed，任一条缺失都不会被别的条补上。

**② 执行端在写入线性化点之前逐操作复核，`generic request` 不得免检**

- **写入线性化点（`[规定]` 定义）**：该能力 handler 里**第一次改动宿主状态**的那次调用（例：`host.openTextDocument` `[码] capabilities.js:109`；未来的写文件 / `applyEdit` / `save` 各自在自己的登记项里写明）。线性化点**之前**拒绝 = 零副作用；**之后**拒绝 = 已落点，见 ④。
- **复核位置**：执行端唯一漏斗 `handleInbound` 交给 `dispatch` **之前** `[码] connector.js:85-99`，以及 `capabilities.dispatch` 分派进 handler **之前** `[码] capabilities.js:229-235`。两处同在一个进程内，调用方绕不过去。
- **复核内容**（逐操作、不看缓存）：按 ①-c 的七行顺序判——请求携带的 `params.grant.id` 与 `params.grant.epoch` 必须与执行端**当前**持有的那份 grant 相等，且**当前持有该请求的连接实例就是 grant 的承载连接**（对象身份比较）。任一不等即拒。**不存在「扩展侧自己算一个当前连接纪元再比」这一步**——那是上一稿的跨域比较，已撤销；扩展侧从头到尾没有自己的代际计数器。
- **`generic request` 不得免检**：不按「是不是糖衣」决定要不要查，而按「该能力是否登记为写入类」决定（清单来自 §2.2 第①步的登记项）。糖衣与 `request('vscode.xxx')` 在协议上不可区分 `[码] index.js:156、263`，所以「只查糖衣」等于不查。
- **今天不会以「漏检」形态出现**：写入类能力在接口层还不存在（本节末段），所以这条约束目前无执行对象，但它必须先写死，否则写能力一落地就是无门状态。

> **`[2026-10-22 落地]`** 「目前无执行对象」已过期：写入类清单现在非空（`[码] packages/dsh-vscode-kit/src/grant.js` 的 `WRITE_METHODS = ['vscode.applyEdit']`），这条约束对每一个登记项都真的在跑；扩展侧的两处漏斗（能力层 `capabilities.js` 与连接层 `connector.js` 的 `dispatch` 之前）用的是**同一个函数** `extensionWriteGate()`，不存在第二份判定。

**③ 失效即失败闭合，禁止改投活跃编辑器**

§6.1 那张表覆盖**发送前**的三种；下表补**在途**与**执行端**两种，两者共用同一个码，区别只在 `data.reason`：

| 触发 | 判定层 | 码 + `reason` | 处置 |
|---|---|---|---|
| **发包后目标连接消失 / 已换成别的连接** | DSH 侧在途 | `-32010` `target-gone` | **不得重发到另一条连接**；直接失败闭合，让调用方重新申请 grant |
| **执行端发现请求与 grant 不同源**（承载连接已换、grant 已被覆盖或撤销、`epoch` 不符） | 扩展侧 | `-32010` `grant-generation-stale`（连接已换）／`grant-revoked`（被覆盖或主动撤销），分派见 ①-c | 拒绝执行并回错；**不得**退回到「当前活跃编辑器」执行 |

**为什么五种情形都归 `-32010`、不新增码（评审要求说明区别）**：`no-grant` / `grant-mismatch` / `grant-revoked` / `target-gone` / `grant-generation-stale` 这五种对调用方的**处置完全一样**——停下、去目标窗口重新申请 grant、不得重试原调用。再加一个码只会把同一条处置路径劈成两条，却不增加任何可执行信息。区别由 `data.reason` 承担（诊断字段，不是判定依据），码本身只表达「没有可用的写绑定」。**若将来出现处置确实不同的情形**（例如需要人重新确认 vs 可以自动重试），那才值得独立码——今天没有这种情形，所以不预留空码，避免又一个「定义了但零处抛出」的码（对照 `-32002` 的现状 `[码] protocol.js:21、37`）。

**④ 越过不可取消写点的操作：报真实结果，不承诺撤销**

- 请求一旦越过写入线性化点，**撤销 grant 不会让落点消失**。契约**禁止**把「撤销后零落点」当承诺（与 §5 表末行同义）。
- 正确表述：这类操作按既有裁决报告**真实结果**——成功即「已落点」；超时 / 断线即「**结果未知**」，必须按「可能已落点」处理并让人核对；`-32002 declined` 才是「人拒绝且未落点」。
- `[规定]`：将来每个写入类能力都必须在 §2.2 第①步的登记项里写明**它的线性化点在哪**、以及**越过之后失败如何报告**。没写这两项的写入类能力不得进 `CAPABILITIES`。

**落地前的外部行为（`[规定]`，原 §6.1 末段，保留不变）**：写入类能力整个视为「未支持」——不是「可能成功」，而是**在接口层就不存在**（当前 `CAPABILITIES` 只有四项只读 `[码] capabilities.js:17-22`）。不允许出现「写入方法已登记但绑定门未做」的中间态：那等于把未授权写入放给所有已加载插件（§6 开头「没有 per-plugin 授权」）。本节的 ①②③④ 是**写能力落地的前提条件**，不是并行项。

> **`[2026-10-22 落地]`** 上段说的「落地前」现在是**落地后**：`vscode.applyEdit` 已进 `CAPABILITIES`（现为五项 = 四项只读 + 一项写入），并且是**先有门、后有方法**——同一提交 `026733c` 里 `-32010` 判定与 `applyEdit` 一起落。①②③④ 四条前提全部照原样进代码，没有为了让实现通过而放宽任何一条：① 七行序由 `judgeGrant()` 唯一实现、两端共用；② 写入清单按登记项判、不按糖衣判；③ `target-gone` 失败闭合、**不回退**活跃编辑器；④ 越过线性化点只报真实结果——`applyEdit` 的线性化点是宿主应用编辑那一调用，越过之后一律按「可能已落点」报告，不承诺撤销即回滚。**唯一没变的仍是「未支持」这一档本身**：`vscode.save` / `createFile` / `deleteFile` 依旧是「预留但未实现」。另需诚实指出一个**尚未补上的缺口**：④ 要求的「每个写入类能力都在 §2.2 登记项里写明线性化点」，`applyEdit` 的线性化点目前只写在代码与本节，§2.2 / §3 的表格里**还没有对应行**——见 §8.5「仍缺什么」。
