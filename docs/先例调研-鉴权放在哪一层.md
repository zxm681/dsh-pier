# 先例调研：鉴权到底该放在哪一层

> 起因：主人 m03110 提出「以后用到某些设计时，先找现成的、优秀的（GitHub 高 star）项目看看它们怎么处理」。
> 第一个被点名的设计是**「正式链接的时候才鉴权」**，也就是我们踩过的洞 2。
>
> 调研方式：`curl` 直接拉这四个项目的**源码原文**（不是博客二手转述）。
> 调研时间：2026-10-21。所有 star 数是调研当天的快照。

---

## 0. 一句话结论

**我们洞 2 的修法方向是对的，但洞 3 的修法方向错了。**

四个项目里有三个把「凭证校验」放在**建立连接之前/之时的传输层**，
而不是「每条消息里带一份凭证」——这正是我们最初的洞 3 方案（让响应带 token）的反面。

| 项目 | Stars | 鉴权放在哪 | 与我们的关系 |
|---|---|---|---|
| [socket.io](https://github.com/socketio/socket.io) | 63,220 | **连接握手时**（middleware 跑完才 `_doConnect`） | **洞 2 的正确做法，我们已独立走对了** |
| [microsoft/vscode](https://github.com/microsoft/vscode) | 194,173 | **HTTP 请求进入时**（`requestHasValidConnectionToken` → 403） | **洞 3 的正确做法：在建立连接时验，不要逐条消息验** |
| [nodejs/node](https://github.com/nodejs/node) | 122,489 | **完全不做 token 鉴权**，只校验 Host 头是 IP 字面量 | 说明 token 不是唯一答案，威胁模型决定 |
| [jupyter-server](https://github.com/jupyter-server/jupyter_server) | 572 | **每个 HTTP 请求**（`get_user(handler)`），token 走 query/cookie | 另一种形态；但它是「每个请求都重新过鉴权」 |

## 1. socket.io：连接准入与「在册」是两个集合 `[源码]`

**这是洞 2 的教科书答案。**

`packages/socket.io/lib/namespace.ts`（main 分支，`_add()` 方法）：

```ts
async _add(client, auth, fn) {
  const socket = await this._createSocket(client, auth);

  // ★ 先放进「预备」集合，此时它还不是正式成员
  this._preConnectSockets.set(socket.id, socket);

  this.run(socket, (err) => {           // ← 跑中间件（鉴权就在这里）
    process.nextTick(() => {
      if ("open" !== client.conn.readyState) { socket._cleanup(); return; }
      if (err) {
        // 中间件拒绝 → 发 CONNECT_ERROR，socket._cleanup()
        socket._cleanup();
        return socket._error({ message: err.message, data: err.data });
      }
      this._doConnect(socket, fn);      // ← 只有通过才进入正式集合
    });
  });
}

private _doConnect(socket, fn) {
  this._preConnectSockets.delete(socket.id);
  this.sockets.set(socket.id, socket);   // ★ 正式成员
  socket._onconnect();
  ...
  this.emitReserved("connection", socket);
}
```

**两个 Set**：`_preConnectSockets`（连上了但没验过）和 `sockets`（验过了）。
`_remove()` 一行同时清两个：

```ts
this.sockets.delete(socket.id) || this._preConnectSockets.delete(socket.id);
```

**为什么这对我们重要**：我们的洞 2 修法（`link.authorized` 标志位 + `filter(l => l.authorized)`）
在**语义上**和它等价，但 socket.io 用的是**两个集合**，而我们用的是**一个集合 + 一个布尔字段**。

| | socket.io | 我们 |
|---|---|---|
| 未准入的连接放哪 | 独立 Set | 同一个 `links`，`authorized=false` |
| 怎么挑对端 | 只遍历 `sockets` | `filter(authorized === true)` |
| 忘写过滤会怎样 | 不可能忘，`sockets` 里本来就只有准入的 | **可能忘**，`links` 里混着两种 |

**这是我们应该改的地方**：把「忘写过滤」从「可能的疏忽」变成「写不出来」的错误。
（列入待办，不是在这次重构里做——见文末 §5。）

## 2. microsoft/vscode：token 在**请求进入时**校验，不在消息里 `[源码]`

**这是洞 3 的教科书答案，而且直接否掉了我们的原方案。**

`src/vs/server/node/serverConnectionToken.ts`：

```ts
export function requestHasValidConnectionToken(
  connectionToken: ServerConnectionToken,
  req: Pick<http.IncomingMessage, 'headers'>,
  searchParams: URLSearchParams
) {
  // First check if there is a valid query parameter
  const queryTokens = searchParams.getAll(connectionTokenQueryName);
  if (connectionToken.validate(queryTokens.length > 1 ? queryTokens : queryTokens[0])) {
    return true;
  }
  // Otherwise, check if there is a valid cookie
  const cookies = cookie.parse(req.headers.cookie || '');
  return connectionToken.validate(cookies[connectionTokenCookieName]);
}
```

`src/vs/server/node/remoteExtensionHostAgentServer.ts:157`，**每个 HTTP 请求（含 WebSocket upgrade）进入时**：

```ts
if (!httpRequestHasValidConnectionToken(this._connectionToken, req, parsedUrl.searchParams)) {
  res.writeHead(403);           // ★ 连连接都不给建立
  return serveError(req, res, 403, `Forbidden.`);
}
```

**关键设计**：token 只在**建连那一刻**验一次（query 参数或 cookie），
连接建立之后**每一条 WebSocket 帧里都没有 token**。之后靠的是「这条 socket 已经是被信任的」。

VS Code 自己的 `connectionToken` 生成方式（同文件）：

```ts
export class ServerConnectionToken {
  static parse(value: string): ServerConnectionToken { ... }
}
// 类型分 Two 种：'query'（放在 URL 里）和 'cookie'
// 服务端启动时 randomBytes 生成，写进 URL 打印给用户
```

### 这一条推翻了我们什么

我们原来的洞 3 方案（`work/security-fix-plan.md` 里写的）是：

> `respond`/`respondError` 附 token + `isResponse` 分支先过 `authorize`

**这是错的思路**。它带来三个副作用：

1. **每条消息都要验**：1000 次响应 = 1000 次字符串比较，还要在协议层到处传 token。
2. **和洞 1 的修法直接冲突**：洞 1 刚把「出站默认不带 token」定成铁律，
   洞 3 又要让响应带 token —— 两条规则互相打架，下一个人必然写错一边。
3. **它没有解决真正的威胁**：洞 3 的攻击是「攻击者的裸连接冒充对端回响应」，
   而**根因在洞 2**（裸连接被当成了对端）。洞 2 修好后，
   请求根本不会发给未准入的连接，也就不会收到它的响应。

**正确修法**：把凭证校验前移到**连接准入**（洞 2 已经做了），
然后**保证请求只发给准入连接**——这一条已经成立。
剩下的只差一件事：**收到响应时，确认来源连接是那条请求实际发往的连接**。

这是个**本地的、零成本的**检查：`pending` 里记下「这条请求发给了哪个 link」，
收到响应时比对 `msg.__from === entry.link`。不需要 token，不需要每条消息鉴权。

## 3. nodejs/node inspector：根本不验 token `[源码]`

`src/inspector_socket.cc` 里有一个 `IsIPAddress()`，注释直白：

```cpp
static bool IsIPAddress(const std::string& host) {
  // To avoid DNS rebinding attacks, we are aware of the following requirements:
  // * the host name must be an IP address (CVE-2018-7160, CVE-2022-32212),
  ...
  if (uv_inet_pton(AF_INET, host.c_str(), ipv4) != 0) return false;
```

**Node 的 inspector 端口没有 token**。它的安全模型是：

1. 只监听 `127.0.0.1`（默认）
2. 校验 HTTP `Host` 头**必须是 IP 字面量**（防 DNS rebinding）
3. 剩下的靠「本机 = 可信」

**这对我们的意义**：说明「token 鉴权」不是本机端口的唯一正确做法，
它取决于威胁模型。Node 认为「本机攻击不在威胁模型内」；VS Code
（要跨网络/远程）就必须有 token；我们处在中间——**我们在威胁模型里明确写了
「本机其他进程可能恶意」**，所以我们需要 token。

**这条不改变我们的设计，但给了我们一句可以说清楚的话**：
不是「本机端口必须鉴权」，是「**你把什么写进威胁模型，就必须为什么付出代价**」。

## 4. jupyter-server：每个请求都重新过鉴权 `[源码]`

`jupyter_server/auth/identity.py:240` 起：

```python
def get_user(self, handler) -> User | None | Awaitable[User | None]:
    """Get the authenticated user for a request
    Return None if the request is not authenticated.
    """
    if <already authenticated>:            # 具体判断见源码
        ...
    _token_user = self.get_user_token(handler)   # token 走 query / cookie
    ...
    # prefer token to cookie if both given
```

**形态**：`get_user(handler)` 是**每个请求**都调用的钩子，token 从 query 或 cookie 取
（`JUPYTER_TOKEN_FILE` 环境变量可指向一个文件）。

**为什么我们不这么做**：它是 HTTP 服务器，请求之间无状态，只能每个请求都验；
我们是**长连接 + 有状态**，连接建立时验一次即可。这是「HTTP vs 长连接」的差别，
不是「谁更安全」的差别。

**但有一条值得抄**：Jupyter 支持 `JUPYTER_TOKEN_FILE`——**token 可以从文件读**
（就是我们发现文件的形态）。这给了我们一个旁证：把 token 写在文件里
让对端读取，是成熟项目也采用的模式，不是我们发明的临时方案。

## 5. 结论：三条要抄的，一条要改的

### 要抄（已经抄对了，记下来别再犯）

1. **连接准入和连接在册必须分开**（socket.io）——我们已用 `authorized` 标志位实现。
2. **凭证在建连时验一次，不在每条消息里带**（VS Code）——我们的 token 现在就是这样
   （建连后第一条消息带 token，验过就不再验）。**这条要写进铁律**。
3. **token 可以放文件让对端读**（Jupyter）——我们的发现文件设计是成熟模式。

### 要改（我们的洞 3 方案是错的）

4. ~~`respond` 附 token + 响应过 authorize~~ → **改成「响应必须来自请求实际发往的那条连接」**。

   实现：`protocol.js` 的 `pending` entry 记下 `link`（或者说「发给谁」），
   `handleMessage` 收到 isResponse 时比对来源。这个检查是**本地的、零成本的**，
   不碰 token，不与洞 1 的铁律冲突。

### 另记账（不在本轮做）

5. **把 `links` 拆成两个集合**（`pendingLinks` / `authorizedLinks`），
   让「忘写过滤」变成写不出来的错误。当前用标志位已经安全，但**容易复犯**。
   归进「比洞 3 更值得做」的清单。

## 6. 这次调研改变了什么（元层面）

主人 m03110 的判断是对的，而且**立刻证明了自己**：

- 我们花了两轮把洞 2 修对 —— socket.io 用了同样的思路，我们独立走对了。
- 我们准备按「响应带 token」修洞 3 —— **VS Code 的源码直接说这方向不对**。
  省下的不只是一次返工，是一个**会推翻自己刚立的铁律**的设计错误。

**但这不等于「每次都要先查」**。判断标准：

| 该查 | 不该查 |
|---|---|
| 涉及**安全边界、鉴权、凭证、并发、协议状态机** | 普通的 CRUD、UI 渲染、目录结构 |
| 你已经踩了两轮还没定论 | 你 10 分钟能验证的小事 |
| 有明确的「成熟项目一定有这个」的直觉 | 太新、没人做过（那就自己设计，但写清威胁模型） |

**查的方式**：`curl` 拉源码原文，别读博客。源码会告诉你「它们到底怎么做的」，
博客会告诉你「作者以为它们怎么做的」——这是两回事。

**证据强度**：本文件所有引用都是 `[源码]`（直接 `curl` 自 main 分支，2026-10-21）。
版本随时会变，引用时请连同 commit 时间一起看。
