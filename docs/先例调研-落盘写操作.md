## 0. 一句话结论

**四个领域、九个仓库，没有一个把「保存」做成可拦截的门；而「删除」的成熟做法是
「缩小到单文件 + 删前把内容留下来 + 失败就拒」，不是「删了再想办法恢复」。**

直接对应到我们的四问：

| 我们的问题 | 先例给的答案 | 强度 |
|---|---|---|
| 保存前钩子能拦什么 | **什么也拦不住**。LSP `willSave` 是**通知**；`willSaveWaitUntil` 只能"提交要在保存前应用的编辑"，且规范明说客户端**可以丢弃结果**；VS Code 的实现给参与者 **1500 ms 硬超时**、报错超过 3 次的参与者**被永久忽略** | 强（规范原文 + 实现原文） |
| 保存能不能做到「比较后再写」（CAS） | **不能**。`TextDocument.save()` 无参数（`vscode.d.ts:160`），这是与 `TextEditor.edit` 有版本 CAS 的**本质差别**；所有先例的保存都不带期望状态 | 强（签名就是证据） |
| 删除要不要回收站 | **要，但谁都不敢承诺"进了回收站"**。VS Code 的 `useTrash` 原文是 "whenever possible"；`IFileOperation` 在 subst 虚拟盘上**静默失败**；上游只能自己做能力探测或干脆拒 | 强 |
| 删除要不要人工确认 | **要**。VS Code 自己 `explorer.confirmDelete` 默认 `true`；Codex 把确认做成 `AskForApproval` 策略层；`git rm` 遇到未保存改动直接**拒删** | 强 |

## 1. LSP：保存前钩子拦不住保存，这是规范层面的事实 `[源码]`

**规范原文** `microsoft/language-server-protocol` · `_specifications/lsp/3.17/textDocument/willSave.md`：

```text
The document will save notification is sent from the client to the server before
the document is actually saved.
```

三个报文的方向与能力完全不同，这一点必须先分清：

| 报文 | 方向 | 有返回值吗 | 能阻止保存吗 |
|---|---|---|---|
| `textDocument/willSave` | client → server，**Notification** | 没有 | **不能** |
| `textDocument/willSaveWaitUntil` | client → server，**Request** | `TextEdit[] \| null` | **不能**，只能"保存前追加一批文本编辑" |
| `textDocument/didSave` | client → server，**Notification**（事后） | 没有 | 不能，木已成舟 |

规范对 `willSaveWaitUntil` 还有一句关键的免责（同文件）：

```text
Please note that clients might drop results if computing the text edits took too
long or if a server constantly fails on this request. This is done to keep the
save fast and reliable.
```

**它怎么做的**：把「保存前」定义成一个**只能提交编辑、不能否决**的窗口，并且明确允许客户端
**在慢或出错时直接丢掉服务器的结果**。
**为什么**：保存是编辑器的核心交互，一个第三方参与者的阻塞会让「按 Ctrl+S 没反应」成为常态；
宁可让参与者的建议落空，也不能让人等。
**对我们**：**别指望靠保存前的一次检查获得任何保证。** 如果 DSH 要在保存前判什么，
那个判定必须发生在**我们自己的调用链里**（调用 `save()` 之前），而不是指望编辑器替我们兜底。
顺带一个正面先例：`willSaveWaitUntil` 返回的是**编辑**而不是**内容**——增量、可撤销、可审计，
和本项目 `applyEdit` 的取向一致。

### 1.1 `workspace/applyEdit` 与保存的边界：先例也把两者分开 `[源码]`

`_specifications/lsp/3.17/workspace/applyEdit.md`，响应是：

```ts
export interface ApplyWorkspaceEditResult {
	applied: boolean;
	failureReason?: string;
	failedChange?: uinteger;
}
```

`ApplyWorkspaceEditParams.label` 的注释是「presented in the user interface for example **on an undo stack**」。

**它怎么做的**：`applyEdit` 只负责**改**，改完回 `applied` + 失败原因 + 第几个 change 失败；
**它不保存**。保存是客户端（人）的另一条路径。
**对我们**：这正是我们 `saved: false` 谓词的同构做法，`[码] capabilities.js:1000-1010`
返回的 `{applied, file, saved:false, textLength}` 与它对齐。**这条先例支持我们的现有设计，
但也意味着：一旦做 Tier 3，我们的返回面要出现 `saved:true` 这个新值，且必须与 `applied` 分开报。**

### 1.2 LSP 根本没有「删前钩子」`[源码]`

`_specifications/lsp/3.17/workspace/` 下只有 `didCreateFiles.md` / `didDeleteFiles.md` /
`didRenameFiles.md`——全是 **`did`**，没有 `will`。`didDeleteFiles` 原文：「sent from the client
to the server **when files were deleted** from within the client」。

**它怎么做的**：删除是客户端的独占动作，服务器**只能事后知道**。
**为什么**：删除一旦开始就跨多个文件、可能不可逆，把一个可能很慢的第三方参与者塞进删除路径，
风险收益比不对——所以规范选择连钩子都不给。
**对我们**：**没人替我们挡删除。** 这正是 §6.2 要把人工确认、内容快照、拒删目录全部压在
**我们自己这一侧**的原因：不是我们保守，是这个动作在上游就不存在任何护栏。

## 2. MCP filesystem server：目录白名单是**字符串前缀 + 逐段 realpath**，没有「先读再写」的版本约束

仓库 `modelcontextprotocol/servers` @ `51b6382`。

### 2.1 白名单怎么落地 `[源码]`

`src/filesystem/path-validation.ts` 的 `isPathWithinAllowedDirectories(absolutePath, allowedDirectories)`：
- 先拒空、拒含 `\x00` 的路径，再 `path.resolve(path.normalize(...))`；
- 然后**逐段**比对前缀，且必须落在**路径分隔符边界**上：

```ts
const dirWithSep = normalizedDir.endsWith(path.sep) ? normalizedDir : normalizedDir + path.sep;
return normalizedPath.startsWith(dirWithSep);
```

- Windows 盘符根与 UNC 共享根单独处理（注释点名 `\\server\share-evil` 不能匹配 `\\server\share`）。

`src/filesystem/lib.ts` 的 `validatePath(requestedPath, allowedDirectories)` 在此之上补两条：
1. **已存在的路径**必须 `fs.realpath()` 后**仍在白名单内**——这就是拦 symlink 的方式
   （报错文案：`Access denied - symlink target outside allowed directories`）。
2. **不存在的路径**（新建文件）走 `resolveUnicodeEquivalentPath()`：**从可信根开始逐段
   `readdir` + `realpath`**，遇到第一个不存在的段就停下，把余下部分拼上去。

`src/filesystem/index.ts` 的 `resolveAllowedDirectories()` 在**启动时**就把白名单目录 realpath 一遍，
并把「原样」和「解析后」**两份都存下来**（注释解释：macOS `/tmp` → `/private/tmp`）。

**它怎么做的**：白名单是**启动参数**，不是请求参数；命中判定 = 前缀（段边界）+ 逐段 realpath。
**为什么**：MCP server 是独立进程，只能靠路径判断；它无法知道宿主信任谁。
**对我们的可借鉴点**：
- ✅ **「原样根 + realpath 根两份都留」**——我们 `[码] workspace-paths.js:145-176 realpathOf`
  的做法一致，先例确认这是对的。
- ✅ **「不存在的尾段拼回去，只 realpath 已存在的前缀」**——我们更严：`[码] workspace-paths.js`
  规则 5「文件必须存在（不新建）」，把整个问题绕掉了。
- ⚠️ **它没有我们那条「工作区根必须是单根、否则拒写」的规则**（`[码] workspace-paths.js` 规则 0），
  所以它能支持多根。我们禁多根是**更保守**的选择，不是漏了什么。
- ❌ **它不检查链上的 reparse point 类型**，只靠 `realpath` 结果比对——软链接可以存在，
  只要解析后还在根内就放行。我们 `[码] workspace-paths.js:121 firstLinkInChain` 是**发现即拒**，
  更严。这条先例**不能照抄**。

### 2.2 有没有「先读再写」的版本约束？**没有** `[源码]`

`src/filesystem/server.ts` 里 `write_file`（`:432`）与 `edit_file`（`:460`）都只收
`path` + `content` / `edits` + `dryRun`；`edit_file` 的处理是 `applyFileEdits(validPath, args.edits, args.dryRun)`。
`lib.ts` 里对写安全的注释集中在**符号链接竞态**而不是**内容版本**：

```ts
// - lstat refuses anything at the path that is not a regular file, a symlink
// - O_NOFOLLOW makes the open itself fail with ELOOP on a symlink.
```

**它怎么做的**：写文件用 `wx`（独占创建）/ `O_NOFOLLOW` 这类**文件系统层**手段防"写穿一个被换掉的符号链接"，
但**完全不管**"我读到的内容和我写回去的内容之间，别人改了没有"。
**为什么**：它的模型是「给我一个路径和一个内容，我写」——没有"文档版本"这个概念，
也没有持有读者会话（它是无状态工具服务）。
**对我们的可借鉴点**：
- ✅ **`O_NOFOLLOW` / 独占创建**是"窗口内被换掉"的正确工具——但 Node 的 `fs` 端口没有等价物
  （这正是 `[码] workspace-paths.js` 头注释承认「本期按威胁模型排除」的那条）。
- ❌ **「不带版本约束就写」这件事我们已经做对了相反的选择**：`[码] capabilities.js:320-358 readExpectedIncarnation`
  与 `:369-376 assertIncarnationMatches`（`-32012`）。MCP filesystem 的先例**不支持**放松这一点。
- ⚠️ **注意：它连 `mtime` 都不比。** 所以「保存前比对磁盘 mtime/size」在成熟项目里**不是标配**——
  见 §3.4 与 §4，真正带"比较后再写"的是 git。

## 3. CLI agent：Aider 与 Codex `[源码]`

### 3.1 Aider：写前必须「读过」，否则**问人** `[源码]`

`Aider-AI/aider` · `aider/coders/base_coder.py` · `allowed_to_edit()`（`:2191-2240`）：

```python
def allowed_to_edit(self, path):
    ...
    if full_path in self.abs_fnames:          # 已在 chat 里 = 读过
        self.check_for_dirty_commit(path)
        return True

    if self.repo and self.repo.git_ignored_file(path):
        self.io.tool_warning(f"Skipping edits to {path} that matches gitignore spec.")
        return

    if not Path(full_path).exists():
        if not self.io.confirm_ask("Create new file?", subject=path):
            self.io.tool_output(f"Skipping edits to {path}")
            return
        ...
    if not self.io.confirm_ask(
        "Allow edits to file that has not been added to the chat?", subject=path,
    ):
        self.io.tool_output(f"Skipping edits to {path}")
        return
```

**它怎么做的**：三档——
① 文件**在 chat 里**（= 模型读过其内容）→ 允许；
② 文件**不在 chat 里** → **必须先问人**「Allow edits to file that has not been added to the chat?」；
③ 文件命中 `.gitignore` → **直接拒**（连问都不问）。
**为什么**：没有读过就写，等于让模型对一份它没见过内容的东西动手——这是幻觉破坏力的来源。
**对我们的可借鉴点**：`abs_fnames` 就是我们的 `expectedVersion`/`expectedIncarnation` 想表达的同一件事的
**较弱版本**（"读过" vs "读到的是这一版"）。我们已经有更强的机制，**但缺一条 Aider 有的东西：
gitignored / 不该碰的路径要有一份显式拒绝清单**（例如 `.git/`、`node_modules/`、`.dsh/`）。
这条列进 §6.2 的 `[待决]`。

### 3.2 Aider：**undo 靠 git，而且删不了文件** `[源码]`

- **写前先提交**：`check_for_dirty_commit()`（`:2175-2190`）——文件脏就
  `self.io.tool_output(f"Committing {path} before applying edits.")`，把"改之前的样子"先钉进 git。
  注释直说了动机：`# We need a committed copy of the file in order to /undo`。
- **`/undo`**：`aider/commands.py` · `raw_cmd_undo()`（`:560-660`），四道前置拒绝：
  1. 最后一个提交**不是本会话里 aider 做的** → 拒（`aider_commit_hashes` 记账）；
  2. 是 merge（`len(last_commit.parents) > 1`）→ 拒；
  3. **任一被改文件 `is_dirty` → 拒**：`"The file {fname} has uncommitted changes. Please stash them before undoing."`；
  4. **已经 push 到 origin → 拒**：`"The last commit has already been pushed to the origin. Undoing is not possible."`。
  全过后才 `git checkout("HEAD~1", file_path)` **逐文件**回滚，最后 `git reset("--soft", "HEAD~1")`；
  部分成功时**两份清单都报**（`Restored files:` / `Unable to restore files:`）并中止。
- **删除**：`base_coder.py` / `commands.py` 里**没有任何** `os.remove` / `unlink` / `shutil.rmtree` / `trash`。
  Aider **没有删除文件的能力**。

**它怎么做的**：把"可撤销"完全外包给 git，并且**拒绝在会丢信息的前提下撤销**（有未提交改动就停）。
**为什么**：git 已经把"历史"这件事做完了，自己再发明一套快照只会漂移；
而"有未提交改动还去 checkout"正是把人家的改动冲掉——与我们的红线同一条。
**对我们的可借鉴点**：
- ✅ **「undo 的前置条件比 undo 本身更重要」**——Aider 用四道拒绝换来的确定性，比一个能撤销但会
  偶尔冲掉别人改动的 undo 值钱得多。我们的 `[码] workspace-paths.js:354 assertTargetUnchanged`
  是同一思路在单次写入尺度上的版本。
- ✅ **「先钉住旧内容，再改」**——`Committing {path} before applying edits`。对应到 Tier 4：
  **删除前先把内容留下来**（§4.3 Codex 直接这么做了）。
- ❌ **Aider 完全没有删除能力**，所以它对我们 Tier 4 的参考价值到"删除需要额外设计"为止。
- ❌ 它用 `git checkout`/`git reset` 做撤销——**这两条命令在我们的红线里被明令禁止**
  （禁止 `git checkout --` / `git restore` / 清理他人改动）。所以 Aider 的 undo 形态**不能抄**，
  只能抄它的**前置拒绝**。

### 3.3 Codex：删除 = 拒目录 + 删前把内容读出来 `[源码]`

`openai/codex` · `codex-rs/apply-patch/src/lib.rs` · `Hunk::DeleteFile`（`:501-563`）：

```rust
Hunk::DeleteFile { .. } => {
    let deleted_content = fs.read_file_text(&path_uri, ReadFileOptions { follow_symlinks }, sandbox)
        .await.ok();
    if deleted_content.is_none() { delta.exact = false; }
    ensure_not_directory(&path_uri, fs, follow_symlinks, sandbox).await.with_context(|| {
        format!("Failed to delete file {}", ...)
    })?;
    if let Err(error) = fs.remove(&path_uri, RemoveOptions { recursive: false, force: false, follow_symlinks }, sandbox).await { ... }
    if let Some(content) = deleted_content {
        delta.changes.push(AppliedPatchChange {
            path: path_uri,
            change: AppliedPatchFileChange::Delete { content },   // ★ 删掉的内容被带回结果里
        });
    }
    deleted.push(affected_path);
}
```

三个决定，逐条都值得看：
1. **`ensure_not_directory`**：`*** Delete File:` **只能删文件，不能删目录**，`recursive: false` 写死。
2. **`read_file_text` 在 `remove` 之前**，且**内容进结果**（`Delete { content }`）——
   删除动作的产物里带着"被我删掉的是什么"，让上层有恢复材料。
3. 读不到内容也不拒删，但会把 `delta.exact = false` 打下来（**诚实降级**，不是假装精确）。

`codex-rs/protocol/src/protocol.rs` · `AskForApproval`（`:1097-1137`）：

```rust
pub enum AskForApproval {
    UnlessTrusted,                       // 未信任项目：默认要求批准
    OnRequest,                           // 模型自己决定何时问人（默认值）
    Granular(GranularApprovalConfig),    // 逐类别开关：sandbox_approval / rules / skill_approval / request_permissions / mcp_elicitations
    Never,                               // 永不问人，失败直接回给模型
}
```

**它怎么做的**：删除的**能力**做得很窄（单文件、不递归、带内容），删除的**许可**交给一个
独立策略层（`AskForApproval`），能力层不做确认。
**为什么**：确认是产品策略（信任等级不同），能力是协议语义——混在一起会让"同一段代码在不同模式下
语义不同"。分开之后，能力层可以永远保持"窄且可报"。
**对我们的可借鉴点**：
- ✅✅ **「能力窄 + 许可独立」正是我们该有的分层**：`vscode.deleteFile` 永远只做单文件、
  永远 `useTrash`、永远带内容快照；"要不要人确认"由 grant/白名单/配置决定，**不写进能力本身**。
- ✅ **拒删目录**这条，codex 给了"成熟 agent 的真实选择"作为依据（不是我们的洁癖）。
- ✅ **`delta.exact = false`** 这种"我做不到精确但我不撒谎"的字段，与我们 §5.1「成功外形的错误结果」
  是同一价值观。
- ⚠️ **`GranularApprovalConfig` 是逐类别布尔**——它告诉我们"许可的粒度应该按**动作类别**分"，
  而不是按插件分一个总分。这直接影响 §6.2 四问之四的白名单粒度（倾向「插件 × 最高档位」）。

## 4. Git 与操作系统层：删除语义

### 4.1 `git rm`：删之前先算「这份内容还有没有别的地方存着」`[源码]`

`git/git` · `builtin/rm.c`（`:150-245`）。核心注释（原文）：

```c
/*
 * "rm" of a path that has changes need to be treated carefully not to allow
 * losing local changes accidentally.  A local change could be (1) file in
 * work tree is different since the index; and/or (2) the user staged a content
 * that is different from the current commit in the index.
 *
 * In such a case, you would need to --force the removal.  However, "rm
 * --cached" (remove only from the index) is safe if the index matches the file
 * in the work tree or the HEAD commit, as it means that the content being
 * removed is available elsewhere.
 */
```

判定就是两个布尔相乘：

| `local_changes`（工作树 ≠ index） | `staged_changes`（index ≠ HEAD） | 结果 |
|---|---|---|
| ✗ | ✗ | 允许删除（内容在 HEAD 里还有一份） |
| ✗ | ✓ | 拒，提示 `use --cached to keep the file, or -f to force removal` |
| ✓ | ✗ | 拒，同上 |
| ✓ | ✓ | 拒（更严重：`staged content different from both the file and the HEAD`） |

`docs` 侧（`Documentation/git-rm.adoc:49-55`）把 `-f` 的语义写成一句极简的话：
**`--force`: Override the up-to-date check.** 另有 `--dry-run` / `-n`（"不真删，只报会删什么"）。

**它怎么做的**：删除的默认行为不是"删"，而是"**证明这份内容在别处还活着**，然后删"。
`-f` 不是"更用力地删"，是**显式放弃这项证明**。
**为什么**：删掉一个只存在于工作树里的版本 = 不可恢复的信息丢失；而 git 恰好有"别处还有一份"这个可判定的谓词。
**对我们的可借鉴点**：
- ✅✅ **「删前先证明内容在别处活着」是 Tier 4 的核心判据雏形**。我们的映射是：
  **`useTrash:true` 就是这项证明的尝试**——但我们**无法证明它成立**（见 §4.2），
  所以必须自己再补一份证明：**把内容读进返回值 / 落快照**（= Codex 的做法）。
- ✅ **`--dry-run` 应该是一个真能力**：先回"我会删什么"，人确认，再删。
  这比"删了再报告"便宜得多，且天然契合两阶段。我们的 §6.1.1 ④ 只规定了"越过线性化点后怎么报"，
  **没有规定"可以停在点之前"**——`dryRun` 是 Tier 4 该有的形状。列进 `[待决]`。
- ❌ **`git rm` 只看 git 视角**：一个文件如果 untracked，`git rm` 根本不处理它（它不在 index 里）。
  我们面对的是**任意工作区文件**，`git rm` 的判据只覆盖 tracked 子集，**不能直接套**。

### 4.2 Windows 回收站：唯一的成熟做法是 `IFileOperation`，而且它会**静默失败** `[源码]`

Node 生态里 `trash`（sindresorhus，最主流）在 Windows 上**不是 JS 实现**：

`trash/lib/windows.js`（全文）：

```js
import chunkedExec from './chunked-exec.js';
// Binary source: https://github.com/sindresorhus/recycle-bin
const binary = new URL('windows-trash.exe', import.meta.url);
export default async function windows(paths) {
	await chunkedExec(binary, paths, 200);
}
```

`trash/package.json` 的运行期依赖有 **9 个**：`@stroncium/procfs`、`chunkify`、`globby`、
`is-path-inside`、`move-file`、`p-map`、`powershell-utils`、`wsl-utils`、`xdg-trashdir`。

那个 `.exe` 的源码在 `sindresorhus/recycle-bin` · `recycle-bin.c`：

```c
if (IsWindows8OrGreater()) {
    CHECK_OBJ(op, op->lpVtbl->SetOperationFlags(op,
        FOFX_ADDUNDORECORD | FOFX_RECYCLEONDELETE |
        FOF_NOERRORUI | FOF_NOCONFIRMATION | FOF_SILENT | ...));
} else {
    CHECK_OBJ(op, op->lpVtbl->SetOperationFlags(op,
        FOF_NO_UI | FOF_ALLOWUNDO | FOF_NOERRORUI | FOF_SILENT | FOFX_EARLYFAILURE));
}
```

同一个文件里两条注释是**这次调研最值钱的东西**：

```c
// Undocumented shell32 export, not in any public header or import library.
// SHFileOperation calls this internally after every recycle-bin delete to make
// Explorer refresh the desktop icon and "Empty Recycle Bin" menu state.
// IFileOperation doesn't reliably trigger the same refresh, so we call it
// ourselves via GetProcAddress.
```

```c
// Resolve subst virtual drive paths to their real paths.
// Without this, IFileOperation silently fails to recycle files on subst drives
// because Windows has no Recycle Bin associated with virtual drives.
```

**它怎么做的**：`IFileOperation` + `FOF_ALLOWUNDO`（`FOF_ALLOWUNDO` 就是"可以撤销 = 走回收站"），
外加**两个补丁**：手动 `SHUpdateRecycleBinIcon()`（一个**未文档化导出**），以及 **subst 虚拟盘的路径解析**。
**为什么**：回收站不是一个 API 调用，是一堆历史包袱——`IFileOperation` 有已知的 UI 刷新缺陷，
虚拟盘上根本没有回收站。（顺带：`send2trash` 是 Python 的同类实现，对本项目无用，只证明"这件事每个语言都要自己扛一次"。）

**对我们的可借鉴点**：
- ✅ **"能进回收站"是一件需要**每台机器分别成立**的事，不是平台保证**。所以 §6.2 里
  `vscode.deleteFile` 的返回值**不许出现 `trashed:true`**——我们拿不到这个事实。
- ✅ **`FOF_ALLOWUNDO` 的语义**是"允许撤销"，不是"可撤销"。连 Windows 自己的措辞都是**允许**。
- ❌ **不引入依赖时，Node 侧没有任何回收站 API**（Node core 无此功能）。而 `trash` 要 **9 个依赖 + 一个
  预编译 `.exe`**，对"协议库零依赖"（`AGENTS.md:10`）的项目是**不可接受的方向**。
- ✅✅ **正解不在 npm 里**：我们的宿主就是 VS Code，它**已经**有一套回收站实现和四个配置项（§4.3）。
  所以 Tier 4 **不需要任何新依赖**。

### 4.3 VS Code 自己就是我们最好的先例：`useTrash` 是「尽力而为」，且**能力位不对扩展开放** `[源码]`

**(a) 扩展 API 的签名与措辞**（`src/vscode-dts/vscode.d.ts:9827-9835`）：

```ts
delete(uri: Uri, options?: {
    recursive?: boolean;
    /** Use the os's trashcan instead of permanently deleting files whenever possible. */
    useTrash?: boolean;
}): Thenable<void>;
```

> **"whenever possible"** —— 契约作者自己承认：**请求了回收站，不等于进了回收站，而且不报错。**

**(b) 平台层有 Trash 能力位，但**扩展 API 拿不到**（`src/vs/platform/files/common/files.ts:636`）：

```ts
/** Provider supports to delete via trash. */
Trash = 1 << 12,
```

`IFileDeleteOptions.useTrash` 的注释（同文件 `:428-436`）也是同一句：**"attempt to move the file to trash… This option may not be supported on all providers."**
而扩展侧 `vscode.workspace.fs`（`FileSystem` 接口，`vscode.d.ts:9785-9835`）**没有** `capabilities` 查询——
只有 `isWritableFileSystem` 之类。**结论：扩展侧无法在删除前探测"这台机器/这个挂载点能不能进回收站"。**

**(c) VS Code 自己的默认值，就是它对人做的承诺**（`src/vs/workbench/contrib/files/browser/files.contribution.ts`）：

| 配置 | 默认值 | 行 |
|---|---|---|
| `files.enableTrash` | **`true`**（"Moves files/folders to the OS trash (recycle bin on Windows) when deleting. Disabling this will delete files/folders permanently."） | `:232-236` |
| `explorer.confirmDelete` | **`true`** | `:494-497` |
| `explorer.enableUndo` | **`true`** | `:499-502` |
| `explorer.confirmUndo` | `Default`（"prompt before **destructive** undo operations"） | `:504-512` |

**它怎么做的**：默认走回收站、默认问一次、默认能撤销、撤销也默认问一次。
**为什么**：VS Code 面对的是同样的不可逆问题，它的答案不是"做个更好的删除"，而是**四个默认值全站在保守一侧**。
**对我们的可借鉴点**：
- ✅✅ **Tier 4 的默认值应该与宿主一致**：`useTrash` 强制 `true`（不提供关掉的参数）、删除前问人。
  既然 VS Code 自己都默认问，DSH 替人删而不问是**比宿主更激进**，不可接受。
- ✅ **撤销**我们做不到（`FileSystem` 没有 restore），所以**更要**把"内容"和"确认"做在前面。
- ⚠️ **`explorer.enableUndo` 的撤销栈是 Explorer 的，不是我们的**：我们删完之后**无法**驱动它。

### 4.4 保存这一侧，VS Code 的实现给了三个硬数字 `[源码]`

`src/vs/workbench/api/common/extHostDocumentSaveParticipant.ts`（全文 177 行，读完了）：

```ts
private readonly _thresholds: { timeout: number; errors: number } = { timeout: 1500, errors: 3 }
```

- **1500 ms 硬超时**：`$participateInSave` 里 `setTimeout(() => didTimeout = true, 1500)`，
  超时后**后面的参与者全部不再执行**（`if (didTimeout) break;`）；
- **报错 3 次以上永久忽略**：`if (typeof errors === 'number' && errors > this._thresholds.errors) {
  this._logService.info(... 'will now be IGNORED because of timeouts and/or errors'); }`
- **版本守卫 + `versionId: undefined`**：

```ts
if (version === document.version) {
    return this._mainThreadBulkEdits.$tryApplyWorkspaceEdit(new SerializableObjectWithBuffers(dto));
}
return Promise.reject(new Error('concurrent_edits'));
```

注意 `dto` 里每个 edit 都是 `versionId: undefined`——**保存前的编辑是"无版本锚"地提交给主线程的**，
版本检查只发生在这个 JS 判断里。也就是说：**连 VS Code 自己的"保存前编辑"也有和我们 B1 同构的窗口**，
它接受这个窗口，因为紧接着就要保存了。

另外 `waitUntil(p)` 有一条硬规则：`if (Object.isFrozen(promises)) { throw illegalState('waitUntil can not be called async'); }`
——**不允许异步地决定"要不要在保存前加编辑"**。

**它怎么做的**：保存前参与者是一个**有预算的、可被永久禁用的、非阻塞门**。
**为什么**：同 §1——保存必须快；一个坏插件不能让人永远存不了盘。
**对我们的可借鉴点**：
- ✅✅ **`vscode.save` 落盘的实际字节 ≠ 缓冲区内容**：`editor.formatOnSave`、`trimTrailingWhitespace`、
  任何 `onWillSaveTextDocument` 参与者都会插入编辑。所以 Tier 3 **不能声称**"磁盘内容 = 我锚定的缓冲区内容"。
  这是"这一档明确不保证什么"里必须有的一条。
- ✅ **1500 ms / 3 次**这两个数字说明：**保存可能因为别人的参与者而失败或变慢**。
  我们的超时必须留够（`-32004 TIMEOUT` 的既有口径），且**不能把"慢"当成"没发生"**（§6.1.1 ④）。
- ✅ **`waitUntil` 不许异步** = "决定要在保存前做什么"必须**同步**做完。我们 `[码] edit-transaction.js`
  把版本比对放进 `TextEditor.edit` 的**同步 callback**，是同一个教训的另一种写法。

## 5. 汇总：我们能借鉴什么 / 不能借鉴什么

| # | 来源 | 能借鉴 | 不能借鉴 |
|---|---|---|---|
| 1 | LSP `willSave` / `willSaveWaitUntil` | **保存前钩子不具否决权**，别把保证建立在它上面；"提交编辑"而非"提交内容"的增量形态 | 指望保存前检查获得任何原子性 |
| 2 | LSP `applyEdit` 结果形状 | `applied` + `failureReason` + 第几个 change 失败；`label` 服务撤销栈 | —— |
| 3 | LSP 只有 `didDeleteFiles` | **删除在上游就没有护栏**，护栏只能自建 | 等一个"删前钩子"出现 |
| 4 | MCP filesystem 白名单 | 「原样根 + realpath 根两份都留」；段边界前缀判定；不存在尾段只 realpath 已存在前缀 | 靠 realpath 结果放行符号链接（我们应当是发现即拒）；无版本约束直接写 |
| 5 | MCP `write_file`/`edit_file` | `O_NOFOLLOW` / `wx` 独占创建是"窗口内被换掉"的正确工具 | 它**完全不比内容版本**——我们已有 `-32012` 双锚点，不能倒退 |
| 6 | Aider `allowed_to_edit` | **没读过就问人**；gitignored 路径**直接拒**（我们缺一份显式拒绝清单） | 用 `abs_fnames` 级别的"读过"代替版本锚点 |
| 7 | Aider `/undo` 的四道拒绝 | **undo 的前置条件比 undo 本身重要**；有未提交改动就停；部分成功要报两份清单 | `git checkout` / `git reset` 做撤销（本项目红线明令禁止） |
| 8 | Aider 无删除能力 | 删除需要单独设计，不能顺带做出来 | —— |
| 9 | Codex `DeleteFile` | **拒删目录**（`ensure_not_directory` + `recursive:false`）；**删前读内容并放进结果**；`delta.exact=false` 式诚实降级 | 读不到内容仍继续删（我们应当宁可不删） |
| 10 | Codex `AskForApproval` | **能力窄 + 许可独立**；许可按**动作类别**分层（`Granular`） | 把确认塞进能力层，让同一段代码在不同模式下语义不同 |
| 11 | `git rm` | **删前先证明内容在别处活着**；`-f` = 显式放弃这项证明；`--dry-run` 是真能力 | 它的判据只覆盖 tracked 子集，我们是任意文件；用 `git rm` 当删除实现 |
| 12 | Windows `IFileOperation`（recycle-bin.c） | 回收站**每机器分别成立**、会**静默失败**（subst 盘）、`FOF_ALLOWUNDO` 只是"允许撤销" | 不引入 9 个依赖 + 预编译 `.exe`（违反零依赖铁律）；声称"已进回收站" |
| 13 | VS Code `useTrash` | 契约措辞就是答案：**"whenever possible"**，且**扩展侧无能力位可探** | 把 `useTrash:true` 当成"已安全"的证据 |
| 14 | VS Code 四个默认值 | `enableTrash`/`confirmDelete`/`enableUndo` 全默认 `true` → **Tier 4 必须问人、必须 trash** | 驱动 Explorer 的撤销栈（我们做不到） |
| 15 | VS Code 保存参与者 | 1500 ms / 3 次错误即忽略 → 保存会因他人失败；`waitUntil` 不许异步 | 声称"磁盘内容 = 我锚定的缓冲区内容"（格式化/trim/参与者会改字节） |
| 16 | `TextDocument.save()` 签名 | **无参数 → 无 CAS → Tier 3 的原子性上限是"尽力早失败"** | 把 Tier 3 的保证写成与 Tier 2 的 `-32012` 等价 |

## 6. 这次调研直接推翻了什么 / 确认了什么

**推翻（草案里不能写的）**：
1. ~~「保存前做一次 isDirty + 版本检查就够了」~~ → 检查**不具约束力**（§1），
   而且真正的问题不是"检查够不够"，是 **`save()` 没有 CAS 参数**（§4.4 / 表 #16）。
   Tier 3 的保证必须**降级表述**。
2. ~~「用了 `useTrash:true` 就是软删除」~~ → "whenever possible"（§4.3），
   且 subst 盘上会静默失败（§4.2）。**返回值里不许出现 `trashed:true`。**
3. ~~「要进回收站就装 `trash` 包」~~ → 9 个依赖 + 预编译 exe，违反零依赖；
   而宿主已经提供了同一能力（§4.3）。**零依赖正解是 `workspace.fs.delete`。**

**确认（我们已有设计是对的，记下来别再动摇）**：
1. **读侧拿到的是缓冲区不是磁盘**（`[码] vscode-host.js` 头注释「不要换成内容哈希或 `mtime`」）——
   §4.1 的 `local_changes` 与 §4.4 的 `versionId: undefined` 都在说同一件事：**"内容版本"和"磁盘版本"
   是两个不同的锚，别混用**。
2. **编辑要增量、要带锚、要能报第几个失败**——LSP `applyEdit`（§1.1）与我们的 `saved:false` 同构。
3. **删除要窄**——Codex 拒目录（§3.3）、VS Code 默认问人（§4.3）、`git rm` 先算信息是否丢失（§4.1），
   三个独立来源指向同一个结论。
