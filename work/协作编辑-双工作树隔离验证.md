## 7. 判断段

### 7.1 这套隔离在 Windows 上是否成立？

**成立。** 依据（按强度排序）：

1. **方向一（文件隔离）**：agent 树 `?? _isolation_probe.txt` 与主树空输出的**同时**快照（第 3 节）；且 `check-ignore` 返回 1，排除"被 ignore 掩盖"的假阴性。
2. **方向二（HEAD 隔离）**：agent 树 `.git` 是**文件**（`gitdir: …/.git/worktrees/dsh-vscode-dev-agent`）、主树 `.git` 是**目录**；两边 HEAD 落在不同物理文件（`refs/heads/main` vs `refs/heads/agent/editing-mvp`），`rev-parse --git-dir` 两边不同，`--git-common-dir` 相同 —— 共享对象库、分离工作区状态，正是 worktree 的设计语义。
3. **index 独立**：`.git/index` 与 `.git/worktrees/dsh-vscode-dev-agent/index` 各自一份（大小恰好都 8958 字节属巧合，路径不同）。index 独立意味着两边 `git add` 不会互相踩。
4. **失败即拒**：三种冲突（路径已存在 / 分支名已存在 / 分支已被别的树检出）全部非零退出并给出明确 fatal，退出码 128 / 255 / 128；未观察到"静默覆盖"或"半成功"。

Windows 特有的风险点（长路径、盘符大小写、`.git` 文件用正斜杠路径）**本次均未触发**：`gitdir:` 行用 `D:/…` 正斜杠，Git for Windows 正常解析，后续对 agent 树的所有 git 操作都 work。

## 8. 经验沉淀（可复用）

1. `git worktree add -b <新分支> <路径>` **不是原子操作**：先建分支 ref，后校验路径。路径冲突时退出码 128，但**分支已留下**。自动化脚本里若用 `-b`，失败后要顺手 `git branch -d <残留分支>`，否则下一次运行会撞上"a branch named … already exists"（255），错误信息还指不到真因。
2. 想避开上述残留：先 `git branch <新名> <起点>` 会同样留 ref；更稳的是**先用 `git worktree list` + 路径存在性做前置校验，再用不带 `-b` 的 `git worktree add <路径> <已存在分支>`** —— 分支被别处占用时会被干净拒绝（128，`already used by worktree at …`），零残留。
3. 判断"两个工作树是否真隔离"，最快的证据链是三个文件：`.git` 是文件还是目录、`rev-parse --git-dir`、`rev-parse --git-common-dir`。三者一眼就能区分"共享对象库 + 独立状态"。
4. 用 `git check-ignore -v` 给 `status` 做交叉验证：否则"文件没出现"可能是被 ignore 掩盖，而不是隔离成功。
