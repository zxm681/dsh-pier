## 2. 两条旧复现重放：H1 关闭

### 2.1 raw request 省略化身：拒绝，零写入

无 session 的 getDocumentState 仍从活跃 B 得到 v7/inc-B；grant 绑定 A。调用公开 `kit.request('vscode.applyEdit', {file, expectedVersion:7, range:第一行1至6列, text:'DSH!!'}, {sessionId:'S'})`，不经糖衣、不带 expectedIncarnation。

本轮独立输出：

```json
{"case":"raw missing incarnation / same v7","code":-32602,"reason":"expected-incarnation-missing","frames":{"A":0,"B":0},"writes":0,"constructs":0,"bufferA":"HUMAN\nline2\nline3\n"}
```

上轮另一个重开模拟（版本回到 1、实际实例换成 inc-reopened）也重放：raw 省略化身得到同样 `-32602 / expected-incarnation-missing`，相对本次调用写帧增量 0、宿主写调用增量 0、edit 构造增量 0，HUMAN 保留。**没有把模拟的版本复用说成真机生命周期实验。**

依据：[kit 共用发送门:1078–1096](<../packages/dsh-vscode-kit/src/index.js#L1078-L1096>)在 grant 判定之后、link.request 之前检查真正的 wireParams；[桥端:346–357](<../packages/dsh-kit-bridge/src/capabilities.js#L346-L357>)及[调用点:859–866](<../packages/dsh-kit-bridge/src/capabilities.js#L859-L866>)无条件要求非空字符串。空串、null、数字不按缺省悄悄降级。

### 2.2 同版本双窗口、双方公告：错误实例拒绝，不再 applied:true

沿用相同 A/B 与授权，把 B 的版本和化身都带到 **raw request** 写 A，刻意不使用糖衣来源表提前拦截，以验证收端真实判断：

```json
{"case":"raw B anchor to A / both advertise / same v7","code":-32012,"reason":"incarnation-mismatch","frames":{"A":1,"B":0},"writes":0,"constructs":0,"bufferA":"HUMAN\nline2\nline3\n"}
```

写帧按 grant 到 A，不到 B；桥端比较的是 A 实例，拒绝原因不是版本不等；零 host.applyEditText 调用、零 edit 构造。**若仍省略化身，正确结果是 §2.1 的 -32602；-32012 是“给了另一实例化身”的结果，两者不混称。**

另外独立把实例切换放进 readDocumentShape 的 await 间隙：早期读到 inc-A，事务实际读到 inc-reopened，版本仍 7。结果 `-32012 / incarnation-mismatch`，host 写调用发生 1 次、builder.replace 0 次，HUMAN 保留。把版本变化放在相同缝隙也得到 -32012、零 edit 构造。不能把“零构造”误说为这两种事务冲突的“宿主零调用”。

正向对照在独立新 setup 中运行：同一 raw 入口带 v7/inc-A/expectedRangeText='HUMAN'，**applied:true、saved:false**，A 缓冲区变成 DSH!!，恰好 1 次写调用/1 次 edit；磁盘前后逐字节一致。门不是把所有写一刀切禁用了。

## 4. 旧测试反转：正当修复，不是迁就实现

**安全不变量应挂在写协议与最终提交路径上，不应挂在对端 features 公告上。**

理由：

1. version 是每实例计数，A/B 可以都为 7；没有 incarnation 就不能证明正在写哪一个实例。公告缺失不提供任何替代证据。
2. 若“没公告 ⇒ 少判化身”，一个正常旧消费者/未公告端就能选择关掉同实例约束，安全退化恰好恢复上轮 H1；这不是安全兼容。
3. 正确的兼容代价是“没有可靠实例锚点就拒写”，不能将旧危险行为当必须维持的成功语义。[收紧说明:320–345](<../packages/dsh-kit-bridge/src/capabilities.js#L320-L345>)明确记录了这项不兼容变更，不是默默改期望值。
4. [新增 raw 回归:361–401](<../packages/dsh-vscode-kit/test/t34-anchor-binding.test.js#L361-L401>)实际调用公开 request，断言零写帧，并有带正确化身的成功对照；[桥端新测试:183–275](<../packages/dsh-kit-bridge/test/t35-incarnation-mandatory.test.js#L183-L275>)含前置拒绝、事务实例错配、事务缺值、正常写与磁盘不变。不是只把四份 params 喂同一 handler 就宣称覆盖四公开入口。
5. 本轮把对应检查去掉后真实变红（§5），证明不是断言永不触发或假计数。

精确核对题设所称“两条反转”：现场 [multiwin:220–255](<../packages/dsh-vscode-kit/test/t5-negative-multiwin.test.js#L220-L255>)的危险跨窗糖衣用例现在期望 **-32602 anchor-source-mismatch**；[265–284](<../packages/dsh-vscode-kit/test/t5-negative-multiwin.test.js#L265-L284>)是**同会话正常写仍成功**的对照，并非也反转为拒绝。生命周期实例复用拒写在桥端 [Q3:283 起](<../packages/dsh-kit-bridge/test/t5-negative-lifecycle.test.js#L283>)。不能机械声称“multiwin 现有两条都改为 -32602”。这个用例拆分不改变正当性裁决；危险成功应反转，正确成功必须保留。

[未公告也拒绝:314–351](<../packages/dsh-vscode-kit/test/t34-anchor-binding.test.js#L314-L351>)的变更同样正当。它拒的是缺化身，不是拒一切未公告端：未公告但确实返回并正确校验化身的实现，仍能正常工作。**仅传一个非空字符串不能证明旧扩展升级了；本报告的安全保证以两端实际运行本次锚点语义为前提，不把注释里的“旧版扩展从此不能写”扩张成对任意旧/伪造宿主的版本强制认证。**
