## 必改项

### B1-a / 阻断：随机隔离名仍不是对象/字节绑定，最终窗口仍可删错并报成功

**位置**：[capabilities.js:1787–1793](<../packages/dsh-kit-bridge/src/capabilities.js#L1787-L1793>)、[capabilities.js:1830–1835](<../packages/dsh-kit-bridge/src/capabilities.js#L1830-L1835>)、[vscode-host.js:521–525](<../packages/dsh-kit-bridge/src/vscode-host.js#L521-L525>)；“没有别人能把目标换到它上面”的断言位于 [capabilities.js:1832](<../packages/dsh-kit-bridge/src/capabilities.js#L1832>)。

**实证（原适配器贯通，不改实现）**：隔离文件验证通过后，在模拟 `workspace.fs.delete` 消费 URI 时，先 rename 隔离文件到 `.old`，在同一隔离名写另一份字节，再 unlink。输出 [output.log:8](<t43-probes/output.log#L8>)：

```text
mode=provider-race
snapshot.text=ORIGINAL_SECRET
实际删除字节=NEW_NO_BACKUP!!（hex: 4e45575f4e4f5f4241434b55502121）
result.deleted=true; backup.delivered=true; deletes=1
quarantined=null; oldQuarantined=ORIGINAL_SECRET
```

这与 T41 B1 实证 2 是同一类 provider 消费路径竞态，只是窗口移到了隔离名。随机名不是私有命名空间，也不提供 compare-and-delete。

**不依赖获知随机名的加强实证**：[output.log:9](<t43-probes/output.log#L9>) 的 `open-writer` 在隔离前对原文件 `openSync(file,'r+')`，在隔离验证完成、实际 unlink 前，使用预先打开的 fd 写入同长度 `NEW_NO_BACKUP!!`。rename 不撤销已有写句柄；结果仍是 `deleted:true`、快照 `ORIGINAL_SECRET`、实际删除 `NEW_NO_BACKUP!!`，且没有留下该新字节。这个交错无需猜隔离名、无需改宿主源文件或取得恶意插件权限；是在 provider 破坏点确定性调度一次既有外部写入，不声称做过真实 GUI 验收。

**为何仍属原 B1**：仍然是“确认/快照里的字节 ≠ 实际删除的字节”，成功回执无法恢复未经确认的新版本；并非重开 T39 无 CAS 上限，也不是另列 I1。隔离确实保护了原名上的后续新文件，但未证明删除本身绑定了已确认版本。

**必须修改**：在具备绑定对象且能阻止验证后内容变化的删除原语之前，关闭/拒绝该删除能力；或由宿主实现并证明这种保证。不得再用随机名字或追加一次 hash 充当原子绑定。补上上述 provider 消费窗口和预存写句柄窗口的回归，要求不删除未确认字节、不报告成功。

### B1-b / 重要：紧贴 rename 前的替换未按要求返回 -32013

**位置**：[capabilities.js:1747](<../packages/dsh-kit-bridge/src/capabilities.js#L1747>)、[capabilities.js:1805–1817](<../packages/dsh-kit-bridge/src/capabilities.js#L1805-L1817>)。

**实证**：[output.log:3](<t43-probes/output.log#L3>) 的 `before-rename` 在宿主执行隔离 rename 前，把原件移到 `.old`，原名写同长度的另一文件；此时确认后第二次字节校验已经完成。验证拒绝并回滚，`deletes=0`，两份字节都在，但返回 **-32603 / target-changed-after-confirm**，不是本轮判据明确要求的 **-32013**。

现有 [B1-② 测试:596–620](<../packages/dsh-kit-bridge/test/t40-delete.test.js#L596-L620>) 的替换发生在 `onConfirm`，不是提供出来的 `onBeforeQuarantineRename` 窗口；因此其 -32013 通过不能覆盖上述情况。

**必须修改**：将隔离后证实目标字节已变化的冲突归类为 -32013，保留当前不删与安全回滚信息；增加真正发生在 rename 之前、最后一次预验之后的回归，断言 -32013 和两份文件均存活。
