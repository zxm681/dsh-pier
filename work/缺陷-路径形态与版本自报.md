## 0. 一句话结论

两个缺陷是**同一个形状**：同一件事实被写了两份。①「路径该长什么样」有三次实现（RPC 出口大写、
事件 payload 小写、注册表键又小写一次），拿字符串精确比较 ⇒ 静默零命中；②「扩展版本是多少」有两次
手写（`connector.js` 与 `package.json`）⇒ 真机报 0.3.1、清单是 0.3.2。

修法是各留**一份**实现：路径形态只存在于 `dsh-vscode-kit/src/paths.js`，版本只存在于扩展
`package.json`（运行时读）。并且把「静默」这件事本身修掉——订阅回执现在会告诉你「这个过滤建立时，
在这个窗口里命中了几个已打开文件」。

## 1. 缺陷①：事件过滤静默失配

### 1.1 你给的已核实事实（我自己复核过，结论一致）

| 位置 | 修改前行为 |
| --- | --- |
| `packages/dsh-vscode-kit/src/event-subscriptions.js:891` | `filter.files.includes(...)` 精确字符串比较 |
| `packages/dsh-kit-bridge/src/capabilities.js:555` | `canonicalPath`：Windows 盘符**大写** |
| `packages/dsh-vscode-kit/src/windows.js:126` | 注册表指纹键：盘符**折成小写** |
| `packages/dsh-kit-bridge/src/editor-events.js` `fileOf()` | 直接回宿主 `doc.uri.fsPath`，Windows 上盘符**小写** |

照 `vscode.listOpenEditors` 返回的 `D:/ws/a.txt` 去写 `subscribe({files:['D:/ws/a.txt']})`，而
payload 是 `d:/ws/a.txt` ⇒ 精确比较不等 ⇒ 一条事件都不来，且 `ok:true`。

### 1.2 统一后的「对外可见路径形态」

**Windows：盘符大写、其余字节原样（段名大小写、分隔符 `/`、尾部斜杠都不动）。POSIX：原样返回。**

- 实现收敛到 `packages/dsh-vscode-kit/src/paths.js`（新文件，导出 `canonicalPath` /
  `pathIdentityKey` / `isUsableFilterPath`）。
- 三处接入，**同一个函数**，没有第二个形态规则：

| 面 | 接入点 | 效果 |
| --- | --- | --- |
| ① 事件过滤 + `payload.file` | kit `event-subscriptions.js`（归一化时把 `filter.files` 规范；`accepts()` 比较两侧都规范；出站 payload 规范）；bridge `editor-events.js` 的 `fileOf()` 是**唯一** `file` 出口，顺带覆盖 `tabsChanged.opened[].files` | 消费者照 RPC 返回值写白名单 ⇒ 命中 |
| ② RPC 返回值（`listOpenEditors` / `getSelection` / `getDiagnostics`） | bridge `capabilities.js` 改为 `import { canonicalPath }`（删掉本地私有副本） | 与事件面同一种写法 |
| ③ 注册表指纹键 | `windows.js` `normalizeRoot()` 改调 `canonicalPath`；`WindowRegistry._load` 增加 `renormalizeFingerprint()`，把老键（盘符小写）**就地迁移**，`win-NN` 号不变、幂等 | 键不再自己发明第三种写法 |

- 另有 `capabilities.js` 的 `serializeKeyFor()`（并发锁身份）改用 kit 的 `pathIdentityKey()`：它
  **不是**对外可见路径（依旧 `toLowerCase()`，理由保持原注释：锁键要的是文件身份，不是漂亮字符串），
  只是把实现也收成一份，避免"同一件事两处代码各自演化"。

### 1.3 取舍（这是本卡唯一会改变既有对外行为的地方）

**取舍：事件 `payload.file` 从「宿主小写盘符」改成「大写盘符」。**

- 为什么值得：不统一，消费者就必须知道"RPC 面大写、事件面小写"这条隐含知识，而这正是缺陷①的成因；
  统一后「同一个文件在对外任何地方都只有一种写法」成为一个可断言的性质（测试 `A1`/`A2`/`①-1` 钉住）。
  而且改动**不改变身份语义**：Windows 路径比较本来就不区分盘符大小写（`C:` 与 `c:` 恒等），
  任何做 `===` 比较的消费者以前是**错的**（收不到事件），现在对了；做规范化比较的消费者不受影响。
- 受影响消费者：只订阅事件、且把 `payload.file` 当**字面量**去匹配自己保存的小写形态的调用方。
  他们的修法是「改成 `listOpenEditors` 给的形态」——也就是本次统一后的形态，与 RPC 面一致。
- 反向兼容（老 DSH ↔ 新扩展 / 新 DSH ↔ 老扩展）都考虑过：白名单在**收进来那一步**
  （`normalizeEventFilter`）就规范化，`accepts()` 再规范化入站值，所以**老 DSH 发小写盘符的白名单照样命中**
  （测试 `A2` / `①-2`）。

### 1.4 过滤失配现在可观测（要求 2）

回执字段 **`filterMatch`**（`vscode.events.subscribe` 的返回值里，同级于 `subscription`）：

| 字段 | 语义 |
| --- | --- |
| `openFiles` | 建立这条订阅那一刻，**目标窗口里打开的文件数**（按规范形态去重） |
| `matched` | 其中**能通过本条 `filter.files` 白名单**的个数；没有文件白名单时 `= openFiles` |
| `filterFiles` | 白名单条目数；`null` = 不限文件 |
| `notOpen` | 白名单里**当时没打开**的前 3 条（按白名单顺序），**原样指出来**，让"拼错了哪一条"一目了然 |

- 数据来源与 `vscode.listOpenEditors` **同一个宿主调用**（bridge 传入 `host.listEditors()`），
  所以这个数字等于消费者真正看到的那份名单（`capabilities.js` 里接的 `openFiles` 钩子）。
- `matched === 0` 且 `filterFiles !== null` 时另做两件事：诊断环记一条 `filter-no-open-file-match`、
  日志 `warn` 一条（即使调用方不看回执也不静默）。`filterMatch` **不参与任何放行判定**。
- 拿不到文件列表 / 宿主没接钩子 ⇒ 整块 `null`（不猜、不因此拒服；测试 `B4`）。
- 同一个诊断也进 `broker.snapshot().subscriptions[].filterMatch`（测试 `B2`），以及客户端
  `handle.filterMatch`（kit facade 侧照抄，供 `forPlugin` 消费者用；测试 `B5`：对端不给 ⇒ `null`，不发明数字）。
- 契约影响：`filterMatch` 是**新增可选字段**，`response-contract` 不拒绝多余字段，老消费者忽略即可
  （`response-contract.test.js` 全绿；E2E 22/22 证明真链路不回退）。

## 2. 缺陷②：hello 自报版本说谎

- 修改前：`packages/dsh-kit-bridge/src/connector.js` 手写 `export const EXTENSION_VERSION = '0.3.1'`，
  而 `package.json` = `0.3.2`；`hello` 里 `extensionVersion` 用的就是前者。
- 修改后：新文件 `packages/dsh-kit-bridge/src/version.js`
  - `bridgePackageJsonPath()` = `<模块目录>/../package.json`（源码 `src/` 与打包 `out/` 同一相对位置；
    `moduleDir()` 优先 `__dirname`（CJS 打包产物），否则 `fileURLToPath(import.meta.url)`（ESM 单测））；
  - `readExtensionVersion()` 运行时 `JSON.parse(readFileSync(...))`，读不到回 `0.0.0-unknown`
    （**绝不**回一个看起来合理的版本号）；
  - `EXTENSION_VERSION = readExtensionVersion()`；`connector.js` 改为 `export { EXTENSION_VERSION }`
    （既有 `import ... from './connector.js'` 全部不受影响，两份 `hello` 构造点无需改）。
- 为什么**运行时读**而不是构建时注入：esbuild `define` 只覆盖产物，单测从 `src/` import 时又会需要一份
  兜底字面量 ⇒ 第二个来源复活。运行时读对「单测 / `node src/...` / `out/extension.cjs` / 装好的 vsix」
  四种跑法都成立，代码里没有平台或构建分支。

### 打包后如何验证（已实测）

1. `node scripts/build.mjs` 重新产出 `out/extension.cjs`（198.8kb）。
2. 产物里**没有任何版本字面量**：`grep -c '0\.3\.1' out/extension.cjs` → `0`；`'0\.3\.2'` → `0`
   ⇒ 版本只能来自运行时读文件。
3. 用 CJS 探针（`Module._load` 打桩 `vscode`，`fs.readFileSync` 拦截）**加载真实产物**：

```

manifestVersion: "0.3.2"
```
   ⇒ 打包产物读的确实是**扩展根**的 `package.json`（不是 cwd 的、不是某个缓存）。
4. 单测 `②-2` 用临时目录把 `src/` 与 `out/` 两种布局都摆出来，断言都读到扩展根清单（不依赖本仓库是否 build 过）。
5. 真机侧的最后一步（重装 vsix 后看 `hello.extensionVersion`）**不在本卡范围**：本卡未重启 DSH、未安装扩展。

## 6. 遗留与风险

   本卡的替代证据是 §2 的产物探针 + 单测 ②-2。
3. `filterMatch` 的 `openFiles` 每次订阅都会调一次 `host.listEditors()`（只读、轻量）。若未来窗口里文件极多
   且订阅风暴，可考虑缓存，但当前无必要（E2E 无性能回退）。
4. 注册表迁移只在 `_load()` 读老键时发生，**下一次写盘**才落盘（`this.migrated` 标记）；期间崩溃不影响
