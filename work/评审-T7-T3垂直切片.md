## 2. 阻断项

### F1 / 阻断：根自身及根祖先的 junction 被放行，写落点可到外部物理目录

**位置**：[workspace-paths.js:86–98](<../packages/dsh-kit-bridge/src/workspace-paths.js#L86-L98>)、[workspace-paths.js:116–143](<../packages/dsh-kit-bridge/src/workspace-paths.js#L116-L143>)；实际调用 [capabilities.js:317–331](<../packages/dsh-kit-bridge/src/capabilities.js#L317-L331>)。

`cursor` 从根开始，但 lstat 只在追加子段后执行，根没有被检查，根的祖先也不检查。之后同时 realpath 根和文件，再比较两者包含关系，恰好把根 junction 的目标当成新的合法物理根。真实 Windows junction 实测：

```text
fixture = C:\Users\zxm\AppData\Local\Temp\t25-review-FwJ1EH
root-junction -> OutsideLongName
P7 ROOT junction:
result = {applied:true, file:"...\\root-junction\\secret.txt", saved:false, textLength:1}
applyEditText.abs = "...\\OutsideLongName\\secret.txt"
applyEditText.range = {start:{line:0,column:0},end:{line:0,column:0}}
P8 ROOT ancestor junction:
result.applied = true
applyEditText.abs = "...\\WorkspaceLongName\\a.txt"
```

P7 的外部目标不是工作区字面根的物理子目录。P8 说明只补根本身 lstat 仍不完整：根的祖先是 junction 时，同样通行。子段 junction 和文件 symlink 反而正确返回 `-32602 reason=symlink`。

**要求修法**：从可信卷根到工作区根及文件全链条检查链接/reparse/别名风险；根本身也必须检查。不能用 `realpath(root)` 自行重新定义“允许的物理根”以放行链接根。不能证明根安全就 `-32602`。补根 junction、根祖先 junction、根 symlink 回归；任何案例不得调用写宿主。

### F2 / 阻断：sessionId 只是存档，发送前未验证会话一致性

**位置**：[index.js:305–327](<../packages/dsh-vscode-kit/src/index.js#L305-L327>)、[index.js:374–410](<../packages/dsh-vscode-kit/src/index.js#L374-L410>)、[grant.js:327–376](<../packages/dsh-vscode-kit/src/grant.js#L327-L376>)。违反 [契约:376 / 402](<../docs/协作编辑-钩子契约.md#L376-L402>)：session 一致性应由 DSH 发送前判。

授权保存 `sessionId`，但 writeGate/judgeGrant 都没有接收当前会话身份的参数，也不比较 record.sessionId。真实 TCP 输出：

```text
TCP authorized {result:{applied:true,...,saved:false,textLength:1},writeDelta:1}
TCP other session S2 using S1 grant
{result:{applied:true,...,saved:false,textLength:1},writeDelta:1}
```

复现调用为：先 `editing.grant({sessionId:'S1'})`，再 `request('vscode.applyEdit', {...params, sessionId:'S2'}, {sessionId:'S2'})`，携 S1 的 grant 仍写入。**这不是证明从外部猜到了随机凭证**，而是证明当前接口没有 S2/S1 的绑定判据：即使调用方明确声明 S2，也无人读取。默认允许 null 会话进一步说明它目前是 bearer grant，不是契约要求的会话授权。

**要求修法**：定义可信、不可由业务 params 自证的当前 session 上下文，发送前强制与保存的 sessionId 一致；缺失或不同均失败闭合。第三方不应负责复制内部 grant 字段。增加同窗口 S1→S2 越权、缺失 session、同 session 正常写入的独立测试。不能仅在扩展侧再加一份会话判断来补洞。

### F3 / 阻断：写目标仍由当前活跃连接选取，违反“授权连接按身份路由”

**位置**：[index.js:379–406](<../packages/dsh-vscode-kit/src/index.js#L379-L406>)、[index.js:125–142](<../packages/dsh-vscode-kit/src/index.js#L125-L142>)。契约 [§6.1.1:362–376](<../docs/协作编辑-钩子契约.md#L362-L376>) 明令写目标是保存的 grant.link，不是 `_activeLink()`。

现实现先 `_waitForEditor()` 选 argmax，再拿 grant 与所选连接比较。它**会拒绝**不匹配，因此未在该分支看到跨窗口实际写入，但正确的 A 授权会因 B 后连而失效式报错，绑定门变成“只许给当前活跃窗口写”的门。

实跑现有独立测试输出：

```text
✔ 目标漂移：grant 绑在 A 上、目标换成 B → grant-mismatch（提示去目标窗口确认）
```

这条测试 [editing-grant.test.js:567–595](<../packages/dsh-vscode-kit/test/editing-grant.test.js#L567-L595>) 明确把此行为锁成预期，正与契约不同。

**要求修法**：写请求先由可信 session 找到 grant 记录，以记录的 link 作唯一目标，检查其准入/版本/存活；读路径继续 active。A 有效、B 新连不应让 A 的合法写请求改选 B；A 消失只能失败，不能回落。相应修正上述测试预期。

### F4 / 阻断：七行判定不是逐行等价，外层还有抢跑判定

**位置**：[grant.js:334–356](<../packages/dsh-vscode-kit/src/grant.js#L334-L356>)、[grant.js:421–436](<../packages/dsh-vscode-kit/src/grant.js#L421-L436>)；契约 [①-c:392–402](<../docs/协作编辑-钩子契约.md#L392-L402>)。

1. 行 1 从“未带 grant”扩大成“id/epoch 任一形状不合法”。已知有效 id 的错误 epoch 应命中行 5；墓碑 id 的错误 epoch 应先命中行 3/4，而现在全被行 1 抢走。
2. extensionWriteGate 在 judgeGrant 前判 live link，从而在行 1/2/5 之前就能返回行 3/6。
3. 墓碑分支行 4 接受所有非 disconnected cause，超出契约明确列的 superseded/revoked。未知 cause 必须拒绝，但诊断不应擅自宣称符合七行原表。

实测：

```text
J active invalid epoch {ok:false,row:1,reason:"no-grant"}       # 应行5
J active missing epoch {ok:false,row:1,reason:"no-grant"}       # 已知id，不能抢到行1
J unknown missing epoch {ok:false,row:1,reason:"no-grant"}      # 应先行2
J disconnected grant (正常epoch) {ok:false,row:3,reason:"grant-generation-stale"}
J disconnected grant (epoch=bad) {ok:false,row:1,reason:"no-grant"}
J no-live no-grant {code:-32010,reason:"target-gone",row:3}     # 应先行1
J epoch mismatch + connection mismatch {ok:false,row:5,reason:"grant-generation-stale"}
WRAPPER 同样多因输入 {reason:"grant-generation-stale",row:6}  # 外层抢到行6
```

好的一面：核心函数只有一份，DSH 与扩展都 import 它，没有两端各抄一份。但“同一个函数”不抵消前置检查重新排序。

**要求修法**：严格按七行次序辨别；grant 对象存在后先查 id，epoch 类型/等值失配留到行 5，墓碑优先。连接存活检查应纳入规定顺序的状态/行，而非外围捷径。加多因同时命中的优先级测试，不能只逐个测单因。

### F5 / 阻断：notify / broadcast 漏掉写绑定门，发送前“零业务帧”不成立

**位置**：[index.js:432–440](<../packages/dsh-vscode-kit/src/index.js#L432-L440>)、[server.js:319–329](<../packages/dsh-vscode-kit/src/server.js#L319-L329>)；对照 [契约:210](<../docs/协作编辑-钩子契约.md#L210>) 与 [契约:309–311](<../docs/协作编辑-钩子契约.md#L309-L311>)。

request 有写门，notify 与 broadcast 只有版本/能力筛选。真实 TCP 连接在无有效 grant 时，调用后用同一 server→editor 流的 `bridge.ping` request 收回执作为 FIFO 栅栏，统计此前 `vscode.*` 入站帧：

```text
DSH notify no grant {writeDelta:0}
FIFO notify business delta 1 hostWrites 2
DSH broadcast no grant {result:1,writeDelta:0}
FIFO broadcast business delta 1 hostWrites 2
```

hostWrites 2 是前两次合法/跨会话写留下的累计数，本两项 writeDelta 都为 0。通知默认没有 token，因此当前扩展在协议鉴权就丢弃，**本次没有成功写入**；但调用者看不到失败、对端已收到业务帧，发送门的契约已被绕过。不能把扩展的第二道门当第一道门已存在的证明。

**要求修法**：所有写入类方法在 notify/broadcast 入口明确拒绝，要求用 request；不要默认添加 token 使其变成可执行写通知。安全覆盖要检查所有出站入口，以 FIFO 栅栏断言零业务帧。

## 3. 重要项

### F7 / 重要：未信任工作区在真实链路中被先报成未绑定

**位置**：[connector.js:248–257](<../packages/dsh-kit-bridge/src/connector.js#L248-L257>)、[capabilities.js:364–371](<../packages/dsh-kit-bridge/src/capabilities.js#L364-L371>)。

```text
TCP untrusted/no-grant {code:-32010,reason:"no-grant",writeDelta:0}
TCP untrusted/valid grant {code:-32006,writeDelta:0}
```

单独 dispatch 先信任，完整 connector 链路先 grant；二者诊断口径不一。没有发现未信任状态实际写入，但会把用户引向“重新绑定窗口”而不是“先信任工作区”。现有 [apply-edit.test.js:204–213](<../packages/dsh-kit-bridge/test/apply-edit.test.js#L204-L213>) 和 [456–485](<../packages/dsh-kit-bridge/test/apply-edit.test.js#L456-L485>) 分别锁了两种相反优先级。

**要求修法**：统一真实入口和直接 dispatch 的信任前置策略，在不把 grant 门移到 onRequest 后面的前提下，让未信任原因可稳定返回；或明确契约裁决双因优先级并给调用者可操作诊断，不能注释声称一律先信任、线上却相反。

### F8 / 重要：超行数范围没有检查，直接传给宿主

**位置**：[capabilities.js:59–88](<../packages/dsh-kit-bridge/src/capabilities.js#L59-L88>)、[capabilities.js:314–331](<../packages/dsh-kit-bridge/src/capabilities.js#L314-L331>)、[vscode-host.js:140–145](<../packages/dsh-kit-bridge/src/vscode-host.js#L140-L145>)。

```text
C zero / negative / fraction / end-before-start -> -32602, calls:0
C past-line-count (只有 one/two 两行，入口 line:999):
result.applied = true
host.range.start.line = host.range.end.line = 998
```

本轮没在真实 VS Code 测其如何规范化越界 range，因此不把“必然写到 EOF”当事实；已证明的是桥接层与适配层都未核对文档行列上界。写路径不能依赖编辑器内部自动夹取来决定落点。

**要求修法**：在 VS Code API 边界读取目标文档并拒绝越过行数/行长的范围；与版本/撤销复核一并保证写点前状态仍有效。新增真实适配器或真实宿主测试，不要让只记录参数的假 host 把越界当正常编辑。

### F9 / 重要：grant 投递是无回执通知，delivered:true 可是假成功

**位置**：[index.js:317–327](<../packages/dsh-vscode-kit/src/index.js#L317-L327>)、[protocol.js:202–210](<../packages/dsh-vscode-kit/src/protocol.js#L202-L210>)、[protocol.js:281–284](<../packages/dsh-vscode-kit/src/protocol.js#L281-L284>)。

构造真实 protocol.connect 的 write 抛 `Error('writer broken')`，onError 仅记录，作为已准入兼容 link：

```text
BROKEN WRITER GRANT {delivered:true,active:1}
```

send 把异常转 false，而 notify 丢掉 false，因此 grantEditing 的 try/catch 看不到失败，保留本地 active grant 并宣称送达。当前扩展没有 grant 仍会拒绝，不是直接放行洞；但违背“失败不能静默”和 grant 必须投递的承诺。[契约:372](<../docs/协作编辑-钩子契约.md#L372>) 写的是 grant request，当前实现却是通知。

**要求修法**：授权用 request 并等结构化确认后才标记 delivered；出错撤销临时本地记录，不自动重发。保留连接 token 的显式携带规则。仅让 notify 返回布尔也不能证明扩展已存档。

### 4.4 坐标转换

[capabilities.js:52–56](<../packages/dsh-kit-bridge/src/capabilities.js#L52-L56>) 是 applyEdit 的唯一 1→0 转换；[vscode-host.js:142–144](<../packages/dsh-kit-bridge/src/vscode-host.js#L142-L144>) 原样构造 Position/Range，没有第二次减法。`line:0`、负数、非整数、end<start 均实测 `-32602 calls:0`；超行数不拒，见 F8。

按整个文件搜索，确有另两处 `- 1`：[capabilities.js:41](<../packages/dsh-kit-bridge/src/capabilities.js#L41>) 是原有 openFile 转换，[vscode-host.js:49](<../packages/dsh-kit-bridge/src/vscode-host.js#L49>) 是原有 openFile 的 lineCount 边界。它们不在 applyEdit 链路，不能因为“别处也有 -1”就误报二次转换。

### 4.5 saved:false 不可伪造成 saved:true 成功

独立构造 kit 对端 request 返回 `{applied:true,file:'D:/fake/a.txt',saved:true,textLength:1}`，使用真实 VscodeKit facade 与有效 grant：

```text

 code:-32009,method:"vscode.applyEdit",
 got:{type:"object",keys:["applied","file","saved","textLength"],at:"saved",value:"boolean"},
 expected:"object with applied:boolean, file:string(non-empty), saved===false, textLength:int>=0"
}
```

[response-contract.js:168–174](<../packages/dsh-vscode-kit/src/response-contract.js#L168-L174>) 确为 `v === false`，不是普通 boolean。发送后的验证在 [index.js:410–420](<../packages/dsh-vscode-kit/src/index.js#L410-L420>)。此项通过；它只能识别响应声明违约，不能证明恶意对端没有保存，也不能撤销已发生的落点。

### 4.6 拒绝零业务帧：采用 FIFO 栅栏，不用固定 sleep 断言

真实 connector socket 的 data 监听记录每条 JSON 帧；每次 facade 拒绝后，从同一 DSH link 发 `bridge.ping` request，等编辑器回执，再统计此前 `vscode.*` 帧增量。协议调度对本探针的同步 grant 和拒绝逻辑有序；没有以“等 50ms 没看见”充当栅栏。

```text
TCP DSH missing -> -32010 no-grant; FIFO rejected business delta 0
TCP DSH shape   -> -32010 no-grant; FIFO rejected business delta 0
TCP DSH unknown -> -32010 no-grant; FIFO rejected business delta 0
TCP DSH reconnect old grant -> -32010 target-gone; FIFO delta 0
notify no-grant -> FIFO delta 1
broadcast no-grant -> FIFO delta 1
```

因此 request 门通过，所有入口总论不通过。扩展收到请求后回错误帧不算发起新的 vscode 业务操作；[protocol.js:379–389](<../packages/dsh-vscode-kit/src/protocol.js#L379-L389>) 回错是正确的失败闭合，不能为了“零帧”把错误帧也吞掉。

## 7. 非阻断观察 / 建议

1. [grant.js:139–154](<../packages/dsh-vscode-kit/src/grant.js#L139-L154>) 由 DSH 唯一生成随机 id/epoch，扩展 adopt 只保存；没有拿 connSeq 冒充授权纪元。这个方向正确，应保留。
2. [grant.js:284–299](<../packages/dsh-vscode-kit/src/grant.js#L284-L299>) 墓碑移除 link 强引用且限制32条，淘汰后拒绝为 no-grant；属于合理的诊断/资源边界。
3. [capabilities.js:332](<../packages/dsh-kit-bridge/src/capabilities.js#L332>) 的 `outcome?.applied !== false` 将畸形宿主结果视为成功；真实适配器目前保证 boolean，尚未复现生产错误，但建议用严格 `=== true` 或验证宿主结果，避免替身/后续适配器异常变成假成功。
4. 不建议把所有 Windows 大小写别名当越界：合法内部同文件大小写差异放行本身不是安全洞；如产品确实要求“任何别名都拒”，应明定规范形与短名策略，勿把测试口号当成已存在的规则。

## 8. 疑问与验证边界

- **真实 VS Code 未验证**：本次没有打开/重启编辑器或改用户缓冲区；根 junction 到外部路径的结论由真实 FS 守卫 + 写宿主调用参数证明，API 适配器对传入路径直接 Uri.file + applyEdit。修复后仍需真机验证范围边界、根 URI 是否保留链接、缓冲区脏标记及不主动保存；不能以现有13项 E2E替代。
- **短名文件覆盖有限**：确实探测到现有 C: 短名目录并被拒，但没有获取项目 D: 真实短名文件，未覆盖“工作区根用短名打开”和全部 reparse 类型。该部分不能标成完整通过；不需要等它验证完才拒绝 F1 已证实的链接根漏洞。
- **TOCTOU**：lstat/realpath 与编辑器实际读写之间没有原子文件身份绑定，若威胁模型包含同用户进程并发替换目录，还需额外设计并测试。这是范围内路径守卫的剩余疑问，本次未复现竞态，不将其冒充已有绕过证据。
- **session 信任源待定义**：目前只见调用者传入可空 sessionId，没有真实会话上下文接入。F2修复不能靠新增一个可随意伪造的 params.sessionId 比较就宣称完成。

## 9. 交接结论

**reject，不批准把这道门作为完整写入授权边界投入使用。**

可保留的已证实结果：普通 request 无授权拒绝；同窗口覆盖/显式撤销拒绝；断开重连后旧 grant 在两端失效；saved:true 被 facade 判 -32009；applyEdit 坐标没有二次转换；两处核心门的变异能让现有测试变红。

必须修复的核心：根/根祖先链接拒绝、多根禁写、真实 session 一致性、按授权连接选写目标、唯一七行顺序、所有写出站入口闭合。其后解决信任诊断优先级、超行数和授权送达假成功，并用 FIFO/真机适配层测试重新验收。
