**署名**：后端架构师
**项目**：`D:/code-workspace/projects/dsh-vscode-dev`（`main` @ `8be5d69`）

**结论一句话**：**归属判定 = 不可靠；结论 = NO-GO**。当前协议层对「这段文本是谁写的」**没有任何可观测锚点**（写入请求不带版本/内容指纹，能力清单里连读文本的能力都没有），真机上人工键入的文本会被下一次 DSH 写入**静默吞掉**且上报 `applied:true`，没有任何错误码或提示。保存边界目前**只是因为"根本没有保存能力"才安全**，不是因为归属判定成立。

| 问题 | 判定 | 依据 |
|---|---|---|

## 1. 结论先行：保存边界到底划在哪

**当前事实边界（不是设计边界）**：

1. **DSH 只能改缓冲区，永不落盘。** `vscode.applyEdit` 的能力实现里没有任何 `save()` 调用（`packages/dsh-kit-bridge/src/vscode-host.js:190-205`，`applyEditText` 只构造 `WorkspaceEdit` 并 `await vscode.workspace.applyEdit(edit)`），返回值 `saved:false` 是硬编码字面量（`packages/dsh-kit-bridge/src/capabilities.js:482`）。
2. **所以"不会悄悄覆盖磁盘"成立** —— 但成立的**原因**是「没有保存能力」，不是「能判归属」。这两件事一旦被混为一谈，下一个卡（落盘）就会带着一个虚假的安全感上线。
3. **缓冲区是共享的、无人记账的。** 人工键入与 DSH 写入改的是同一个内存 `document`；系统里没有任何一方记录「上次我看到的内容是什么」，因此写入永远是「按坐标盲替换」。

这就是 NO-GO 的那条线：**在能判归属之前，不能给 DSH 任何自动保存能力**。理由见 §5。否则 T4 之后紧接着做落盘，就是「DSH 用过期坐标把人工未保存的改动写进磁盘」——从内存可撤销变成磁盘不可撤销。

## 2. 机制事实（为什么判不可靠 —— 代码级根因）

### 2.1 写入请求里没有任何「我基于哪一版写的」

`packages/dsh-kit-bridge/src/capabilities.js:462`：

```js
const outcome = await host.applyEditText(writeTarget, toApiRange(range), text)
```

交给宿主的全部信息 = **路径 + 坐标 + 文本**。没有 `document.version`、没有内容哈希、没有 etag、没有「我以为这里是什么」的期望值。`packages/dsh-kit-bridge/src/vscode-host.js:196` 之后直接 `vscode.workspace.applyEdit(edit)` —— VS Code 按坐标替换，**坐标已漂移也照样接受**。

### 2.2 写前的唯一观测只用于「越界」，不与历史比对

`packages/dsh-kit-bridge/src/capabilities.js:440` 读了一次文档形状：

```js
const shape = await readDocumentShape(host, real, [range.start.line, range.end.line], method)
assertRangeInBounds(shape, range, method)
```

`readDocumentShape` 返回 `{lineCount, lineLengths}`（`packages/dsh-kit-bridge/src/vscode-host.js` 同名函数），**不含任何文本**。它只回答「这个坐标在不在文档里」，不回答「这个坐标上的字还是不是我上次看到的字」。所以它能拦住「越界写」，拦不住「写到别人的字上」。

### 2.3 连读都读不到：能力清单里没有文本读取

`packages/dsh-kit-bridge/src/capabilities.js:24-30` 的全部能力：

```
vscode.openFile / getSelection / getDiagnostics / listOpenEditors / applyEdit
```

真机探针（`work/t4-fixture/t4-driver.log`，r1/r2/r3）实测：

```
{"id":"r2","ok":false,"error":{"code":-32005,"message":"editor does not advertise capability for \"vscode.getDocumentText\""}}
{"id":"r1","ok":false,"error":{"code":-32005,"message":"editor does not advertise capability for \"vscode.readFile\""}}
{"id":"r3","ok":false,"error":{"code":-32005,"message":"editor does not advertise capability for \"vscode.save\""}}
```

**归属判定需要两件事：知道「现在是什么」+ 知道「上次我写的是什么」。当前实现两件都没有。** 这不是「参数再传一个字段」能补的洞：`applyEdit` 出站路径上根本不存在可以携带期望内容的字段，宿主机也没有能力把当前文本回给 DSH。

### 2.4 与基础门的关系（说明这不是授权问题）

写入的会话绑定门（`packages/dsh-vscode-kit/src/index.js:599-650`，`isWriteMethod` → `_writeGate`，`opts.sessionId` 参与判定）在真机上**工作正常**：不带 grant 的写入被 `-32010 no-grant` 拦住，带 grant 的写入放行。**授权门解决的是「谁有权写」，T4 问的是「写到的这块字是谁的」——门做好了一点都不帮助归属判定。**

## 4. 四个实验

### 实验 1｜归属能否可靠判定 → **不可靠**

**做法**：DSH 写第 2 行 → 人工在第 4 行末尾键入 → 再让 DSH 写第 4 行。

1. DSH `applyEdit` line2 `line2`→`LINE2-BY-DSH`：`{"applied":true,"saved":false,"textLength":12}`
   证据图 `evidence/01-dsh-wrote-line2-dirty.png`（第 2 行已是 DSH 文本，页签带未保存圆点）。
2. 人工：光标点第 4 行末 → `End` → 键入 `" HUMAN-TYPED-A"`，状态栏 `行4, 列20`。
   证据图 `evidence/02-human-typed-line4.png`（第 4 行 = `line4 HUMAN-TYPED-A`）。
3. DSH 再写第 4 行（整行）：`{"applied":true,"saved":false,"textLength":18}` → 第 4 行变成 `LINE4-DSH-TAKEOVER`，` HUMAN-TYPED-A` **消失**。
   证据图 `evidence/03-human-text-gone-line4.png`（`行4, 列7`，人工 14 个字符无影）。

**结论**：`applied:true` 之外**没有任何字段**能表达「我可能刚覆盖了别人的字」。第 3 步之前 DSH 无从知道缓冲区已被人工改过（§2.3：连读文本都做不到）。**归属判定：不可靠。**

> 这个实验的保留意见：第 3 步的替换范围覆盖到人工文本，才吃掉它（按列替换只会吃到范围内）—— 所以它是"能覆盖"，不是"一定会覆盖"。**更诚实的杀伤在实验 2b：DSH 完全不需要知道人工写了什么，坐标漂移就够。**

### 实验 2｜交错改动（DSH → 人工 → DSH）→ **人工那段丢了，NO-GO**

**2a**：见上（同一行内的追加被整行替换覆盖）。

**2b（纯坐标漂移，DSH 对人工内容零知情）**：
1. 现态：1 `line1` / 2 `LINE2-BY-DSH` / 3 `line3` / 4 `LINE4-DSH-TAKEOVER` / 5 `line5`。
2. 人工：光标第 2 行末 → `Enter` → 键入 `HUMAN-INJECTED` → 变成第 3 行，`line3` 下移到第 4 行。
   证据图 `evidence/04-human-injected-line3.png`。
3. DSH 仍按它自己的旧视图以为「第 3 行 = `line3`」，发 `range line3 col1..15 = "LINE3-BY-DSH"`：
   `{"applied":true,"saved":false,"textLength":12}`。
   结果：第 3 行（**人工那行**）被换成 `LINE3-BY-DSH`，`HUMAN-INJECTED` 消失，而它真正想改的 `line3` 还在第 4 行**一点没动**。
   证据图 `evidence/05-drift-ate-human-line3.png`。

**结论**：一次**完全无意**的写入，吃掉了一整行人工内容，并且写到了错误的目标上；`applied:true`、无警告、无错误码。按卡的判定标准：**丢了 = 直接 NO-GO**。

### 实验 3｜未保存缓冲区 vs 磁盘 → **磁盘没变（逐字节/mtime 双重证据）**

全程 `alpha.txt` **3 次写入 + 2 次人工编辑 + 1 次丢弃**，磁盘：

```
sha256  77165950de0a3f78fa118b964335e26deb3c895a7de50035bb5f8505a19f19cf   （= 实验前同一值）
size    30
mtime   1792673734（= 夹具创建时刻，全程未变）
```

`beta.txt` 1 次 DSH 写入后同样：`sha256 76843515…`、`size 15`、`mtime 1792673734` 未变。

第三次事实（这条比 mtime 更狠）：对仍带未保存改动的 `alpha.txt` 执行「关页签 → **不保存**」后再 `openFile`，`listEditors` 报 `{"isDirty":false}` —— 缓冲区回到磁盘内容 `line1..line5`，**DSH 的三次写入与人工的键入一起蒸发**，磁盘从头到尾没变。

**结论**：`saved:false` 是真的不落盘（真机 + 单测双证）。**同时这也意味着：未保存的 DSH 写入不可核对、不可恢复，并且它和人工改动共用同一条"丢失"通道。**（本报告不会说"磁盘写入已验证通过"之类的话——落盘能力根本不存在。）

### 实验 4｜混合归属文件 → **既不自动保存、也不停写、也不报错**

1. 同一文件 `alpha.txt` 里既有 DSH 改动（`LINE3-BY-DSH` 等）又有人工改动残留/已被覆盖 → 继续写入：`applied:true`（实验 2b）。
2. 「不许自动保存」成立，但原因是**没有保存能力**（`vscode.save` 返回 `-32005`，见 §2.3）。
3. 「其他文件仍可继续写」：`beta.txt` 写入 `{"applied":true,...}`（e4b）。
4. 「归属未知 → 停该文件」：**未实现**。能力层没有任何 per-file 状态；`listOpenEditors` 只给 `isDirty` 布尔（`e4c`/`v2`），它只能说「有人改过」，**说不了"是谁改的"**——而 alpha 的 `isDirty:true` 恰恰是 DSH 与人工共同造成的，无法拆开。

**结论**：「归属未知」这个状态在当前实现里**不存在**，所以也谈不上「停文件」。这既是 NO-GO 的后果，也是它暂时"看起来安全"的假象来源。

## 5. 最小可行收窄方案（**只写方案，本卡不实现**）

按代价从低到高，三档；建议 **A 档 + B 档的一部分**，都不要一步跳到「自动保存」。

### A 档（最小、可当天做）：**只允许在「干净的保存态」写入**
- 写前要求 `document.isDirty === false`（`listOpenEditors` 已经能取到 `isDirty`，无需新能力）；`isDirty:true` → 拒写 `-32011 document-dirty`，**由 DSH 侧把决定交回人**。
- 语义诚实：能证明的是「没有未保存改动」，**不能**证明「没有别人在编辑」——所以报告/错误码里必须写清这是**保守拒绝**，不是归属判定。
- 代价极低；能挡住实验 2a/2b 这一整类（人工改动必然是脏态）。
- 遗留：**保存态下人工刚改完又保存**，DSH 仍会按自己的旧视图写 —— 见 B 档。

### B 档（真正的归属锚点）：**写入必须携带版本前置条件**
- 需要新增能力：`vscode.getDocumentVersion`（或让 `openFile`/`readDocumentShape` 回 `version` + 目标行文本摘要），并让 `applyEdit` 接受 `expectedVersion` / `expectedText`；不一致 → `-32012 conflict`，**不写**。
- 这是唯一能真正回答「我基于哪一版写的」的路径，也是所有成熟协作系统（LSP `TextDocument.version`、Yjs/OT、`vscode.workspace.applyEdit` 之上的 diff 层）的共同做法。
- 代价：能力清单 +1、协议参数形状变更、两侧单测与 E2E 都要动 ——**属于新卡，不属于 T4**。

### C 档（兜底，可与 A 同时）：**整文件快照语义**
- DSH 只允许「整文件替换」（先读全文、基于全文重写），把「局部坐标盲写」这个最危险的形态从协议层去掉；冲突检测退化成「全文是否与我读到的一致」。
- 好处：坐标漂移这一类彻底消失（实验 2b 不可能发生）；坏处：大文件代价高，且需要读文本能力（§2.3 也没有）。
- 适合作为 B 档之前的中期形态。

**共同红线**：在上述任一档落地之前，**不要给 DSH 增加保存能力**。当前"不落盘"是唯一可靠的护栏。

## 6. 人工改动待确认时，给用户的分析建议（文字层面，不实现 UI）

如果将来要把「可能有人改过，要不要继续写」交回给人（A 档的必然产物），建议的措辞与信息结构：

1. **先说是谁的问题，不说结论**：「这个文件在 DSH 上次读取之后被改动过。我无法判断改动来自你还是来自我之前的写入。」——**不要**说「检测到你改了」（我们并没有检测到"你"）。
2. **给出可核对的坐标与文本，不给出猜测**：「第 3 行：我上次看到的是 `line3`，现在是 `HUMAN-INJECTED`。」坐标 + 两侧原文是唯一可核验的东西；任何"应该是""大概是"都不要写。
3. **三个明确可选的处置，不许隐式默认**：
   - **放弃本次写入**（默认建议，尤其当文件 `isDirty`）；
   - **以当前内容为基准重算**（DSH 重新读、重新给 diff）；
   - **覆盖**（必须显式、必须把被覆盖的原文同时列出来）。
4. **说明后果的不可逆性**：「覆盖之后，这段文本只能靠编辑器的撤销历史找回；如果先保存再覆盖，连撤销也找不回。」——这正是"必须先判归属、后做落盘"的原因。
5. **说明检测能力的边界（诚实优先）**：「我只能看到文件当前是否未保存、以及我想改的那几行现在长什么样；我看不到编辑历史，也分不清两次改动的时间先后。」这句建议固定出现在任何"归属提示"里，避免用户以为系统在做它做不到的事。
6. **批量场景要降级**：一次涉及多个文件时，不要逐个弹窗轰炸；先汇总「N 个文件疑似有人改动（其中 M 个未保存）」，只对用户点开的那个给细节。
