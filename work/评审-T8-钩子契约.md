### R4 — high — “调用失败必可见”未覆盖成功外形的错误结果，示例也未观察 Promise

- 位置：[草案:46–47](<D:/code-workspace/projects/dsh-vscode-dev/docs/协作编辑-钩子契约.md#L46-L47>)、[草案:105–120](<D:/code-workspace/projects/dsh-vscode-dev/docs/协作编辑-钩子契约.md#L105-L120>)。
- 问题：request 并不保证所有协议失败都 reject。响应只按 id 且无 method 识别；有匹配 id、却既无 result 又无 error 的 JSON 对象会让 pending Promise resolve(undefined)，而非结构化失败。同名方法返回错误形状也没有 facade 校验。
- 证据：[protocol:240–251](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/protocol.js#L240-L251>)直接 `entry.resolve(msg.result)`；[index:155–160](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/index.js#L155-L160>)原样转发。静态可达示例为匹配 id 的 `{"id":1}`（id 必须对应 pending）；这不是本轮已跑的实验。
- 另外：草案最小示例不 await/return/catch openFile。即便返回 rejected BridgeError，调用方示例也没有把它转成人可见结果，可能只留下 unhandled rejection；真实 demo 则 await 并转换成 `{ok:false, code, message}`。
- 必改：将无效/缺失响应形状及业务返回结构不兼容列入失败契约，要求在责任边界校验或明确现阶段无法保证；示例必须 await 并呈现/传播失败。notify 明确仅 best-effort，不能当动作成功信号。不能以“用了 request”代替“确认业务成功”。
- 影响边界：正常官方 handler 的抛错能被传回；此 finding 针对坏响应、错配对端及消费者示例，不声称正常四能力错误会一律丢失。

## 3. 五个判据逐条结论

### 3.1 单一钩子是否真的够

**消费现有能力：够；第三方独立新增 VS Code 能力：不够。**
一个服务名足以承载 transport 与通用 request，无需额外服务名；但是固定桥端 dispatcher 不会凭 inject 自动获得新 handler。
R1 的代码与三步规定构成直接证据。最小接入和最小扩展是不同成本，demo 只证明前者。
入站回调也仍是 [index:370–390](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/index.js#L370-L390>)的 ping/hello 固定 switch；不过第三方新增出站编辑能力的首要障碍不是它，而是 VS Code 端实现/发布。

### 3.2 版本兼容风险

**核验成立：当前业务源码无协议版本比较门；但草案关于错配后的具体结果与安全性推导过强。**
检索 `protocolVersion|PROTOCOL_VERSION|ERR.DECLINED` 及全部 version 相关标识后，逐读所有 9 个 src 文件；版本字段只有声明、发送、导出或诊断，不见协议兼容比较。
测试中存在版本相等断言，所以“全仓零版本比较”若包括测试字面含义并不准确；正确范围是“生产 src 无兼容拒绝分支”。
hello/发现文件没有读取版本的路径；缺 protocolVersion 是被忽略，不是实现了“按 v1 解析”的协商分支。
“静默放行”可能显式失败、超时，也可能同名方法成功但语义错；并非所有错配都会立即 -32005。
**应升级为契约冻结 blocker（R2）**；当前四能力的真实错配复现、事故概率无法判定，未冒充动态验证。

### 3.3 失败态是否可静默

**不能保证全部可见，存在静默成功路径。**
正常 handler 抛错经 [protocol:293–303](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/protocol.js#L293-L303>)转为 error，超时/断线通常 reject，草案对此大体正确。
但缺 result/error 的响应 resolve(undefined) 是 R4 的明确反例；版本同名语义错也不受错误码保护。
notify 在 [protocol:198–202](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/protocol.js#L198-L202>)忽略 send 返回值；普通业务通知不带 token，[connector:144](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-kit-bridge/src/connector.js#L144>)会拒绝非 hello 通知，发送方仍无回执。草案禁止用它执行动作是正确的。
草案引用 withToken 是底层 API，facade notify 只有两个参数，无法透传该选项，不能向第三方暗示可用这一补救。
waitReady(false) 是明确的失败值而非异常；且它只等监听，不等编辑器或重新授权，断线后重新调用并不等于重新连接成功。

### 3.4 安全边界能否被绕过

**当前只读/准只读通道有准入防线，但并无可证明的协作编辑安全边界。承认缺口是诚实，拿它延后硬门则不可接受。**
[server:155–164](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/server.js#L155-L164>)逐请求/通知 token 准入，[server:243–246](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/server.js#L243-L246>)广播只遍历 trusted；连接和编辑 grant 必须分开。
[capabilities:72–77](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-kit-bridge/src/capabilities.js#L72-L77>)只有 workspace trust；[vscode-host:34–42](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-kit-bridge/src/vscode-host.js#L34-L42>)做 normalize/resolve，[vscode-host:129](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-kit-bridge/src/vscode-host.js#L129>)的 stat 跟随链接，均不是物理根与 reparse point 防护证明。
源码未见 grant、重连撤销 epoch、归属记录或单文件冻结；目前没有写能力，不能把这些记作已落地，也不能凭文本保证后续新增写方法不可绕过。
合理分层是 facade 保留一个入口，受控路由身份与 grant 执行边界在内部协作；路径/归属在真实操作层守门，generic request 不得免检。见 R3。
另：0600 是代码申请的 mode，不是 Windows ACL 已验证保证；[discovery:49–51](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/discovery.js#L49-L51>)明确 best effort。此处只作为证据边界，不另列 finding。
既有[先例调研:209–224](<D:/code-workspace/projects/dsh-vscode-dev/docs/先例调研-鉴权放在哪一层.md#L209-L224>)“只验一次”的历史概括与现代码不一致，本轮以现代码为准，未将旧调研冒充新上游验证。
