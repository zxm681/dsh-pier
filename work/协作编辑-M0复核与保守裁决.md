## 5. 审计新发现如何提高未来写权门槛

`docs/威胁模型-通道可达面.md:9-18,26-43`：服务是 loopback 裸 TCP/ndjson；常规 WebSocket 握手不能直接变成功通道，但**HTTP POST 正文含合法 ndjson 与正确测试 token 的旧隔离抽样 `dispatched=1`**；并未证明恶意网页可取得 token 或跨浏览器端到端可利用，亦不得宣称浏览器完全不可达/DNS rebinding 绝对不成立。发现文件明文 token、Windows chmod/DACL 未证、未准入 socket 可能收到 `broadcast`（当前生产敏感广播未证）及连接资源边界，均是条件风险而非已证事故。今后写许可必须独立于 token，绑定经人可见授权的会话/窗口/物理根/epoch，逐请求鉴权与授权路由，失信任/断连清除；不要让发现文件 token、网页、未准入连接或最后一条 link 自动取得写权。先复核 Windows ACL、广播已准入过滤、HTTP 正文注入及 DNS rebinding 条件链、速率/资源边界；在隔离夹具使用**测试 token**和负例，真实 VS Code 宿主验证撤销/applyEdit 竞态、跨窗口错路由、路径替换和缓冲区版本/hash CAS，变异测试要证明守门；任何失败闭合无法证明则新 T3 继续 NO-GO。未来改 HTTP/WS 入口须另立 Host/Origin/CSRF/PNA 评审，不沿用裸 TCP 推断。
