## 3. F1–F5 逐条闭合判定

### F1【上轮阻断】判定绑到「这条连接」上 → **闭合**
逐条核实现作者自述（全部在代码里成立，不是我采信自述）：
1. `ctx.link` 落位：`packages/dsh-vscode-kit/src/protocol.js:333`
   `const ctx = { id: msg.id, token: msg.token, link: self }`；`self` 在 `protocol.js:394`
   起名、`editor: null`（`protocol.js:404`）是**每连接一份**的身份槽。✔
2. hello 写入连接：`packages/dsh-vscode-kit/src/index.js:559` `msgCtx.link.editor = editor`，
   紧接着 `kit._notifyHello(msgCtx.link)`；`msgCtx` 由 `index.js:533`
   `function handleInbound(method, params, msgCtx)` 接收、`index.js:473` `onRequest: handleInbound`
   由 server 透传（`server.js:150`）。✔ 真到了没有 link 的分支，只 `log('warn')` 不写身份
   ⇒ 该连接「版本未知」⇒ 业务方法被门拒（fail-closed，不会误放行），处理正确。
3. `lastEditor` 只读 getter：`index.js:121` `get lastEditor() { return this._activeLink()?.editor ?? null }`；
   `request()` 里已删掉 `kit.lastEditor = null`（原 `index.js:426` 一带），构造器里也没有该槽。✔
4. `_waitForHello(link, waitMs)`（`index.js:173`）只认**传进来的那条**：waiter 用
   `if (who === link) finish(true)` 比对，其他连接的 hello 不能给它解围。✔
5. `snapshot()` 同源：`index.js:322` `const editor = this.lastEditor` → `protocolCompatible`
   （`index.js:331`）/`protocolReason`/`lastEditor` 三字段都从这一份取。✔
6. `link.closed` 跳过：`index.js:107` `if (link.closed === true) continue`（`closed` 由
   `protocol.js:406` 的 getter 暴露）。D 场景靠它回退到**另一条**而不是继续选死连接。✔

「能否构造出目标与背书仍不同源的新路径」—— 我按五种形态找，没有找到：
- 门与发包**共用同一个局部 `link`**：`index.js:285-291`
  （`await this._waitForHello(link, …)` → `_assertProtocolCompatible(method, link)` →
  `link.request(...)`），不存在「判的是 A、发的是 B」的窗口。
- A 已 hello → B 连上未 hello → 请求发到 B：读的是 **B 的** `editor`（null）→ `-32008`
  （这正是回归①，见 §5 变异第一条）。
- B 是目标、A 后 hello 覆盖全局槽：**全局槽已不存在**，hello 只写 `msgCtx.link.editor`，
  A 的背书在结构上无法落到 B（探针 B 实测 `-32008`）。
- 目标回退：`link.closed`/`socket.destroyed` 双重跳过（探针 D `-32008`）。

  （`index.js:97` 起遍历 `this.server.trusted`）⇒ 自证清白也换不来收包资格，方向是收紧的。
- 扩展侧：`peer` 仍是「每条连接一份」语义（`connector.js:222` `attach()` 里 `peer = pendingPeer()`），
  单 socket 模型下「目标」与「背书」是同一条，见「非阻塞提醒 N3」的唯一理论窗口。
