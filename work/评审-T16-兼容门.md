## 4. findings

### F1 —【阻断】版本判定绑在全局 `lastEditor` 上，目标切换时 fail-open：不兼容对端照样收到业务请求
**位置**：`packages/dsh-vscode-kit/src/index.js:175-196`（`_assertProtocolCompatible` 读 `this.lastEditor`）、`index.js:468-500`（hello 无条件覆盖同一个槽）、`index.js:427-431`（准入清空）
**问题**：契约要求「只认这条连接的 hello」，实现是「整个 kit 一份最后 hello」。`_activeLink()` 挑的是 `connSeq` 最大的活连接，而 `lastEditor` 记的是最后一次 hello —— 两者在目标切换/交错时不是同一条连接。探针实测两种形态都成立：

```
B. 目标=B(ptv=2)，但最后一次 hello 来自 A(ptv=1)
   → code=null ok={"done":"vscode.getSelection"} lastEditorClient=A B收到业务帧增量=1 A收到业务帧增量=0

D. B(v2) 先连、A(v1) 后连并断开 → 目标回退到不兼容的 B
   → code=null ok={"done":"vscode.getSelection"} lastEditorClient=A-v1 protocolCompatible=true B收到业务帧增量=1
```

D 是**现实场景**（两个 VS Code 窗口，新版先连、旧版后连，旧版关掉后目标回退到新版的 v2 扩展）：业务请求被发给声明 ptv=2 的对端，`request()` **正常返回**，`snapshot().protocolCompatible` 还报 `true`。这正是「宁可 fail-closed」要防的形态，且 `index.js:426` 的注释自述「兼容门只认这条连接的 hello」——注释与实现不符。
**必须怎么改**：把判定挂到连接上，而不是 kit 上。
1. `packages/dsh-vscode-kit/src/protocol.js:327` 的 ctx 增加 link 引用（`connect()` 内部可拿到自身，如 `const ctx = { id, token, link: self }`；或在 `server.js:148-152` 传 `onRequest` 时绑定 `link`）。
2. hello 处理（`index.js:468-500`）写 `msgCtx.link.editor = {...}`（挂在 link 对象上，随连接回收），不再写全局 `lastEditor`；`lastEditor` 若要保留仅供诊断，必须注明「非判据」。
3. 门改为读目标连接的判定：`const link = this._activeLink(); const editor = link?.editor`；`_waitForHello` 同样只等**目标连接**的 hello，而不是任意一条。
4. `snapshot().protocolCompatible` 用同一来源，否则诊断会与真实放行结果矛盾。
5. 补两条回归（用我探针 B/D 的场景）：① 目标连接不兼容 + 另一条兼容连接后 hello → 仍 -32008；② 目标回退到不兼容连接 → -32008。

### F2 —【重要】`notify()` 完全绕过版本门（也没有能力预检），契约「没有例外」被公开 API 绕过
**位置**：`packages/dsh-vscode-kit/src/index.js:251-256`（facade 暴露于 `index.js:357-361`）
**问题**：门只加在 `request()`。实测：

```
C. 不兼容时 notify() 业务方法
   → threw=null 对端收到业务帧增量=1
C2. 同场景 request() 对照
   → code=-32008
```

同一场景下 `request()` 拒、`notify()` 放行且对端真的收到业务帧。契约 §4.1 写的是「不得执行任何业务能力调用，没有例外」；一个单向通知也是业务能力调用。当前仓库内无业务 `notify` 调用方，所以是潜在缺口而不是现网漏洞——但它是**公开 facade**，任何人都能这么绕。
**必须怎么改**：`notify()` 里同样调用 `this._assertProtocolCompatible(method)`（放在 `_activeLink()` 之后、`link.notify()` 之前）；若认定 `notify` 只允许协议层使用，则直接拒绝非 `bridge.*` 的 `notify`，把「单向业务通知」明确为不支持。顺手把能力预检也覆盖上（现在 `notify('vscode.openFile')` 连能力降级都不过）。

### F3 —【建议】扩展侧的入站门在 `onRequest` 自定义钩子**之后**，注入点可绕过门
**位置**：`packages/dsh-kit-bridge/src/connector.js:167-177`
**问题**：`handleInbound` 先跑 `inbound[method]` 与 `deps.onRequest(method, params, ctx)`，`custom !== undefined` 就直接返回，门在后面。`deps.onRequest` 的文档写着「测试/扩展用」（`connector.js:35`），将来有人用这个注入点挂业务方法，就绕过兼容门，而门上方的注释还写着「放在 dispatch 之前」。
**必须怎么改**：把门提到自定义钩子之前（协议层 `bridge.*` 仍豁免），或在校验里显式断言自定义钩子只处理 `bridge.*`、其余一律 `throw`。当前无生产调用方，故列为建议。

### F4 —【建议】`incompatible` 状态没有 `reason`，状态栏只说「原因 无」
**位置**：`packages/dsh-kit-bridge/src/connector.js:143-148`（setState patch 只带 `error`）、`packages/dsh-kit-bridge/src/extension.js:177-181`
**问题**：`showStatus` 用 `s.reason ?? '无'`，而 `incompatible` 的 patch 里没有 `reason`，用户在状态栏看不到「协议版本不兼容」，明细只在输出面板日志里。这类「不可用但不告诉你为什么」正是排障成本最高的形态。
**必须怎么改**：patch 里加 `reason: 'protocol-incompatible'`（或让 showStatus 在 `state.state === 'incompatible'` 时读 `s.error?.message`）。

### F5 —【建议】`onEditorConnected()` 是死代码，本次又往里加了逻辑
**位置**：`packages/dsh-vscode-kit/src/index.js:573`
**问题**：全仓 grep 只有定义、**零调用方**；本次改动在其中新增 `kit.lastEditor = null`，与 `apply()` 内 `onAuthorized` 重复维护同一份状态。将来若有人接上它，两处清空/唤醒的时序会互相干扰。
**必须怎么改**：删除该导出，或接进 `onConnected` 并由测试覆盖；不要保留「两份看起来都对」的状态写入口。
