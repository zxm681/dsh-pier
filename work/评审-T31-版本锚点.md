### B1｜版本检查与写入不原子，旧锚点仍能吃掉人工新行

**位置**：[capabilities.js:696–749](../packages/dsh-kit-bridge/src/capabilities.js#L696-L749)、[vscode-host.js:234–246](../packages/dsh-kit-bridge/src/vscode-host.js#L234-L246)。

3. 740 行重新检查了 grant，747 行重新检查了路径，**没有重新检查文档版本/目标文本**。
4. 749 行只把路径、range、text 交给宿主；宿主不接收 `expectedVersion`，239–240 行按当前坐标生成并提交 WorkspaceEdit。

因此锚点只证明「较早一次读取的版本匹配」，不证明「实际写入时仍匹配」。即使宿主自己为 WorkspaceEdit 捕获当前版本，那也是**提交时的新版本**，并非请求携带的旧版本。

- 初始 v1：`line1 / line2 / line3`；请求基于 v1 准备替换第 3 行。
- 版本比对通过后，在读取范围形状的异步窗口中模拟人工插入第 3 行 `HUMAN`，真实版本改成 v2，原 `line3` 下移。
- 写入仍成功，人工新行变成 `DSH!!`，原 `line3` 保留在下一行——正是 T4 实验 2b 的错误落点。

- `expectedRangeText` 分支：请求携带旧文本 `line3`；范围读取先取得旧文本快照，再在异步返回前插入人工行。文本比对仍通过，v1 请求在 v2 上覆盖人工行。

**修改建议**：把版本前置条件传入真正落点，由宿主在所有异步准备结束后，对实际 TextDocument **同步**比对 `doc.version === expectedVersion`，失败时抛 `-32012`；与构造/提交版本感知的编辑之间不得再有让出点。范围文本前置条件也应绑定同一个文档快照。使用 VS Code 能执行版本 CAS 的路径，或核实 public WorkspaceEdit 的版本捕获时机并在其前紧贴同步校验。仅「再 await 读一次版本」仍有竞态；仅给 DSH 请求加串行队列也挡不住人工编辑。补两类回归：受控 barrier 的人工坐标漂移、同版本并发重放（至多一个成功）。

## 二、重要项

**无额外已证实的重要缺陷。特别是题设的「没有 grant 也能通过正常 applyEdit 线路探到 actual」在当前实际调用链上不成立。** 不能只读 handler 中的一段顺序就报漏洞。

- [connector.js:243–263](../packages/dsh-kit-bridge/src/connector.js#L243-L263)：协议兼容门后、分派前已有 grantGate。
- [capabilities.js:793–800](../packages/dsh-kit-bridge/src/capabilities.js#L793-L800)：dispatch 在 handler 前再次 grantGate。
- [index.js:758–775](../packages/dsh-vscode-kit/src/index.js#L758-L775)：DSH raw request 和糖衣发包前也过写权限门。
- [connector.js:301–312](../packages/dsh-kit-bridge/src/connector.js#L301-L312)：业务请求还有 token 准入校验；不是只有 grant 一层。

独立探针把文档设为 v7、请求设为 v1 且去掉 grant，经 dispatch 返回 `-32010 no-grant`，没有 actual；宿主零写入。**未发现无读权限连接能借此获取 actual，也未发现未授权写入成功。**

如果进程内消费者刻意绕过 dispatch，直接调用导出的 `handlers['vscode.applyEdit']`，确实会先得到 `-32012 actual:7`。但这不是 connector 的线路入口，而且同样的已准入、可信工作区上下文原本就可无 grant 调 `getDocumentState`。故不据此升级为阻断；它也不是能够证明「没有读权限」的连接。

**防御建议**：handler 开头同步补 grantGate（保留落点前复核），或不向外暴露未包门的原始写 handler；若未来引入独立读 ACL，应在读文档状态/文本之前检查，未授权统一 `-32010` 且 message/data 都不得带 actual。当前无需把 version 当作秘密或写权限令牌。
