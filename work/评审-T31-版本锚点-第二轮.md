## 二、重要项

### I1｜必改：Windows realpath 返回值未统一段名大小写，同文件进入两条队列

**位置**：[capabilities.js:224–226](<../packages/dsh-kit-bridge/src/capabilities.js#L224-L226>)、[capabilities.js:429–434](<../packages/dsh-kit-bridge/src/capabilities.js#L429-L434>)、[capabilities.js:748–749](<../packages/dsh-kit-bridge/src/capabilities.js#L748-L749>)。

**问题**：锁键使用 `canonicalPath(real)`，但 canonicalPath 只统一盘符大小写，不统一目录和文件名大小写。本机 Node v24.20.0 / Windows 的 `fs.realpathSync` 在这里保留了调用方段名大小写；“来自 realpath”并不等于“唯一字符串”。

**未经源码变异的独立复现**：[探针](<t32-independent.mjs>)、[完整结果:7–9](<t32-independent-complete.log#L7-L9>)、[安全断言原始失败](<t32-path-bypass-final-red.log>)。

1. 真文件为 [a.txt](<t32-fixture/a.txt>)。A 用原始绝对路径写，挂在版本前置检查后的 shape barrier。
2. B 用目录和文件名全大写、斜杠形式的绝对路径写；C 用 `./a.txt` 写。三个请求均为 expectedVersion=1。
3. 真文件系统 `stat` 确认 A/B **同 dev、同 ino**，不是两个不同文件。路径守卫均接受。
4. A 的 barrier 未释放，B 已读版本、经过 shape、完成 `applied:true`。同文件进入读阶段的次数为 **2（应为 1）**。C 仍在 A 的链上等待。
5. 同时另一文件 b 正常成功，证明不是全局锁；释放 A 后 A 因事务版本不符被拒、C 因前置版本不符被拒。**事务 CAS 保住了至多一成功，但队列确实已被别名绕过。**

实跑的真实路径键（节选）：

```text

B real: D:\CODE-WORKSPACE\PROJECTS\DSH-VSCODE-DEV\WORK\T32-FIXTURE\A.TXT
sameInode: true
sameFileReaders while A held: 2
```

复现命令与原始失败（exit 1；不是变异导致）：

```bash

```


**具体修改建议**：把“对外展示路径”与“锁身份键”分开。按当前路径守卫已有的 Windows 不区分大小写比较口径，对经过验证的 real 路径生成统一大小写锁键；非 Windows 保持原语义。不要为此改掉响应 file 的展示大小写。新增同实例能力层 barrier 回归：原始绝对路径 / 大小写别名 / 相对路径三者只能有一个进入锁内，另一文件仍可完成；同时保留事务内 CAS，不能以修锁代替版本落点门。

## 三、非阻断观察与建议

### N1｜重要但不阻断本轮：永久 pending 会永久占有该路径链

**位置**：[capabilities.js:441–450](<../packages/dsh-kit-bridge/src/capabilities.js#L441-L450>)、[capabilities.js:759–769](<../packages/dsh-kit-bridge/src/capabilities.js#L759-L769>)、[capabilities.js:816](<../packages/dsh-kit-bridge/src/capabilities.js#L816>)。

- reject 会释放：shape 抛错、editor.edit reject 两种独立注入中，已排队请求都能结束；移除故障后的下一条成功。证据：[结果:10–11](<t32-independent-complete.log#L10-L11>)。
- pending 不会释放：挂住 a 的 shape Promise、再排一条 a，观察窗口 100ms 后第二条仍未完成、同文件锁内 reader=1；另一文件 b 成功。主动解除 barrier 后队列继续。证据：[结果:12](<t32-independent-complete.log#L12>)。
- 100ms 本身不证明“无限久”；**无限阻塞结论来自代码没有 deadline/cancel/dispose 分支，release 仅在 tail settle 后执行**。客户端超时也没有在这段取消 task 的入口。任一宿主 await 永不 settle，就会持续占链，后续请求闭包亦会累积。

**建议**：增加有界排队/背压及可取消的准备阶段，明确实例销毁的收尾策略。已提交编辑不能简单 Promise.race 超时后放锁，否则仍在运行的旧写会与后继写交错；应取消或隔离在途操作、保留 CAS，并把提交后超时标成结果未知。这里没有实证旧版本成功、双成功或新的越权触发方式，**不据此增加 needs_revision 理由**。

### N2｜建议：提交后异常的结果未知语义宜显式编码，不能把所有 reject 当作零写

**位置**：[edit-transaction.js:115–159](<../packages/dsh-kit-bridge/src/edit-transaction.js#L115-L159>)；传输错误映射参照 [protocol.js:395–404](<../packages/dsh-vscode-kit/src/protocol.js#L395-L404>)。

- 正常冲突路径自洽：callback 发现 actual 不等，constructed 保持 false，apply 不执行；编辑器提交空集后抛 `-32012`。另一条 `applied:false` 且版本变化分支，也只在宿主明确返回 false 后声称“没有写”。未发现它们先写再报冲突。
- 通用 editor.edit 抛错没有 catch / 阶段标记。故障注入“宿主实际执行编辑后响应丢失并 reject”得到 buffer=DSH!!、version=2，同时向上抛普通 Error，data=null。证据：[结果:15](<t32-independent-complete.log#L15>)。正常传输层会把普通 Error 转为 `-32603`，不附 `mayHaveApplied`。
- **这是结果未知模型的故障注入，不是实际 VS Code 丢回复实测，不证明真实宿主已发生该问题。** 当前能力层 JSDoc 原本就把宿主调用后的超时/断线定为“可能已落点”，因此不能把“未带 mayHaveApplied”解释为“保证没写”。
- 另一个合成 log 抛错探针也可在成功后抛错（[结果:13](<t32-independent-complete.log#L13>)），但真实 [vscode-host.js:23](<../packages/dsh-kit-bridge/src/vscode-host.js#L23>) 已吞掉 OutputChannel 日志异常，**不把该合成情形当生产漏洞**。

**建议**：对提交后不确定异常显式包装 `mayHaveApplied:true, retryable:false`，已确认零构造的冲突继续返回确定未写；补“提交前抛错 / 主线程 CAS false / 提交后回复失败”三类测试。不能盲重试，也不能把 data 缺失当作 mayHaveApplied=false。本项非本轮返修理由。

### N3｜建议：测试标题不是四种真实调用；本轮已额外真正重放四入口

**位置**：[edit-transaction.test.js:380–407](<../packages/dsh-kit-bridge/test/edit-transaction.test.js#L380-L407>)。

## 四、B1 与并发逐项核实

### 1. 原子落点

- [capabilities.js:816](<../packages/dsh-kit-bridge/src/capabilities.js#L816>) 将 expectedVersion 本身传给宿主。
- [vscode-host.js:257–274](<../packages/dsh-kit-bridge/src/vscode-host.js#L257-L274>) 在所有 editorFor await 结束后进入 applyEditAtomically；apply 是同步的 Range / Position / builder.replace。
- [edit-transaction.js:115–131](<../packages/dsh-kit-bridge/src/edit-transaction.js#L115-L131>) callback 内同步读取 `editor.document.version` → 等值比较 → apply(builder)，**没有 await**。不等在 constructed=true 之前 return，故 **constructed===false**、零 builder.replace；随后回调外抛冲突。
- 只靠扩展宿主同步段还不足以防主线程输入；还依赖 TextEditor.edit 带版本提交，主线程 CAS 不符整体拒绝。本轮读取上游原文核对：[ExtHostTextEditor](<https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/api/common/extHostTextEditor.ts>) 的 TextEditorEdit 构造器捕获 document.version、edit 同步 callback、_applyEdit 传 documentVersionId；[MainThreadTextEditor](<https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/api/browser/mainThreadEditor.ts>) 的 applyEdits 先比 getVersionId，不等直接 false，相等才 executeEdits。这是读取时 main 源码证据，不冒充已安装 VS Code 版本的真机审计。

### 3. 并发、键与释放

- 同路径 expectedVersion=1 并发两条真实 kit.request：恰好 `applied:true` 一次、`-32012` 一次；宿主调用1、构造1、版本仅1→2。证据：[结果:5](<t32-independent-complete.log#L5>)。

### 4. 保证边界（必答）

**这个锚点在同一文档版本生命周期内、调用方确实依据该 expectedVersion 的快照推导坐标、且实际宿主使用当前同步版本判定 + TextEditor.edit 主线程版本 CAS 时，能保证不把“取锚点之后发生的人工改动”按旧坐标覆盖；如果调用方拿新版本配旧坐标、主动替换快照里已有的人工文字，或换成不执行该 CAS 的适配器，仍不能保证不覆盖人工改动。** 它不是内容合并器，也不是允许读取新版本后盲目重试的许可。队列本身不是防人工竞争的保证。
