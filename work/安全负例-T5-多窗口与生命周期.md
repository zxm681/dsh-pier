## 1. Q1 多窗口并发写同一文件

### 1.1 写目标按 grant 绑定 —— **成立**

`[源码]` `packages/dsh-vscode-kit/src/index.js:713-731`：

```js
// 读路径：当前活跃连接；写路径：**grant 记录里的承载连接**，不经过 `_activeLink()`。
let link
let wireParams = params
if (write) {
  const bound = this._bindWriteTarget(params, sessionId)
  link = bound.link
  wireParams = bound.params
} else {
  link = await this._waitForEditor(waitMs)   // ← 读路径：活跃连接
}
```

`_bindWriteTarget`（`src/index.js:250-265`）取 `grant` 记录里的承载连接，`_liveTargetOrNull` 校验存活；`src/index.js:240-247` 的注释写明这是评审 F3 的口径（"B 后连不影响 A 一个字"）。`[单测]` `★ T5 多窗口：写目标按 grant 绑定…` 断言 A 收到 1 帧、B 收到 0 帧；变异 M-C（写路径退回 `_activeLink()`）→ 该用例红。

### 1.2 版本锚点在多窗口下 —— **不成立**（本次新增高危）

读路径走 `_activeLink()`（`src/index.js:316-334`：扫 `server.trusted` 取 **`connSeq` 最大**的活连接）。而 `vscode.getDocumentState` 是**读**方法 → 它永远问**最新连上的那个窗口**，与"哪个窗口被授权写入"无关。

后果链（全部在契约要防的那条线上）：

1. A 窗口拿到 grant（承载连接 = A）；
2. B 窗口后连（`connSeq` 更大）；
3. DSH 调 `vscode.getDocumentState` → **落在 B**，拿到的是 **B 的 `TextDocument.version`**；
4. DSH 用这个数字当 `expectedVersion` 调 `vscode.applyEdit` → **落在 A**（`src/index.js:713-731` 写路径）；
5. A 侧版本门比的是"锚点 vs **A** 的 `document.version`"。两个窗口是两个独立模型实例、各数各的 `document.version`（T4 报告 §9 已指出"两个缓冲区的改动会互相打架"）。
   - 数字不等 → `-32012`（fail-closed，但 DSH **永远无法**拿到 A 的版本，多窗口下写入长期不可用）；
   - **数字相等 → 放行**，按 **B 视角的坐标**写进 A 的缓冲区。这不是竞态（不需要并发时序），是**结构性**的：只要两份文档版本数字撞上就成立。

`[单测]` 三条守它：
- `★ T5 多窗口：锚点从"活跃连接"B 读、写入按 grant 落 A（版本锚点跨窗口不成立）` —— 断言 `getDocumentState` 在 A 上 **0 次**、B 上 1 次，而 `applyEdit` 落 A 且帧里的 `expectedVersion` 等于 B 报的版本；
- `★ T5 多窗口：两窗口版本数字重合时不报错，写按 B 的锚点放行（静默错配的最小证据）` —— 数字相等时本端无处可判，照常发帧，收端也不会拒；
- 变异 M-D（`_activeLink()` 取最小 `connSeq`，即"读回退到先连窗口"）→ 第 ② 条红，证明断言咬住的是"读到哪份文档"这件事本身。

**为什么算高危**：T30/T31 引入 `expectedVersion` 的**唯一目的**是"锚点必须描述被写的那份文档"。多窗口下这条不变式在 kit 层就断了；而多窗口打开同一文件夹是正常用法，不是异常配置。

### 1.3 会不会一个窗口的写落到另一个窗口的缓冲区

按字面回答：**写帧本身只会到 grant 窗口**（§1.1 成立）；但**坐标与锚点**可能来自另一个窗口（§1.2），所以"另一个窗口的内容被按别人的视角改掉"是成立的 —— 只是被改的是 grant 窗口自己的缓冲区，改的依据是别的窗口的视图。

- 已做：`[单测]` 两连接模型（帧级）+ `[源码]` 行号，两半结论都落在可复现的断言上。

## 2. Q2 磁盘被外部改动后按旧锚点写

### 2.1 干净文档：外部脚本改磁盘 → 编辑器重载 → 旧锚点被拒 `[真机]`

`ws/solo.txt` 版本 1、`isDirty:false`；用 `printf 'only one\nonly two\nEXTERNAL-A\n' > ws/solo.txt`（**非编辑器**）改磁盘，等 2s：

- `getDocumentState` → `version: 2`、`isDirty:false`，文本已含 `EXTERNAL-A` → **VS Code 静默重载并 `version+1`**；
- 用旧锚点 `expectedVersion: 1` 写 → `-32012`，message `document version is 2, but the request was prepared for version 1; re-read vscode.getDocumentState and re-apply against the current version`，`data {expected:1, actual:2}`。

**结论：不会静默覆盖外部改动。**

### 2.2 脏缓冲区：外部脚本改磁盘 → 不重载 → 旧锚点放行，但只改内存 `[真机]`

`ws/shared.txt` 脏 v2（含 DSH 写入的 `DSH-E3 `）；外部写入 `alpha one\nbeta two\nEXTERNAL-B\ngamma three\ndelta four\n`，等 2s：

- `getDocumentState` **仍 `version: 2`**、`isDirty:true`、缓冲区**未**重载（VS Code 不重载脏缓冲区，实测）；
- 用 `expectedVersion: 2` 写 → `applied:true`、`saved:false`，缓冲区变 `alpha one\nDSH-STALE DSH-E3 beta two\ngamma three\ndelta four\n`；
- **磁盘仍是外部内容**（含 `EXTERNAL-B`）—— DSH 没有保存能力（§4），一个字节都没落盘。

**结论：DSH 不会静默覆盖磁盘外部改动。** 但如实记录残留风险：**DSH 感知不到"磁盘与缓冲区已分叉"**（`writeUnderLock` 没有 `isDirty` 门，`capabilities.js:795-877`），它写的是缓冲区；此后**任何一次保存**（用户按 Ctrl+S、或别的工具）都会把外部改动覆盖掉，而 `-32012` 这条保护在这条链上**不会出现**。

`[单测]` `★ T5 Q2a …` / `★ T5 Q2b …` 两条把两个分支都钉住（含"磁盘字节未变"断言）；变异 M-AB（见 §5）→ Q2a 红。

## 3. Q3 丢弃缓冲区的生命周期（T31 遗留未决问题）

### 3.1 机制：判定就是一个整数相等 `[源码]`

`packages/dsh-kit-bridge/src/edit-transaction.js:115-131`：

```js
const actual = editor.document.version
observedVersion = actual
if (actual !== expectedVersion) {
  conflict = { expected: expectedVersion, actual }
  return // ← 不构造任何 edit
}
```

`document.version` 是**纯整数**，协议与宿主侧都**没有**任何「这份文档是哪一次打开」的身份（`vscode.getDocumentState` 的返回形状 `{file, version, isDirty, eol, lineCount, textLength}` 里也没有 incarnation / mtime / 内容指纹）。因此只要两份 incarnation 的版本数字相同，旧锚点就**能重新匹配**。

### 3.2 已拿到的真机数据 `[真机]`

| 场景 | 观测 |
|------|------|
| 三个文件首次创建（`shared.txt` / `solo.txt` / `other.txt`） | `document.version` 全是 **1** |
| 干净文档被外部改写 → 重载 | `version` **1 → 2**（+1，不复位） |
| 脏缓冲区 + 外部改写 | `version` **不变** |
| 一次成功写入（Dirty 化） | `version` **+1** |

### 3.3 没测到的（也是本卡的"无法判定"部分）

"关闭再打开" / "revert 丢弃改动" / "保存后重载" 之后 `version` 是否**回退到 1**——这三步都需要真实 IDE 操作。本轮桌面输入被中断（§1.4），且协议层**没有**关闭文档的路径：`vscode.openFile` 走 `showTextDocument({preview:true})`，实测打开 `other.txt` 后 `listOpenEditors` 仍是 3 个（preview 不替换已存在/脏的 editor，见 `vscode-host.js` 的 `editorFor`）。所以**这一步本轮无法在协议内自证**。

### 3.4 判定

- 若真机证明"关闭再打开后 `version` 回到 1"（VS Code 新建 `TextDocument` 的常见行为，且与 §3.2"首次创建都是 1"一致）→ **高危**：旧锚点可对**另一次打开的另一份内容**重放，落点是别人的上下文；
- 机制侧已经**不依赖**上述假设：`[单测]` `★ T5 Q3 新的 incarnation 版本数字相同时，旧锚点重新匹配（无 incarnation 身份）` 证明了"版本相等 ⇒ 门无法区分第几次打开"，落点证据是 `REOPENED alpha` 被切成 `REPLAY!NED alpha`；
- 因此本卡对 Q3 的结论写作 **`无法判定（缺真机生命周期数据）`**，但把"若复用即高危"的机制、复现步骤、行号全部给出，并附一条反向用例（`★ T5 Q3 版本数字不相等时被拒`）说明这道门**只**靠这一个整数。

**修法（未实施）**：`getDocumentState` 增补一个不透明 `incarnation`（扩展侧首次打开时 `crypto.randomUUID()`，`onDidOpenTextDocument` 换新；`applyEdit` 的锚点必填它并一等比对）。这比"重开后把 version 调大"可靠——后者依赖 VS Code 的行为。

## 4. Q4 删除 / 保存能力必须仍然不存在

### 4.1 真机 `[真机]`（对被中断前的真实扩展，port 7410）

| 请求 | 结果 |
|------|------|
| `vscode.save` / `vscode.deleteFile` / `vscode.getDocumentText` / `vscode.renameFile` / `vscode.writeFile` / `fs.delete` | `-32005`，message `editor does not advertise capability for "<method>"`，`data.capabilities` 恰好 6 项：`vscode.openFile, vscode.getSelection, vscode.getDiagnostics, vscode.listOpenEditors, vscode.applyEdit, vscode.getDocumentState` |
| `bridge.save` | `-32005 capability not implemented: bridge.save`（DSH 侧 `dispatch`） |
| `notify vscode.applyEdit` | `-32600`：`write method "vscode.applyEdit" cannot be sent via notify: it has no receipt and no write gate; use request()` |
| `notify vscode.save` | `-32005`（本地能力预检，帧未出门） |
| 裸协议探针（绕过 kit 预检）发 `vscode.save` / `constructor` / `__proto__` / `toString` / `valueOf` | 一律 `-32601 unsupported inbound method`（DSH 入站白名单）→ 扩展 `dispatch` 无法从线路直达 |

### 4.2 "没有任何路径能把它们变成可用" `[源码]` + `[单测]`

1. **对外声明唯一源**：`packages/dsh-kit-bridge/src/capabilities.js:24-33` 的 `CAPABILITIES` 是静态数组（构建期写死），hello 与发现文件都读它；
2. **handler 表是闭包内字面量**：`capabilities.js:879-886` 六个键；`dispatch`（`:892-906`）`if (!handler) throw -32005`，入口之后才是 `assertTrusted` → `grantGate` —— **能力门先于授权门**，所以"给不给 grant、可不可信"都不影响结论（`[单测]` 用例把可信 + 有效 grant 拉满仍是 `-32005`）；
3. **无注册 API**：`createCapabilities` 只 `return { dispatch, handlers, CAPABILITIES }`，线路侧没有任何写 `handlers` 的方法；
4. **写门白名单**：`packages/dsh-vscode-kit/src/grant.js:96` `WRITE_METHODS = Object.freeze(['vscode.applyEdit'])`，新写能力必须同时登记，否则写门静默失效（**信息级建议**：加能力时把这两处绑成一个断言）。

`[单测]` `★ T5 Q4 删除/保存能力不存在…` 覆盖 1-3 并额外断言 `Object.keys(handlers)` 与 `CAPABILITIES` 一一对应。

### 4.3 附带发现（**不可利用**，信息级）

`handlers` 是普通对象字面量，`dispatch` 用 `handlers[method]` 取值 → 走原型链。进程内实测：

```
dispatch('constructor') → RESOLVED，返回参数回显 {file: ...}
dispatch('toString')    → RESOLVED "[object Undefined]"
dispatch('__proto__')   → TypeError: handler is not a function
```

即"未实现方法"的 `-32005` 可以被**继承属性名**跳过。但**换不到任何能力**：拿到的只是回显/字符串/TypeError，不碰缓冲区、不碰磁盘（用例断言 `totalOps` 与磁盘字节均未变）；线路上还有两道门（kit `_assertCapability` 回 `-32005`、DSH 入站白名单回 `-32601`，均真机实测）→ **不是可利用路径**。加固建议：`Object.hasOwn(handlers, method)` 或 `Object.create(null)`。
