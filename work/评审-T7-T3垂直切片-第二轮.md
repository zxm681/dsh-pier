**独立确定性复现**：新夹具 `work/t25-r2-fs-iLW8km`，字面根 `WorkspaceFresh`，其外同级 `OutsideFresh/a.txt`。先检查根内普通目录 `Swappable/a.txt`；在文档 shape 的 await 缝隙将自己的 `Swappable` 移至 `Swappable.backup`，原位置建立指向 `OutsideFresh` 的真实 junction；随后让文档 shape 完成。无需修改源码或 grant。

```text
VERIFIED_OWN_RENAME {
  from: ".../WorkspaceFresh/Swappable",
  to: ".../WorkspaceFresh/Swappable.backup", withinFixture: true
}
label: TOCTOU-after-check-before-apply
```

关键复现结构（`victim`、`backup`、`outside` 全属本轮自建夹具）：

```js
host.readDocumentShape = async () => {
  await Promise.resolve();
  fs.renameSync(victim, backup);
  fs.symlinkSync(outside, victim, 'junction');
  return { lineCount: 1, lineLengths: [6, 6] };
};
host.applyEditText = async (abs, range, text) => {
  calls.push({ abs, actual: fs.realpathSync(abs), range, text });
  return { applied: true };
};
```

**字符串绑定裁决**：不是“检查 A，却直接把未经检查的原始 B 传给宿主”。当前传给 shape 和 apply 的都是检查产物 `real`，这点正确。漏洞是同一字符串没有固定物理身份，检查结果跨 await 被继续信任。把 `abs` 换成 `real` 并不能消除这种窗口。

**要求修法**：把目标验证、文档身份/版本和落点绑定在同一受保护操作中；至少补 await 后、首次读宿主文档前及写点前的重验并做目录替换回归，但不得把“最后再 lstat 一遍”宣称为原子防护。若威胁模型包含同用户进程并发换目录，需要 Windows 防替换/句柄锁定等可证实机制，或明确收紧该阶段可写路径/威胁模型，不能继续声称全链检查就是完整边界。本轮已经把上一轮的 TOCTOU 疑问升级为**真实 FS + 写宿主调用的绕过证据**。

### R2-2 / 阻断：等回执前 grant 已 active；无任何回执仍可并发写（F9 修法引入的中间态）

**位置**：[index.js:412–427](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/index.js#L412-L427>)、[index.js:137–166](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/index.js#L137-L166>)、[grant.js:139–154](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/grant.js#L139-L154>)。

`grants.issue()` 立即插入 active 表，然后才 await `bridge.grant` 回执。另一调用不必知道 id/epoch，只需同 session，就能通过 `_grantForSession()` 取出这条尚未确认的记录并自动补凭证。超时后 revoke 只能阻止未来写，不能抹掉等待期间已发生的写。

**独立实测一：真实 TCP + kit facade，对端永不回应 grant**：

```text
ACK_PENDING_STATE {active:"active", settled:false}
WRITE_WITHOUT_ANY_ACK {applied:true,file:"fixture.txt",saved:false,textLength:1}
ACK_PENDING_WRITE {frames:1,settled:false}
NO_ACK_FINAL {result:{code:-32004},active:0}
```

**独立实测二：真实协议端点 + GrantStore.adopt + createCapabilities.dispatch**，grant handler 存档后永不回包，写请求由真实 capabilities 执行，不是对端直接伪造 applied：

```text
REAL_HANDLER_NO_ACK {
  result:{applied:true,file:".../t25-r2-handler-anv9NL/ws/a.txt",saved:false,textLength:1},
  writes:[{abs:".../ws/a.txt",r:{start:{line:0,column:0},end:{line:0,column:0}},t:"X"}],
  localActive:1,remoteActive:1
}
REAL_HANDLER_NO_ACK_FINAL {
  grantResult:{code:-32004},localActive:0,remoteActive:1,writes:1
}
```

复现顺序：先启动但**不 await** `editing.grant({sessionId:'S-await',timeoutMs:150})`；等对端确认已收到报文（只作测试栅栏，**不是协议 ack**）；调用 `vscode.applyEdit(params,{sessionId:'S-await'})`（params 不带 grant）；写宿主调用完成；最后 grant 超时报错。

这直接违反本轮“无回执 = grant 不生效”的验收要求。不是在指控网络攻击者猜出了随机凭证；是本地状态机提前发布了还没生效的权限。

**要求修法**：引入 pending 状态，不得被 lookup-active、`_grantForSession` 或 writeGate 用于放行；回执验证且连接/授权仍有效后再原子激活。失败时还要收口执行端已 adopt 的 pending 权限（可通过撤销/终止该承载连接等方式；不能把“没收到回执”当“对端没存档”）。补“回执被挂起/永不返回，同时同 session 自动找 grant 写入”的并发回归；断言等待期间 host 零调用、active 为零，超时后仍不可写。

### Q3：ack 只比 id、不比 epoch，是否可接受？

位置：[index.js:419–423](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-vscode-kit/src/index.js#L419-L423>)、[connector.js:103–113](<D:/code-workspace/projects/dsh-vscode-dev/packages/dsh-kit-bridge/src/connector.js#L103-L113>)；契约[400](<D:/code-workspace/projects/dsh-vscode-dev/docs/协作编辑-钩子契约.md#L400>)明确 epoch 是冗余校验、id 已唯一。

独立对端返回 `{ok:true,id:本次id,epoch:'wrong'}`，当前 `grant()` 确实 `delivered:true,active`，并将返回 ack 归一成 `{ok:true,id}`。**不把这点判成独立安全阻断**：ack 本来就没有规定 epoch 字段；随机128-bit id 标识本次授权，请求/响应按该承载连接的 pending 配对，写点还会检查 epoch。正常可信扩展 handler 先 adopt 实际收到的 id/epoch，再回同 id，能确认这一条投递；不知道本次 id 的其他连接不能仅靠缺 epoch 假造确认。已被攻陷/故意撒谎的授权对端也能照抄 epoch，回显它不是签名。建议明确 ack schema，并可增加 epoch 回显以检测实现/串包错误；不应让它掩盖已经实证的 pending-active 漏洞。
